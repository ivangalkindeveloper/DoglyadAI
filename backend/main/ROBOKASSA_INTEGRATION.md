# План интеграции Robokassa в Doglyad

Проверено 1 ноября 2026 года. Предлагаемый вариант: backend создаёт и проверяет
платежи, клиент открывает платёжную страницу Robokassa. Учёт подписок остаётся
в PostgreSQL. Это проект изменений; платёжный код пока использует ЮКассу.

## Схема покупки

```text
Paywall: план -> backend: заказ, сумма, согласие и контакт для чека
  -> платёжная страница Robokassa -> оплата
       +-> ResultURL -> проверка на backend -> подписка в PostgreSQL
       +-> Робочеки СМЗ -> регистрация дохода в ФНС и чек покупателю
Возврат в приложение -> checkPayment(paymentId) -> refreshStatus()

Продление: billing_worker -> новый счёт по сохранённой родительской оплате
  -> проверка результата -> новый оплаченный период и чек
```

Возврат в приложение и успешный callback мобильного окна не доказывают оплату.
Backend сопоставляет конкретные заказ, план, сумму, магазин и среду. Повторное
уведомление не добавляет второй период доступа.

## Платёжный интерфейс клиента

Официальные SDK существуют для [iOS](https://github.com/robokassa/sdk-ios/) и
[Android](https://github.com/robokassa/sdk-android). iOS SDK показывает WebView,
а публичный инициализатор требует `password` и `password2` магазина. В просмотренном
API нет публичного входа только с готовой платёжной ссылкой.
Поэтому предлагается открыть серверную ссылку через браузерный адаптер, без этих SDK.
Пароли магазина остаются на backend. Форк SDK для этого не требуется.

Для выпуска iOS по `ExternalPurchaseLink` использовать имеющуюся страницу `/pay`.
В `SKExternalPurchaseLink` задаётся постоянный HTTPS URL без query-параметров.
Одноразовый код существующего checkout свяжет браузер с владельцем и выбранным планом.
Страница сохраняет добавленный StoreKit токен, затем переводит на оплату.
Это короткая платёжная страница без регистрации и веб-кабинета пользователя.
Нужны допуск Apple и отчётность внешних покупок.
[External Purchase](https://developer.apple.com/documentation/storekit/external-purchase),
[требования к URL](https://developer.apple.com/documentation/bundleresources/information-property-list/skexternalpurchaselink)

Android в RuStore сможет открывать checkout по одноразовой ссылке в браузере.
Для Google Play вне РФ сохраняется план интегрировать нативный Google Play Billing.
Применимость внешней оплаты в других сборках определяется правилами их магазина.
Прямое открытие ссылки в локальной iOS-сборке позволяет проверить интеграцию,
но не проверяет разрешённый Apple сценарий для релиза.

## Изменения кода

| Участок | Предлагаемое изменение |
|---|---|
| `app/service/billing/robokassa_payment_provider.py` | Новый `RobokassaPaymentProvider`: HTTP через существующий `httpx.AsyncClient`, подписи и проверенные результаты провайдера. |
| `SubscriptionService`, `ServiceFactory`, `BillingWorker` | Подключить новый провайдер. Сохранить блокировки владельца, снимки цены и периода, учёт использования и восстановление. Заменить формат платежей и продлений ЮКассы. |
| `PaymentGateway`, `ApplicationFactory` | Добавить `/webhooks/robokassa`; переиспользовать `/pay` и страницы возврата. Клиентские операции оставить под App Check и bearer. |
| `server.json`, Caddy, deployment | Политики новых маршрутов в общем `endpoints`; публичный HTTPS callback направить в payment-приложение. |
| `SubscriptionRobokassaRepository` | Заменить `SubscriptionYooKassaRepository`; только неизменяемые зависимости и операции с backend. |
| `SubscriptionRepositoryFactory` | На каждой операции получать storefront; `RUS` выбирает Robokassa. Управление покупкой выбирается по её источнику. |
| `SubscriptionRootViewModel`, Paywall, ManageSubscription | Сохранить владение состоянием, задачами и конкретной ожидающей покупкой. Добавить браузерный платёжный адаптер и обновление статуса после возврата. |
| Доменные модели | Добавить источник `robokassa`, обновить ссылки на покупку и HTTP-модели. Убрать SDK-поля ЮКассы и `tokenize_payment` после замены потока. |

`SubscriptionStoreKitRepository`, Apple verification, каталог из восьми продуктов,
локализованные названия и цены в `amountMinor` сохраняются. Цены для Apple по-прежнему
поступают из StoreKit. Комиссию калькулятора обновить по договору Robokassa.

## Методы Robokassa

| Операция | Интерфейс и обработка |
|---|---|
| Первая оплата | `CreateInvoice`, `InvoiceType=OneTime`; сохранить `id`, числовой `invId`, URL. Для согласованных автосписаний передать `Recurring` в `AdditionalParameters`. Подпись формирует backend. |
| Уведомление | `ResultURL`: проверить подпись с паролем №2 и исходными строковыми значениями, затем сумму и заказ. Ответ `OK{InvId}` — после сохранения обработки. |
| Проверка боевой оплаты | `OpStateExt`: успешный запрос и `State.Code=100`. Проверять реквизиты операции и точный заказ, сохранять `OpKey`. |
| Продление | `POST /Merchant/Recurring`: новый `InvoiceID`, сохранённый `PreviousInvoiceID`. Ответ `OK` ещё не подтверждает списание. |
| Возврат | `Refund/Create` с `OpKey` и паролем №3; сохранить `requestId`. Проверять `Refund/GetState` до окончательного результата. |

[Invoice API](https://docs.robokassa.ru/ru/invoice-api),
[уведомления](https://docs.robokassa.ru/ru/notifications-and-redirects),
[статусы](https://docs.robokassa.ru/ru/xml-interfaces),
[автосписания](https://docs.robokassa.ru/ru/recurring-payments),
[возвраты](https://docs.robokassa.ru/ru/refund-api)

Собственный worker управляет расписанием. Параллельно включать расписание подписок
в кабинете Robokassa нельзя. Согласие на автосписания и его версия сохраняются.
Отмена останавливает будущие списания; уже отправленная операция продолжает сверяться.
До сетевого вызова сохраняются идентификатор операции, факт отправки и снимок
родительской оплаты. Не переносить эту ответственность в мобильный клиент.
При тайм-ауте сохраняется прежний идентификатор операции. Не создавать новый счёт
или возврат, пока неопределённый исход предыдущего запроса не разрешён.

## База данных и идентификация

- Сохранить UUID заказа и связь с анонимным владельцем. Добавить числовой `invoice_id`,
  магазин, среду, идентификатор счёта провайдера и родительский счёт продления.
  Уникальность задаётся с учётом магазина и среды.
- Обновить ограничения и индексы источника подписки. Старые оплаты ЮКассы нельзя
  переименовывать в оплаченные через Robokassa или использовать для новых автосписаний.
- Хранить контакт для чеков отдельно от секрета владельца. Предлагается собрать email
  на платёжной странице и сохранять для продлений. Email не подтверждает владение подпиской.
- Сохранить Keychain-идентификацию и восстановление по recovery key. Авторизация
  пользователей и отдельный сервис учёта не требуются. Бэкапы PostgreSQL сохраняются.
- Полные и частичные возвраты хранить отдельно от доступа. Успешное создание заявки
  возврата ещё не означает возврат денег.

## Чеки НПД и вопросы подключения

После активации «Робочеков СМЗ» регистрацию дохода и доставку чеков выполняет
Robokassa. Собственную повторную выдачу чеков не создавать.
[Описание сервиса](https://robokassa.com/online-check/robocheck-smz/)

У магазина нужно подтвердить автосписания для НПД, состав данных для корректного
названия подписки в чеке и корректировки при полном/частичном возврате. Отдельно
запросить способ получения статуса и ссылки чека, сверки возвратов из кабинета и
разрешения неизвестного результата запроса возврата. Публичный Refund API не описывает
ключ идемпотентности и поиск потерянного `requestId`; автоматический повтор опасен.
Автоматическую корректировку НПД нельзя считать подтверждённой общим API возвратов.

`Receipt/Register` для отложенных кассовых чеков прямо исключает самозанятых и ИП
на НПД. Для этой задачи его не использовать.
[Ограничение](https://docs.robokassa.ru/ru/deferred-receipt-registration)

## Настройки и проверка

В `backend/main/secrets/.env.development` владелец задаёт `ROBOKASSA_MERCHANT_LOGIN`,
`ROBOKASSA_PASSWORD1`, `ROBOKASSA_PASSWORD2` из тестовых настроек.
В `.env.production` — боевые значения и `ROBOKASSA_PASSWORD3` для возвратов.
Это предлагаемые новые имена: текущий код их ещё не читает.
`ENVIRONMENT=development` должен принудительно включать `IsTest=1`; production
использует боевой режим. При замене сохранить блокировку реальных списаний до готовности.

Настроить публичный `ResultURL`, `SuccessURL`, `FailURL` и алгоритм подписей,
совпадающий с адаптером. Для проверки с iPhone через локальный backend понадобится
публичный HTTPS callback или изолированный development-сервер. Сам `localhost`
недоступен серверам Robokassa.

`OpStateExt` не поддерживает тестовые платежи. В development проверять подписанный
`ResultURL` тестовым паролем и ожидаемый заказ; не подменять ошибку API успехом.
В production сверять боевую операцию через API. `ResultUrl2` не является основой
тестового потока: тестовая среда его не отправляет.
[Тестовый режим](https://docs.robokassa.ru/ru/testing-mode),
[ограничение OpStateExt](https://docs.robokassa.ru/ru/xml-interfaces)

Проверить первую оплату, продление, отмену, дубли уведомлений, неверные подпись/сумму,
смешение сред, тайм-ауты, возврат, перезапуск приложения и восстановление на другом
устройстве. Реальную доставку чека НПД подтвердить отдельно при боевом запуске.
Остальные условия запуска — в [BILLING_RELEASE_PLAN.md](BILLING_RELEASE_PLAN.md).

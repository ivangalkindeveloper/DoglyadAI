# Локальная проверка подписок

## Коротко

- `Backend: Local Mock` в VS Code запускает PostgreSQL в Docker, ожидает готовности и применяет миграции до старта API.
- `BILLING_DATABASE_URL` — строка подключения: адрес PostgreSQL, порт, имя БД, пользователь и пароль. Локальный профиль задает ее автоматически.
- Без URL backend работает без подписок. При заданном URL он проверяет доступность таблиц.
- Локальная БД доступна на `127.0.0.1:5433`. Данные лежат в Docker-томе `doglyad-local-billing-data` и сохраняются между запусками.
- В отдельном billing Compose данные PostgreSQL лежат в томе `billing_database`, внутри контейнера — `/var/lib/postgresql/data`.
- После подготовки БД примените миграции. Для оплаты запустите API и worker; для уведомлений нужен gateway с HTTPS.
- Миграции меняют структуру БД. Они не заменяют резервную копию и не восстанавливают удаленные платежи.

## Автоматическая подготовка локальной БД

Запустите Docker Desktop. Выберите профиль `Backend: Local Mock` в VS Code.
Его подготовка загружает обычное development-окружение, затем запускает
`tools/local_billing_database.py` через Make. Скрипт поднимает PostgreSQL 17,
ждет успешной проверки готовности и выполняет `alembic upgrade head`.
Ошибка подготовки останавливает запуск API. App Check остается обязательным.

БД можно подготовить отдельно из корня проекта:

```sh
make start-local-billing
make stop-local-billing
```

Остановка сохраняет контейнер и том. Автоматического удаления данных нет.
Локальная БД использует опубликованные тестовые реквизиты из
`docker-compose.local-billing.yml` и слушает только loopback-интерфейс.
Скрипт миграций всегда выбирает development и эту локальную БД.

Локальный URL:

```text
postgresql+asyncpg://doglyad_local:doglyad_local_only@127.0.0.1:5433/billing
```

Для ручного запуска API, worker и gateway передайте этот URL в их окружение.
Другие профили VS Code сохраняют свою прежнюю настройку подключения.

## Миграции

`migrations/env.py` берет подключение из `BILLING_DATABASE_URL` и загружает модели БД.
`alembic.ini` задает пути миграций и Python-импортов. `script.py.mako` служит шаблоном
для новых файлов в `versions/`. В каждом файле есть `upgrade()` и `downgrade()`.
Таблица `alembic_version` хранит текущую версию схемы.

Текущая история сведена до первого релиза к одной начальной миграции:

```text
Пустая БД -> 0001_initial -> текущие таблицы, поля, индексы и ограничения
```

Команды ниже выполняются из `backend/main` с заранее загруженным окружением:

```sh
../../.venv311/bin/python -m alembic current
../../.venv311/bin/python -m alembic history
../../.venv311/bin/python -m alembic upgrade head
```

Для изменения структуры моделей создайте миграцию на отдельной БД разработки:

```sh
../../.venv311/bin/python -m alembic revision --autogenerate -m "Describe schema change"
```

Проверьте сгенерированные `upgrade()` и `downgrade()`, включая перенос существующих
данных. Выполните `make format-backend` из корня проекта. Проверьте миграцию на копии БД.
Перед обновлением рабочей БД сделайте резервную копию и остановите API, gateway и worker.
Примените `upgrade head`, затем запустите процессы новой версии. Billing Compose
выполняет миграцию отдельным процессом до запуска приложений.

После первого релиза не меняйте уже примененные миграции. Исправления оформляйте
следующей миграцией. Откат `0001_initial` разрешен только для пустой БД и удаляет
ее таблицы. При наличии данных он завершается ошибкой до удаления таблиц.

Если локальная БД использовала прежние пять миграций, сначала сделайте резервную
копию и сверьте полную схему с `0001_initial`. При полном совпадении можно сменить
только метку Alembic, сохранив записи:

```sh
../../.venv311/bin/python -m alembic stamp --purge 0001_initial
../../.venv311/bin/python -m alembic check
```

`stamp` не создает и не изменяет таблицы. Не применяйте его к БД с неполной старой
схемой. Такую БД без нужных данных можно пересоздать отдельно; обычный локальный
запуск не удаляет данные автоматически.

## Подробная настройка

Локальный main backend поддерживает подписки. Обычный запуск `Backend: Local Mock`
подменяет только генерацию ИИ: PostgreSQL и платежные провайдеры остаются настоящими.
Каталоги уже содержат восемь Apple-продуктов и восемь тарифов ЮКассы. Для оплаты
все равно требуются локальная БД, миграции и настройки тестового магазина.

## Что подготовить

1. Локальную PostgreSQL через `make start-local-billing` либо собственный сервер
   PostgreSQL с отдельным `BILLING_DATABASE_URL`.
2. В `config/development/billing.json` уже настроены тарифы в общем списке `products`.
   Apple использует их ID, а ЮКасса — также период и рублевую `price`. При необходимости
   для отдельного локального окружения можно использовать минимальный каталог:

   ```json
   {"termsVersion":"local-test-v1","tiers":[{"id":"pro","titleLocaleKey":"paywallProLabel",
      "featureLocaleKeys":["paywallProModelsDescription"]}],
    "products":[
     {"id":"local-pro-monthly","period":"monthly",
      "titleLocaleKey":"subscriptionProMonthlyLabel",
      "priceTemplateLocaleKey":"subscriptionMonthlyPriceDescription",
      "entitlement":"pro","price":{"amountMinor":10000,"currencyIso2Code":"RUB"}}
   ]}
   ```

   Поддерживаемые периоды ЮКассы: `weekly`, `monthly`, `sixMonth`, `annual`.
   Действующие начальные цены и источник пересчета указаны в [BILLING.md](BILLING.md).
3. Тестовый магазин ЮКассы с разрешенными платежами через мобильный SDK:
   `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `YOOKASSA_CLIENT_APPLICATION_KEY`.
   Режим определяется через `ENVIRONMENT`: `development` разрешает только тестовые
   магазины и платежи, `production` — только боевые. Для локальной проверки нужны
   `ENVIRONMENT=development` и реквизиты тестового магазина в `secrets/.env.development`.
   Оставить `IS_YOOKASSA_LIVE_ENABLED=false`: это временная блокировка реальных
   списаний до выполнения условий запуска. `IS_YOOKASSA_TEST_ALLOWED` больше
   не используется. Ключи передаются только через секретное окружение.
4. Обычные настройки Firebase и SMTP, `ENVIRONMENT=development`,
   `MODEL_SERVICE_TYPE=mock`. Firebase App Check остается обязательным;
   debug-токен симулятора должен быть зарегистрирован в Firebase.

## Запуск

Команды ниже выполняются из `backend/main` с одним и тем же заранее загруженным
окружением. `Variables` не читает `.env` автоматически. VS Code загружает
`secrets/.env.running` через свой `envFile`; процессы, запущенные отдельно в
терминале, это окружение автоматически не получают.

Сначала применить миграции:

```sh
../../.venv311/bin/python -m alembic upgrade head
```

В разных терминалах запустить API и обработчик сверки платежей:

```sh
../../.venv311/bin/python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

```sh
../../.venv311/bin/python -m app.billing_worker
```

Для входящих уведомлений дополнительно запустить платежный ingress:

```sh
../../.venv311/bin/python -m uvicorn app.payment_main:app --host 127.0.0.1 --port 8001
```

ЮКассе нужен доступный HTTPS адрес `/webhooks/yookassa`: для локального Mac
использовать HTTPS туннель до порта 8001. Для браузерного `/pay` также задать
`BILLING_PUBLIC_URL=https://YOUR_TUNNEL_HOST/pay`. Нативная оплата SDK не требует
страницы `/pay`. Первую оплату можно проверить без webhook: приложение и worker
запрашивают канонический статус известного платежа через API провайдера. Для
полной проверки уведомлений и возвратов нужен доступный callback.

iOS запускается схемой `Doglyad-Debug-Local`; подготовка адреса Mac выполняется
существующей командой `make init-ios-local`. Ветка ЮКассы выбирается по App Store
Storefront `RUS`. Язык, IP и местоположение устройства его не заменяют; неизвестный
storefront оставляет StoreKit. В модульных тестах storefront подставляется явно.

Для отдельной локальной БД использовать отдельный симулятор: текущая запись
Keychain общая для схем с одним bundle ID. Смена `BASE_URL` не создает владельца
в другой БД и не переносит туда подписку; сохраненный секрет другого окружения
будет отклонен сервером.

## Что проверять

- Покупка: SDK → одноразовый токен → backend → подтверждение SDK → проверка
  провайдера → подписка и оплаченный срок в PostgreSQL.
- Отмена формы и отказ банка не открывают доступ. Повторная проверка одного
  платежа не создает вторую подписку.
- После перезапуска приложения статус восстанавливается с сервера. Для нового
  устройства внешняя подписка восстанавливается ключом восстановления.
- Отмена продления сохраняет оплаченный срок; webhook полного возврата отзывает
  доступ. Работа worker и повторные уведомления проверяются отдельно.

Встроенный `TestModeSettings` SDK имитирует ответы и не проверяет оплату через
тестовый магазин или запись подписки в БД. Он используется только в тесте открытия
и закрытия формы SDK; обычное приложение его не включает.

StoreKit Configuration в Xcode подходит для локальной проверки нативного интерфейса.
Для проверки Apple-подписки вместе с нашим backend нужен Apple Sandbox и серверные
ключи/сертификаты из [BILLING.md](BILLING.md): локальные Xcode-транзакции backend
автоматически не принимает.

3DS и возврат из банковского приложения СБП проверить на физическом iPhone.
Для банков с сертификатами Минцифры требуется настройка доверия по инструкции
[SDK ЮКассы](https://git.yoomoney.ru/projects/SDK/repos/yookassa-payments-swift/browse/README.md).
Сейчас системный ATS не ослаблен; эта часть совместимости еще не закрыта.

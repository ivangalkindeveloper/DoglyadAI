# План подготовки подписок к боевому запуску

Текущий этап — проверка оплаты через нативный SDK ЮКассы в тестовом магазине.
Чеки НПД и отчётность внешних покупок Apple отложены до следующего этапа.
Цель — автоматическая регистрация дохода НПД и доставка чеков покупателям.
До выполнения применимых условий запуска `IS_YOOKASSA_LIVE_ENABLED=false` сохраняется
в development и production. Наличие продового магазина само по себе не включает списания.

## Что уже оформлено

Владелец подтвердил:

- [x] Оформлена самозанятость.
- [x] Подписан договор с ЮКассой.
- [x] Созданы тестовый и продовый магазины.

Повторно оформлять эти подключения для текущих тестов не требуется. Development
использует только тестовый магазин. Настройка локального запуска — в [BILLING_LOCAL.md](BILLING_LOCAL.md).

## Решение для автоматических чеков

Проверено 1 ноября 2026 года. В открытой документации не найден подтверждённый
отдельный сервис чеков НПД для собственных продаж одного самозанятого через ЮКассу.
Наличие API для выплат чужим исполнителям не подтверждает поддержку этой задачи.

Рекомендация — сначала согласовать подключение **Robokassa + Робочеки СМЗ**.
Robokassa заявляет автоматическую регистрацию и доставку чеков по своим платежам
без отдельной платы за сервис чеков. Автосписания требуют предварительного согласования.
Это предложение заменить эквайринг для реального запуска; текущий код пока использует
ЮКассу. Совместимость Робочеков СМЗ с внешними платежами ЮКассы не подтверждена.
[Робочеки СМЗ](https://robokassa.com/online-check/robocheck-smz/),
[автосписания](https://docs.robokassa.ru/ru/recurring-payments)

У ФНС есть два списка: [банки](https://npd.nalog.ru/credit-orgs/) и
[электронные площадки](https://npd.nalog.ru/aggregators/). Среди площадок —
Prodamus, Самозанятые.РФ, Ckassa, Qugo и Консоль.Про. Само включение в список
не подтверждает наличие подходящего API. Юридическое лицо, через которое
Robokassa регистрирует доход НПД, нужно уточнить при подключении.

Prodamus — запасной кандидат из реестра ФНС: заявляет автоматические чеки и
подписки. На его странице для самозанятых полный функционал с рекуррентами стоит
10 000 ₽ за подключение. Однако в последнем найденном сообщении официального
канала отправка чеков в «Мой налог» ещё восстанавливалась. До подтверждения её
работы этот вариант не готов к запуску.
[Условия](https://prodamus.ru/priem-platezhej-dlya-samozanyatyh),
[сообщение о восстановлении](https://t.me/prodamus_ru/2086)

## Что потребуется от владельца перед боевым запуском

1. Отправить запрос в Robokassa: `support@robokassa.ru`. Текст приведён ниже.
   Получить подтверждение автосписаний для своего статуса и продукта, способа
   регистрации чеков НПД, возвратов и полной стоимости. До ответа не оплачивать
   подключение и не начинать замену провайдера.
2. После подтверждения зарегистрировать магазин и подписать договор. Указать свои
   реквизиты для выплат. Подключить выдачу чеков по инструкции сервиса и подтвердить
   разрешение в «Мой налог». Получить тестовые и боевые параметры интеграции;
   секреты хранить в соответствующих env-файлах, не в чате и не в Git.
3. Подключить автоплатёж налога: «Мой налог» → «Прочее» → «Платежи».
   [Инструкция ФНС](https://www.nalog.gov.ru/rn49/news/activities_fts/16639667/).
   Проверять поступление чеков и ежемесячное начисление. Налог рассчитывает ФНС:
   базово 4% с продаж физлицам и 6% организациям/ИП,
   с полной суммы продажи до комиссии. Начальный вычет уменьшает налог автоматически.
   Срок уплаты — до 28-го следующего месяца с учётом переноса выходных и первого
   налогового периода. Общий лимит дохода НПД — 2,4 млн ₽ за календарный год.
   [ФНС](https://npd.nalog.ru/faq/)
4. Для выпуска iOS оформить подходящий Apple Developer аккаунт с достоверными данными,
   договоры и разрешение Apple на выбранный сценарий внешней оплаты. Отдельно подтвердить,
   допускает ли он встроенный SDK. Условия внешней ссылки не подтверждают допуск
   нативной платёжной формы. [StoreKit External Purchase](https://developer.apple.com/documentation/storekit/external-purchase)
5. Подтвердить данные продавца, контакты поддержки и условия автопродления, отмены
   и возврата для обновления оферты и политики конфиденциальности.

Текст запроса в Robokassa:

> Я самозанятый без ИП. Продаю доступ по подписке к собственному приложению Doglyad AI,
> которое помогает специалистам анализировать УЗИ и составлять протоколы. Оплату
> принимаю от физических лиц. Нужны подключение из мобильного приложения, API,
> автосписания за неделю, месяц, 6 месяцев и год, автоматические чеки НПД на первую
> оплату и каждое продление, полные и частичные возвраты. Подтвердите доступность
> этой схемы для моего статуса и продукта. Какое юридическое лицо регистрирует доход
> в ФНС и какое разрешение нужно дать в «Мой налог»? Как получить статус и ссылку
> чека через API? Автоматически ли корректируется доход при возвратах? Пришлите
> документацию, порядок подключения и полный тариф, включая НДС и дополнительные услуги.

Если сохранение ЮКассы обязательно, замена не выполняется. Для этого варианта
сначала нужен подтверждённый поставщик отдельного API чеков НПД по внешним продажам.
Сейчас такой поставщик не выбран. Тесты SDK ЮКассы можно продолжать.

ЮКасса прекратила поддержку своего сервиса чеков для самозанятых 29 декабря 2025 года.
Договор эквайринга не заменяет выбранный процесс выдачи чеков НПД.
[Изменения API ЮКассы](https://yookassa.ru/developers/using-api/changelog)

## Что доделать для чеков

- [ ] После выбора провайдера реализовать его адаптер и получение подтверждённого
  чека. Если провайдер сам регистрирует доход и доставляет чек, не дублировать эти
  действия отдельным сервисом. При замене ЮКассы доработать оплату, автопродления,
  уведомления и возвраты; серверный учёт подписок сохранить. Подключение выполняется один раз;
  подтверждение каждой продажи владельцем не требуется.
- [ ] Проверить экономику тарифов с фактической комиссией выбранного провайдера,
  НДС на его услуги и налогом НПД. Обновить калькулятор при изменении условий.
- [ ] Добавить контакт для доставки чека. Вход в приложение и отдельный веб-кабинет
  для этого не нужны. Обновить правила обработки и хранения контактных данных.
- [ ] Для каждой канонически подтверждённой оплаты и автопродления контролировать
  регистрацию чека. Если выдаёт отдельный партнёр, создавать задачу выдачи.
  Повторное уведомление не должно создавать второй чек.
- [ ] Хранить связь чека с платежом, сумму, номер, ссылку, дату, статус и ошибки обработки.
  Сейчас существует только `BillingPaymentDB.is_receipt_pending`; обработчика выдачи нет.
- [ ] Добавить повторные попытки и уведомление разработчику о зависших задачах.
  При неопределённом результате сначала сверять состояние операции у партнёра.
- [ ] Обработать полные и частичные возвраты и корректировки по правилам выбранного
  процесса НПД. Изменять статус чека только после подтверждённого результата.
- [ ] Проверить оплату, продление, повтор webhook, сбой сервиса чеков и возврат.
  Ошибка выдачи чека не должна приводить к повторному списанию денег.

```text
Рекомендуемый вариант после подтверждения подключения:
Приложение -> backend создаёт заказ -> оплата через Robokassa
Успешная оплата:
  +-> backend проверяет платёж и обновляет подписку в PostgreSQL
  +-> Робочеки СМЗ регистрируют доход и доставляют чек покупателю
Backend отдельно сверяет и сохраняет результат выдачи чека.

Вариант с сохранением ЮКассы, если найдётся совместимый партнёр:
ЮКасса подтверждает оплату -> backend сохраняет платёж и задачу
  -> партнёр регистрирует доход -> чек покупателю и результат в БД
```

Та же обработка применяется к каждому успешному автопродлению. При отменённом
или неуспешном платеже доход не регистрируется. Возврат запускает корректировку
ранее зарегистрированного дохода. Операции тестового магазина не передаются в
боевой «Мой налог».

## Что доделать для внешних покупок Apple

Этот раздел относится к внешней оплате в iOS по применимому допуску Apple.
Обычные покупки StoreKit 2 и Android в RuStore не отправляются в этот контур.

- [ ] После получения допуска выбрать соответствующий StoreKit External Purchase API.
  Если разрешена только внешняя ссылка, согласовать переход на разрешённый сценарий
  перед выпуском. Для текущих локальных тестов оставить нативный SDK ЮКассы.
- [ ] Получать токен внешней покупки в iOS и передавать его на backend. В текущем
  нативном потоке токена нет; браузерный `PaymentGateway` только сохраняет переданный
  токен в `BillingCheckoutDB.apple_token`.
- [ ] Хранить токены и связь с платежами и продлениями. Токен Apple служит для
  отчётности и не заменяет проверку платежа или bearer-секрет владельца.
- [ ] Добавить адаптер External Purchase Server API с ключами App Store Connect
  и подписанием JWT. Отправлять покупки, продления, возвраты, исправления и токены
  без завершённой покупки по требованиям выданного допуска.
- [ ] Добавить очередь отчётов, устойчивые идентификаторы запросов, статусы приёма,
  повторные отправки и контроль ошибок. Сейчас отправки отчётов в проекте нет.
- [ ] Обработать проверенные уведомления `EXTERNAL_PURCHASE_TOKEN`, включая неизвестные
  и неотчитанные токены. Проверить отчёты и повторные отправки в Apple Sandbox.

Точный состав отчётов и сроки определяются применимой программой Apple.
[External Purchase Server API](https://developer.apple.com/documentation/externalpurchaseserverapi)

## Когда включать реальные платежи

- [ ] Работает выбранный процесс выдачи и доставки чеков НПД.
- [ ] Для выпуска iOS подтверждён допустимый платёжный сценарий и работает требуемая
  отчётность Apple. Для отдельного выпуска Android применимость этого условия
  рассматривается отдельно; текущая общая блокировка платежей пока сохраняется.
- [ ] Обновлены оферта, политика конфиденциальности и раскрытие условий автопродления.
- [ ] Проверены webhook, продления, возвраты, повторная обработка, мониторинг
  и восстановление PostgreSQL из резервной копии.
- [ ] После проверки готовности разрешить реальные платежи только в production.
  Для существующей интеграции ЮКассы это `IS_YOOKASSA_LIVE_ENABLED`.
  При замене провайдера обновить механизм блокировки реальных платежей.

Детали существующей реализации и остальные условия запуска — в [BILLING.md](BILLING.md).

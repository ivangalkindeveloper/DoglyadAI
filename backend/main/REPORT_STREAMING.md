# Потоковая генерация протокола

Приложение сохраняет исследование до сетевого запроса. Поэтому запись сразу
доступна в истории. `ReportGenerationController` получает поток независимо от
экрана ReportReceived. Закрытие экрана не отменяет задачу.

## Контракт

Все маршруты ниже находятся под `/v1/ultrasound`. Они требуют App Check и
`Authorization: Bearer …` владельца подписки. UUID задачи не даёт доступа.

| Запрос | Результат |
|---|---|
| `POST /report_generations` | `202`, идентификатор и снимок задачи |
| `GET /report_generations/{generation_id}` | Текущее состояние или готовый результат |
| `GET /report_generations/{generation_id}/events` | HTTP SSE (`text/event-stream`) |
| `POST /report_generations/{generation_id}/cancel` | Отмена задачи |

Тело старта: `requestId` (UUID попытки), `examination` (прежний
`USExaminationRequest`), необязательный `replacesGenerationId`.
Повтор тела с тем же `requestId` возвращает ту же задачу. Изменённое тело
с тем же идентификатором вызывает `409`. Токен и язык не меняют принятую задачу.

Ответ содержит `generationId`, `modelId`, `status`, `sequence`, `expiresAt`,
`partialReport`, `report`, `errorCode`. Серверные состояния: `queued`,
`generating`, `completed`, `failed`, `cancelled`.

SSE-события `reportDelta`, `completed`, `failed` содержат **полный текущий снимок**,
а не текст для добавления. Клиент заменяет текст и отбрасывает старые `sequence`.
После переподключения сервер сразу возвращает последний снимок. Журнал токенов
и `Last-Event-ID` для восстановления не нужны. `heartbeat` приходит каждые 10 секунд.

Worker передаёт запрос в `inference /v1/generation/stream`. Inference использует
vLLM `stream=true`. После закрытия корневого JSON-объекта inference проверяет
JSON Schema, закрывает HTTP-поток к vLLM и освобождает слот модели. Последний
фрагмент и событие `completed` отправляются после этой проверки. Ожидать
дальнейшие пробелы, `finish_reason` и `[DONE]` для готового объекта не нужно.
Для обычного текста и числовых корней сохраняется проверка `finish_reason=stop`
вместе с `[DONE]`. Main показывает предварительные текстовые
поля, затем проверяет полный JSON прежним валидатором протокола. Только после
этой проверки задача получает `completed` и расходует зарезервированный лимит.
Остальные конечные состояния освобождают резерв.

## Состояние клиента

- Исследование и исходные данные сохраняются перед стартом сети.
- Частичный текст и состояние попытки сохраняются автоматически. Фотографии
  не перезаписываются при каждом фрагменте.
- После 30 секунд без сетевых данных клиент переподключается. Он также проверяет
  снимок задачи. Серия неудачных попыток даёт локальный статус `interrupted`.
- «Повторить» сначала проверяет прежнюю задачу. Готовый результат восстанавливается;
  действующая задача продолжает приём. Для завершившейся ошибкой или истёкшей задачи
  создаётся новая попытка внутри того же исследования.
- Повтор из ReportDetail использует выбранные на этом экране модель и шаблон.
  Он сохраняет прежний ответ и открывает ReportReceived без кнопки «К протоколу».
- Незавершённые ответы отмечены карточкой ошибки в деталях. В истории сообщения
  об ошибке генерации не отображаются. Копирование и отправка
  доступны только для полного ответа. Незавершённые предыдущие ответы не экспортируются.
- Во время генерации текст в ReportReceived и карточке ответа в ReportDetail
  использует `dShimmer()`. После завершения или ошибки эффект отключается.
- До первого непустого фрагмента ReportReceived показывает строки с шиммером.
  При поступлении текста строки заменяются протоколом. При ошибке до первого
  фрагмента строки скрываются, а экран показывает карточку ошибки и повтор.
- Сервер отклоняет три точные копии предложения длиной от 64 символов внутри
  одного раздела, в том числе с другими предложениями между ними. Проверка
  трёх последовательных повторов блока от 80 символов также сохраняется.
  Проверки работают на частичных и готовых ответах. Новая проверка предложений
  не учитывает короткие одинаковые находки, незавершённые предложения и повторы
  между разделами. Она останавливает ошибочный ответ, но не проверяет клиническую
  обоснованность текста и может отклонить намеренные длинные повторы в одном разделе.
- Для `descriptionRemarks` инструкция требует кратко назвать противоречие или
  неоднозначность исходного описания. Для согласованного описания допустим `null`.
  Ограничений `maxLength` у текстовых разделов ответа нет: декодер может закрыть
  строку посреди фразы при достижении такого предела. Готовые замечания длиннее
  512 символов сохраняются целиком. Общий бюджет `maxTokens`, ограничение размера
  ответа, таймаут и проверка повторов сохраняются. Валидный JSON сам по себе
  не подтверждает полноту или достоверность медицинского текста.
- Ошибка локальной записи не запускает модель снова. Приложение сохраняет результат
  в памяти, записывает тип ошибки в журнал и повторяет запись автоматически.
  Сбой записи не меняет статус генерации и не хранится в `USReportGeneration`.

При сворачивании клиент приостанавливает чтение SSE без ошибки. Сервер продолжает
генерацию. При возврате в тот же процесс клиент запрашивает текущий снимок и снова
подключается к потоку, если задача ещё выполняется. Переход через `inactive`
(например, системное окно) не приостанавливает чтение.

После завершения процесса при новом запуске приложение меняет локальные
`generating` на `interrupted`. Оно сохраняет частичный текст и не запрашивает
результат с сервера автоматически. iOS не гарантирует callback при закрытии,
поэтому статус обновляется в отдельном шаге инициализации до открытия экранов.
Это также относится к завершению процесса самой iOS в фоне. Состояние сервера
при этом может уже быть `completed`: клиентский статус описывает сохранённый ответ.

Метаданные попытки находятся в `USReportGeneration` в домене и `USReportGenerationDB`
в SwiftData. Модель ответа содержит одно поле `generation`.
Версий схем и специального плана миграции нет: совместимость прежней тестовой БД
в рамках этой дорелизной фичи не поддерживается.

## Хранение и запуск

Нужны PostgreSQL из существующей инфраструктуры main и отдельный процесс:

```bash
alembic upgrade head
python -m app.report_worker
```

Исходная схема `0001_initial` включает таблицу задач `report_generations`.
Отдельной миграции этой дорелизной фичи нет. Исходный запрос, токен App Check и снимки шифруются Fernet перед записью.
При завершении задачи worker удаляет зашифрованный исходный запрос с токеном.
Задача и её снимки доступны 12 часов с момента создания. Worker удаляет просроченные записи; API уже не выдаёт их.
При остановленном worker физическая очистка возобновится после его запуска.
Резерв и состояние задачи завершаются в одной транзакции.

Main API и worker должны получать одинаковые `BILLING_DATABASE_URL` и
`REPORT_GENERATION_ENCRYPTION_KEY`. Создайте ключ один раз в защищённом окружении:

```bash
python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'
```

Для production задайте `REPORT_GENERATION_ENCRYPTION_KEY` в
`backend/main/secrets/.env.production`. При развёртывании этот файл передаётся
на main VM. Compose загружает его и в API, и в worker. Создайте отдельный ключ
для каждого окружения один раз, а не при каждом запуске. Не коммитьте его.
Не меняйте ключ при обычном обновлении: сохранённые задачи используют прежний ключ.
Без ключа новые маршруты возвращают `503`; worker не запускается.
Файлы секретов не изменены этой реализацией.

Compose main содержит `report_worker`. Billing overlay задаёт ему зависимость от
миграции. API и worker используют один образ. Обновление и откат через центральный
скрипт охватывают оба процесса, если worker уже добавлен в Compose машины.
Первое развёртывание требует установки нового Compose, ключа и миграции.
Сначала обновите inference, затем main с worker, затем клиент iOS.
Прокси должен пропускать SSE без буферизации; ответ содержит `X-Accel-Buffering: no`.

Обычные профили VS Code `Backend: Local Mock` и `Backend: Local Inference`,
включая варианты Cold, запускают `app.local_main`. Launcher запускает API и worker
в одном процессе с отдельными задачами и соединениями. Остановка профиля завершает
оба компонента. Prelaunch по-прежнему готовит локальный PostgreSQL и миграции.

Если ключ не задан окружением, launcher один раз создаёт
`~/.local/share/doglyad/report-generation.key` с правами `0600`. API и worker
получают одинаковый ключ. Не удаляйте файл, пока нужны сохранённые локальные задачи.
Launcher разрешён только для development с PostgreSQL на loopback-адресе.
Он не изменяет файлы `secrets` и не отключает App Check.
Прежний прямой запуск uvicorn без ключа оставляет маршруты задач недоступными (`503`).
Mock использует тот же жизненный цикл задачи, но возвращает готовую фикстуру одним фрагментом.

Параметры очереди, хранения и heartbeat находятся в `server.json.report_generation`
для обоих окружений. Сохраняются таймауты main 130 секунд и inference 120 секунд.
Настройки DGX 4/4/4 и квантование не меняются.

Для протоколов main задаёт `server.json.report_generation.repetition_penalty=1.05`.
Транспорт передаёт его как `repetitionPenalty`, а inference — как
`repetition_penalty` в vLLM. Обычная генерация и стриминг используют один путь
подготовки запроса. Разбор диктовки не задаёт этот параметр и сохраняет настройки
движка. Параметр снижает склонность к повторам, но не гарантирует правильность
медицинского содержания. Проверки измерений и результата остаются обязательными.

Для применения требуется обновлённый inference и перезапуск main API и worker.
В локальном профиле VS Code оба компонента main перезапускаются вместе.
Перезапуск vLLM и загрузка весов для этого изменения не требуются.

## Проверки реализации

- Main: Ruff, mypy, 562 теста; 5 тестов пропущены по условиям окружения.
- После объединения схемы: 14 тестов локального запуска, задач и исходной схемы;
  1 PostgreSQL-тест пропущен в этом прогоне. Подготовка реального локального PostgreSQL прошла.
- Inference: Ruff, mypy, 62 теста.
- PostgreSQL 17: отдельно прошли 7 тестов задач, включая конкурентную идемпотентность и отмену.
- iOS: 18 тестов потока, истории, состояния экранов и сохранения на отдельном симуляторе iPhone 17.
  Проверены обрыв соединения, сворачивание, быстрый возврат и локальный статус после нового запуска.
- Сборки Development и Production прошли. Форматирование прошло для обоих backend и iOS.
- Обновление и откат worker: 13 тестов скрипта развёртывания.
- Архитектура изменённых файлов: проверка прошла. Общая проверка репозитория
  по-прежнему сообщает о существующих фрагментах View в неизменённых UI-компонентах.

Живой прогон через DGX потребует развёртывания новых backend, миграции и настройки ключа.

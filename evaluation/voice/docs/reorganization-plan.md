# Организация проекта оценки речи

Статус: схема согласована пользователем и выполнена. Проверки зафиксированы
в [reorganization-checks.json](reorganization-checks.json).
Точная карта каждого файла — [reorganization-map.json](reorganization-map.json).

## Структура

```text
evaluation/voice/
  README.md                 # начало работы и актуальные команды
  pyproject.toml
  __init__.py
  common.py                 # существующие общие константы и функции
  doctor/                   # «Медицинские тесткейсы»: интерфейс и инструкция
    index.html
    prepare_medical_review.py
    README.md
  datasets/                 # генераторы, описание и проверка тесткейсов
    fixtures/               # исходные наборы и медицинские эталоны
  audio/                    # озвучивание, подготовка WAV, шумовые варианты
    swift/                  # AudioASR, AudioSynth, AudioSynthAlt, LexiconReplay
  runners/                  # запуск iPhone/Mac/GPU, импорт и воспроизведение
  scoring/                  # метрики, нормализация, оценка полей, пересчёт
  analysis/                 # диагностика ошибок, сравнения, сборка отчётов
  docs/                     # текущий протокол, устройство проекта
    reports/                # существующие отчёты об экспериментах
  results/                  # зафиксированные результаты и контрольные суммы
  tests/                    # тесты инструментов оценки и интерфейса
```

В корне сейчас 132 файла, включая 99 Python-модулей. План охватывает переносы
из корня, fixtures и вспомогательных Swift-каталогов; tests уже расположен
отдельно. Сгенерированные пакеты врача, WAV, модели и промежуточные результаты
остаются в `build/voice-eval/`.

## Ответственности и зависимости

- `doctor/index.html` показывает тесткейсы и сохраняет ответы врача;
  `prepare_medical_review` собирает пакет из корпуса. Голд автоматически
  не подтверждается и ответы моделей врачу не раскрываются.
- `datasets` владеет содержанием и контрактом тесткейсов;
  `clinical_corpus` и `validate_gold` проверяют разметку и происхождение.
- `audio` подготавливает звуковые входы, пользуясь описаниями тесткейсов.
- `runners` запускает существующие адаптеры инструментов на данных корпуса
  и сохраняет наблюдаемые ответы, настройки и ошибки.
- `scoring` вычисляет существующие метрики по данным корпуса и ответам;
  `analysis` использует эти оценки для сравнений и диагностики.

Сохраняются существующие функции и адаптеры. Основной приём — группировка
модулей по ответственности; отдельные сервисы, сервер, фреймворк интерфейса
и новые иерархии классов для перемещения файлов не требуются. У старых
модулей с несколькими обязанностями код пока остаётся вместе: разделение
алгоритмов не входит в эту миграцию.

## Объём миграции

1. Переместить файлы по карте и добавить `__init__.py` в Python-пакеты.
2. Обновить импорты, пути к fixtures и Swift, CLI-команды, Makefile и
   текущую документацию. Обновить сбор списков исходников и их хешей.
3. Сохранить содержимое fixtures и исторических `results` без изменения
   медицинских эталонов, схем результатов и старых контрольных сумм.
   Записанные старые пути в архивных результатах остаются свидетельством
   исходного запуска. Их чтение при необходимости разрешается явно
   в инструментах оценки; архивы не переписываются.
4. Обновить страницы врача в прежних каталогах `build/voice-eval`, сохранив
   их наборы тесткейсов и ключи состояния. Новый исходный вход —
   `doctor/index.html`; совместимые Python-модули на старых местах не оставлять.
5. Запустить тесты оценки и UI, Ruff, проверку импортов/CLI и ссылок;
   сравнить контрольные суммы fixtures и архивных результатов до/после.
   Проверить на тестовой матрице, что перенос не меняет численные оценки.

## Состояние ответов врача

Название страницы — «Медицинские тесткейсы». Для существующего статического
пакета кнопки «Сохранить всё» и «Сохранить тесткейс» сохраняют черновик ответов
в этом браузере. При следующем открытии того же набора он восстанавливается
автоматически. Ключ содержит идентификатор исходного корпуса и состав набора;
ответы разных наборов не смешиваются. Ошибка сохранения видна врачу и не
выдаётся за успех. Скачивание и импорт файла остаются способом переноса
между браузерами/компьютерами и резервного сохранения.

При открытии HTML через `file:` поведение browser storage зависит от браузера;
это оговорено в [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage).
Если хранилище недоступно, страница предлагает скачать копию и сохраняет
несохранённые ответы в открытой форме. Это локальный инструмент; он не
синхронизирует ответы с сервером или другими компьютерами.

Создание новых аудиотесткейсов — отдельный согласованный пользовательский
сценарий. Текущий перенос файлов сам по себе не создаёт диктофон или импорт
новых медицинских эталонов.

# Последовательная генерация и сравнение движков

Дата: 2026-11-03. Статус: испытания завершены, рабочие сервисы восстановлены.

**Лимит 1 не устраняет зацикливание. SGLang также воспроизводит сбой и не даёт
ускорения в проверенной конфигурации. Рабочий режим сохранён: vLLM, 4/4/4.**

## Задача

Проверить, исчезает ли зацикливание MedGemma 4B при одном разрешённом запросе.
Затем сравнить vLLM и SGLang на тех же весах, запросах и JSON Schema.
Отдельно измерить скорость генерации при одном и четырёх клиентах.

## Условия

- DGX Spark, GB10, исходная `google/medgemma-4b-it`, BF16.
- Ревизия весов: `290cda5eeccbee130f987c4ad74a59ae6f196408`.
- Квантование весов и KV cache не применяется.
- Каждый движок допускает 1 или 4 активных запроса. В основной серии качества
  клиент отправляет запросы последовательно. Дополнительная серия проверяет
  четыре одновременных запроса при лимите движка 4.
- Две остальные MedGemma остаются в памяти. Их счётчики запросов проверяются
  до и после серии. Они не должны выполнять генерацию во время теста.
- Временный движок работает в контейнере с `--network none`. Запросы идут через
  loopback внутри контейнера. Порты наружу не публикуются.
- Рабочий контейнер 4B временно останавливается. Контроллер восстанавливает его
  в `finally`, проверяет прежние ID, образ и команду. Время запуска остальных
  трёх сервисов должно остаться прежним.

Все входы синтетические. Приложение и его историю тесты не используют.
Набор проверяет воспроизводимость сбоя, а не клиническую пригодность модели.

## Набор проверки корректности

Основная серия содержит прежние 13 запросов: исторический проблемный промпт,
обычный протокол, противоречивые данные и разбор диктовки. Это четыре типа входа,
а не 13 независимых исследований. Для трёх типов протокола используются greedy
и температура 0.3 с seed 0, 42 и 123. Штраф повторения равен 1.0.

Два дополнительных greedy-запроса проверяют штраф 1.05. Они не заменяют проверку
всего приложения с его настройками. Три проверки изображений используют PNG
сплошного красного и синего цвета: одно, два и шесть изображений. Проверяется
число и порядок цветов в структурированном ответе. Это проверка мультимодального
пути, а не медицинской интерпретации изображений.

Предел полного ответа — 2048 токенов, для проверки цветов — 128. JSON Schema
и запрет свободных пробелов сохраняются. Незакрытый JSON, повторение текста,
отказ валидатора main и неверное распознавание цвета учитываются отдельно.

При лимите движка 4 дополнительно запускаются четыре полных greedy-запроса
одновременно: по одному на каждый тип входа. Это отдельная проверка поведения
при реальном перекрытии генераций. Она не входит в 13 последовательных запросов.

Сравниваются сырые ответы движка. Защитная остановка повторов в inference/main
не применяется к этим тестовым запросам. Полученные тексты затем проверяет
нынешний валидатор main. Хеши его исходников сохранены.

## Метод измерения скорости

Для скорости используется обычный протокол с greedy и пределом **256 токенов**.
Обрезка здесь намеренная: эти ответы не учитываются как полные протоколы.
Так разная длина ответа или цикл не увеличивает объём одного измерения.

Перед измерением выполняется прогрев. Для каждой параллельности запускается
ещё одна немеряемая серия. Затем следуют три измеряемые серии: по одному
запросу либо по четыре запроса, отправленных одновременно через барьер.
Загрузка и распаковка образа завершаются до начала измерений.

- TTFT — время до первого непустого фрагмента SSE.
  Это может быть открывающая скобка JSON, а не первое медицинское слово.
- Время ответа — до завершения потока SSE.
- Скорость одного запроса: `(completion_tokens - 1) / (время ответа - TTFT)`.
  Это оценка скорости декодирования по потоку, а не профиль GPU-ядер.
- Общая скорость серии: сумма выходных токенов / время всей серии.
- Для отдельных запросов приводится медиана. Размер выборки мал: три серии.
- Кеш общего начала запросов прогрет. Main backend, App Check и сеть телефона
  в измерение не входят.
- Порядок запуска сборок не рандомизирован. Температура GPU не контролировалась
  во всех замерах. Небольшую разницу скорости нельзя считать устойчивым выигрышем.

## Сборки

| Движок | Версии |
|---|---|
| vLLM | 0.28.0; PyTorch 2.13.0+cu130; Transformers 5.15.1; XGrammar 0.2.3 |
| SGLang | 0.5.23; PyTorch 2.14.1+cu130; Transformers 5.19.0; XGrammar 0.2.7 |

Сравниваются готовые сборки. Разницу результатов нельзя приписать только одному
компоненту. Входные token IDs сохраняются для проверки шаблона диалога.
Одинаковый seed не гарантирует одинаковую случайную выборку между движками.

SGLang зафиксирован по ARM64 digest
`sha256:7f132b890eb6d55f6a8ded87f85e359434878d0fb7f6758582cf759ffb35b5d8`.
Сборка соответствует commit `297e54fd105e974cdf401e5b4d20253a22c16f90`.
Команды каждого запуска и исходные параметры находятся в `engine-comparison/`.

Для SGLang выбран Triton attention: реализация Gemma 3 использует его для
двунаправленного внимания к изображениям. Chunked prefill отключён.
В журнале vLLM также выбран `TRITON_ATTN` для основной модели; для визуального
энкодера — `FLASH_ATTN`. Название backend не означает одинаковые GPU-ядра.
Флаг `--enable-multimodal` включён явно. В SGLang 0.5.23 для Gemma 3 этот режим
по умолчанию отключён. Первый пробный запуск остановлен при обнаружении этого
сообщения, до измерений. Его журнал сохранён отдельно.
Второй пробный запуск выявил несовместимый диагностический параметр тестового
клиента: SGLang запрещает `return_prompt_token_ids` и `return_token_ids` вместе
со streaming. Клиент переключён на `return_input_ids_in_sglext` и
`return_output_ids_in_sglext`. Ответ `400` исключён из сравнения движков.
Следующая проверка выявила двойной BOS в мультимодальном пути SGLang:
`[2, 2, 105, ...]` вместо эталонного `[2, 105, ...]`. В историческом запросе
SGLang передал 1545 входных токенов, vLLM — 1544. Единственное отличие — лишний
токен 2 в начале. Эта серия также остановлена и исключена из основного сравнения.

В SGLang передан отдельный Jinja-шаблон: копия штатного шаблона без начального
`{{ bos_token }}`. Включённый мультимодальный путь SGLang повторно токенизирует
текстовый запрос без изображений с `add_special_tokens=True`. Эта ветка в
`base_processor.py` обходит проверку двойного BOS из `process_mm_data`.
Веса и файлы токенизатора
не изменены. Тестовый клиент требует совпадения входных token IDs с vLLM уже
на коротком прогреве и затем на каждом текстовом запросе. Несовпадение прерывает
серию. Штатный и адаптированный шаблоны сохранены рядом с результатами.

KV pool ограничен 16384 токенами. У vLLM сохранён рабочий бюджет KV cache 4 GiB.
Это разные способы выделения памяти; проверяемые запросы должны помещаться
без вытеснения активных последовательностей.

Лимит SGLang 16384 — общий размер KV pool. Он не обеспечивает четыре контекста
по 16384 токена одновременно. Эта конфигурация предназначена для сравнения
коротких запросов из набора; её нельзя переносить в рабочий сервис без отдельной
проверки ёмкости. В этой сборке SGLang для мультимодальной Gemma 3 также отключает
оптимизацию гибридного SWA-кеша. CUDA Graphs включены у обоих движков.

## Результаты

### Один разрешённый запрос

При последовательной отправке все **18 ответов vLLM совпали** между
`max-num-seqs=1` и `max-num-seqs=4`: входные token IDs, выходные token IDs и текст.
В обеих сериях цикл воспроизведён в 4 из 13 контрольных запросов.
У первого greedy-ответа одна фраза повторилась 50 раз.
Таким образом, одновременные запросы не являются необходимым условием сбоя,
а уменьшение лимита движка до 1 не изменило ответы этой серии.

### Полные ответы при последовательной отправке

| Движок | Лимит активных запросов | Цикл до 2048 токенов | JSON Schema | Валидатор main |
|---|---:|---:|---:|---:|
| vLLM | 1 | 4/13 | 9/13 | 6/13 |
| vLLM | 4 | 4/13 | 9/13 | 6/13 |
| SGLang | 1 | 3/13 | 10/13 | 8/13 |
| SGLang | 4 | 3/13 | 10/13 | 7/13 |

SGLang завершил обычный greedy-протокол, который зацикливался в vLLM.
Исторический greedy-запрос зациклился в обоих движках. Входные token IDs
совпали во всех 15 текстовых проверках каждой серии SGLang.
Часть ответов SGLang с температурой 0.3 различается между лимитами 1 и 4,
хотя в запросах сохранены seed. Одна серия на конфигурацию не позволяет
отделить влияние лимита от непобитовой воспроизводимости вычислений.

Закрытый JSON не всегда пригоден для main. Например, SGLang с лимитом 1
вернул исторический ответ с `descriptionRemarks` длиной 5456 символов.
Текущий main его отверг. Другие ответы дошли до границы 512 символов:
схема может принудительно закрыть строку, но не доказывает завершённость мысли.

Все три проверки порядка цветов прошли в четырёх конфигурациях.
В двух дополнительных greedy-запросах со штрафом 1.05 оба движка завершили JSON.
У vLLM валидатор main принял 1 из 2 ответов, у SGLang — 2 из 2, при обоих лимитах.
Двух запросов недостаточно, чтобы считать штраф 1.05 надёжным исправлением.
Это также не полная проверка рабочего режима с температурой 0.3.

### Четыре полных запроса одновременно

| Движок, лимит 4 | Цикл до лимита | JSON Schema | Валидатор main |
|---|---:|---:|---:|
| vLLM | 2/4 | 2/4 | 1/4 |
| SGLang | 1/4 | 3/4 | 2/4 |

Исторический запрос зациклился в обоих движках: по 44 копии повторяющейся фразы.
В vLLM дополнительно зациклился обычный протокол. Оба движка завершили JSON
для противоречивого входа, но main отверг замечания на границе 512 символов.
Разбор диктовки прошёл валидатор источника в обоих движках.

### Скорость на одинаковых 256 выходных токенах

| Движок | Лимит движка | Одновременные клиенты | TTFT, мс | Ответ, с | На один запрос, токенов/с | Суммарно, токенов/с |
|---|---:|---:|---:|---:|---:|---:|
| vLLM | 1 | 1 | 63.9 | 10.58 | 24.2 | 24.1 |
| vLLM | 4 | 1 | 62.2 | 10.70 | 24.0 | 23.9 |
| vLLM | 4 | 4 | 106.9 | 9.01 | 28.6 | 112.4 |
| SGLang | 1 | 1 | 60.8 | 11.04 | 23.2 | 23.2 |
| SGLang | 4 | 1 | 61.4 | 11.05 | 23.2 | 23.2 |
| SGLang | 4 | 4 | 111.9 | 9.39 | 27.5 | 109.0 |

Суммарная скорость относится ко всем четырём потокам, а не к каждому из них.
Пакетная обработка повысила и общую скорость, и скорость отдельного потока
на этом коротком прогретом запросе. Такой результат не гарантирован для длинных
разных запросов или при одновременной работе трёх моделей.
В проверенных конфигурациях SGLang не дал выигрыша по скорости.

Всего в основное сравнение вошли **80 полных проверок**: 72 последовательные
и 8 параллельных. Ещё **36 запросов** использованы для измерения скорости.
Прогревы и три исключённые попытки настройки SGLang в эти числа не входят.
Все измеряемые запросы завершили SSE без транспортной ошибки.
В журналах этих серий нет сообщений об OOM или вытеснении активных запросов.

Дополнительная проверка сохранности измерений ищет исходные размеры долей,
их объёмы, общий объём и толщину перешейка в `description` завершённых JSON.
Она также отмечает числа в описании, которых не было во входе. Это буквальная
проверка; она не подтверждает правильную привязку к стороне, пересчёт единиц
или медицинский смысл. Незакрытые JSON в этот подсчёт не входят.
Во всех 45 разобранных JSON-протоколах из полных серий эта проверка не выявила
пропущенных исходных измерений или новых чисел в описании.

Для диктовки `main_valid` означает успешное выполнение валидатора источника,
который может удалить или понизить достоверность предложенных полей. Это не
означает, что сырой ответ был достоверным: оба движка придумали номер исследования
и дату рождения, которых не было в синтетической диктовке. Очищенный результат
сохранён в `validated_value`.

## Решение

- Сохранить vLLM и рабочий лимит 4/4/4. Уменьшение лимита до 1 не исправляет
  зацикливание и ограничивает общую пропускную способность.
- Не переводить рабочий сервис на SGLang по результатам этого набора.
  Валидатор принял больше ответов, но циклы остались. Выигрыша по скорости нет.
- Не переносить этот опыт на 1.5 4B и 27B как готовое исправление. Для них
  нужен самостоятельный набор, если появится подтверждённый кандидат.
- Сохранить JSON Schema и исходные BF16-веса. Эксперимент не меняет рабочие
  промпты, штраф повторения, квантование или API приложения.

Зацикливание воспроизведено при одном запросе и в двух серверных движках.
В предыдущей серии тот же исторический greedy-ответ зацикливался и в
Transformers, совпав с vLLM во всех 2048 токенах: см. [FORMATTING.md](FORMATTING.md).
Следовательно, ни параллельность, ни ошибка только в vLLM не объясняют этот сбой.
Это не доказывает, что любой движок или любой запрос MedGemma поведёт себя так же.

## Восстановление

Проверка завершена после последней серии, результат сохранён в
`engine-comparison/restoration-verified.json`:

- Все четыре исходных контейнера запущены. Их ID, образы и команды сохранены.
- Все три vLLM-контейнера имеют `healthy`, внутренний `/health` возвращает 200.
- Лимиты движков — 4/4/4. Активных и ожидающих запросов нет.
- Контейнеры 1.5 4B, 27B и inference не перезапускались. Счётчики генерации
  двух остальных моделей не менялись во время каждой измеряемой серии.
- `/v1/generation` и `/v1/generation/stream` возвращают 401 без App Check.
- Временный контейнер удалён. Образ SGLang и артефакты теста сохранены для
  воспроизведения; рабочего сервиса SGLang нет.

Проверка приложения через iPhone и публичный main backend в этот опыт не входит.

## Проверки артефактов

Ruff прошёл для тестовых скриптов. `make check-architecture` сообщил 13 нарушений
`swift.view-fragment` в существующих iOS-файлах. Эксперимент эти файлы не меняет.
Сборка и установка iOS-приложения не выполняются.
Хеши используемых валидатора, схемы, промпта и конфигурации совпали с началом
эксперимента. Проверены число ответов, завершение SSE, длина скоростных ответов
и совпадение текстовых входных token IDs. Результат — `artifact-checks.json`.

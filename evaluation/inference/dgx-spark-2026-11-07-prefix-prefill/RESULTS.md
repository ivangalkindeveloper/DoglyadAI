# Результаты проверки 7 ноября

Перенос шаблона дал небольшой выигрыш без фото. Удаление ID фото из текстовой
схемы ухудшило результаты MedGemma 4B. Сравнение prefill остановлено при запуске
бюджета 4096: 4B получила ошибку памяти CUDA. На этапе измерений промпты
приложения не менялись. После обсуждения применён только перенос шаблона
в локальном коде; см. раздел «Применение» ниже.
Исходный бюджет 2048 восстановлен на всех трёх моделях. Образы и команды
совпали с исходными, файлы развёртывания не изменены.

## Порядок текста

### Перенос шаблона перед данными пациента

При одинаковом шаблоне и отсутствии фото увеличился общий префикс:
движок повторно использует 1040 токенов вместо 800. Медиана времени до первого
непустого фрагмента SSE по трём повторам, секунды:

| Модель | Исходный порядок | Шаблон в начале | Разница |
|---|---:|---:|---:|
| MedGemma 4B | 0,116 | 0,091 | около 25 мс |
| MedGemma 1.5 4B | 0,116 | 0,089 | около 27 мс |
| MedGemma 27B | 0,601 | 0,458 | около 143 мс |

Это результат на прогретом общем префиксе, а не ускорение всего отчёта на
такой же процент. Технический ответ ограничен 16 токенами. Вход и строгая
JSON Schema сохранены. Кеш мультимодального обработчика предварительно прогрет
для обоих синтетических изображений; первые запросы используют отдельные salts.

С фотографией перенос одного шаблона не увеличил префикс: осталось 1008 токенов.
Раньше шаблона различаются ID фото в текстовой копии схемы. У 27B TTFT остался
1,186 секунды; небольшие колебания моделей 4B не дают основания обещать ускорение.

Полные ответы без фото проверены отдельно: 24 генерации, по два пациента,
два языка, три модели, исходный порядок и перенос шаблона. Все 12 русских
ответов приняты валидатором main. Все 12 английских ответов отклонены с
`reportMeasurementsMismatch`, поровну до и после перестановки. Нового отказа
из-за перестановки на этом малом наборе не выявлено. Набор не доказывает
равенство клинического качества при любом вводе.

Вывод: перенос шаблона даёт небольшой измеренный выигрыш без фото.

### Постоянная текстовая схема без конкретных ID фото

Строгая схема `response_format` во всех вариантах содержит исходный `photoId.enum`.
Только его текстовая копия в системных инструкциях становится постоянной.

С фото и шаблоном комбинация двух изменений увеличила повторно используемую
часть с 1008 до 1600 токенов. TTFT у 27B сократился с 1,186 до 0,695 секунды,
у 4B — с 0,226 до 0,162, у 1.5 4B — с 0,239 до 0,154 секунды.

Однако полные ответы не прошли проверку качества результата. В следующей
таблице — ответы, принятые JSON Schema и валидатором main; по четыре попытки
на модель и вариант:

| Модель | Исходный | Только шаблон выше | Только постоянная схема | Оба изменения |
|---|---:|---:|---:|---:|
| MedGemma 4B | 2/4 | 2/4 | 0/4 | 0/4 |
| MedGemma 1.5 4B | 0/4 | 0/4 | 0/4 | 0/4 |
| MedGemma 27B | 4/4 | 4/4 | 4/4 | 4/4 |

При изменённой схеме ответы 4B достигали лимита 2048 токенов либо main
отклонял повторные записи одного `photoId`. Число принятых ответов снизилось
с 2/4 до 0/4. У 1.5 4B такие повторы встречались
уже в исходном варианте. Здесь использовано серое геометрическое тестовое
изображение, а не УЗ-снимок; диагностическая точность изображений не оценивалась.
Оборванные ответы не засчитаны как быстро полученные готовые отчёты.

Вывод: удаление конкретных ID из текстовой схемы не рекомендуется по этому
результату. Выигрыш времени начала ответа не компенсирует ухудшение результатов
MedGemma 4B. Исправление замечаний к фото — отдельная задача, оно не смешивалось
с экспериментом производительности.

## Бюджет prefill

На текущем профиле выполнены 99 запросов с бюджетом 2048, включая три запроса
прогрева. Все три модели работали одновременно: восемь слотов на модель,
N-gram 8, BF16, контекст 16384 и исходные закреплённые образы vLLM 0.28.0.
Менялся только `--max-num-batched-tokens`; остальные аргументы сохранены.

| Нагрузка | Число запросов в волне | Время всей волны |
|---|---:|---:|
| Технический ввод около 8000 токенов, по 4 запроса на модель | 12 | 77,03 и 77,04 с |
| Тот же ввод, по 8 запросов на модель | 24 | 138,40 и 138,47 с |
| Полный отчёт RU без фото и шаблона, по 8 запросов на модель | 24 | 67,46 с |

Технический вывод фиксирован: 128 токенов. В каждой волне 8/8/8 два запроса
превысили внутренний лимит приложения 120 секунд. Прямой тест движка допускает
600 секунд, поэтому эти ответы удалось сохранить. Это не успешная проверка
таймаута приложения. Все 24 полных отчёта прошли JSON Schema и валидатор main
и завершились раньше 120 секунд. Медиана полного ответа: 22,54 с у 4B,
21,90 с у 1.5 4B и 63,14 с у 27B.

При бюджете 4096 первой запустилась 27B. Следующий движок 4B не прошёл запуск:
`torch.AcceleratorError: CUDA error: out of memory` возникла в
`torch.accelerator.get_memory_info` при инициализации устройства. В журнале
ядра есть соответствующие записи `NV_ERR_NO_MEMORY`. OOM-kill хоста не
зафиксирован. Контроллер остановил сравнение и начал возврат исходных команд.
Генераций при 4096 нет; сравнивать его скорость с 2048 по этой серии нельзя.

Такие ошибки запуска ранее отмечались на этом DGX и с другими настройками;
см. [диагностику хоста](../../../deploy/dgx-spark/README.md#перезагрузка-и-диагностика).
Эта попытка не доказывает, что причиной был именно бюджет 4096. Она также
не подтверждает работоспособность нового режима. Решение: сохранить 2048.
Историческая серия с четырьмя слотами и без N-gram также не показала выигрыша
от 4096; её результаты приведены в [README](README.md#2-бюджет-prefill).

При восстановлении похожая ошибка CUDA возникла у MedGemma 1.5 4B уже
с бюджетом 2048. `docker compose --wait` завершился раньше успешного запуска,
из-за чего контроллер не дошёл до итоговой проверки. Существующая политика
Docker автоматически перезапустила контейнер. Ожидание готовности продолжено
отдельным скриптом `finish_restoration.py`, без изменения параметров движка.
Все три модели стали healthy в 03:13:29 MSK. Это дополнительное ограничение
вывода о причине сбоя кандидата.

В журнале ядра за эксперимент сохранены 20 строк с ошибками выделения памяти
NVIDIA. Записей Xid и OOM-kill в этой выборке нет. Таким образом, запуск и
восстановление нельзя назвать прошедшими без ошибок, даже после успешного
возврата рабочих настроек.

После восстановления выполнены шесть полных контрольных генераций: по два
пациента на каждую модель. Все шесть ответов естественно завершены и приняты
JSON Schema и валидатором main. Из inference backend доступны `/health` и
нужная модель через `/v1/models` для каждого движка. Оба маршрута генерации
без App Check вернули 401. Контейнер backend не перезапускался. Между
восстановлением и итоговой проверкой новых выбранных ошибок ядра не найдено.
Полный путь из iOS с действующим App Check в этой задаче не проверялся.

## Применение

После обсуждения результатов в `PromptFactory.build_prompt` шаблон перенесён
перед данными пациента. ID фотографий сохранены в пользовательском тексте,
текстовой копии схемы и строгом `response_format`. Бюджет prefill не менялся.
Изменение внесено в локальный код, на сервер не развёрнуто.

Новый запрос побайтно совпал по пользовательскому и системному тексту
с сохранённым вариантом `template_first` во всех 96 проверках: 48 входов
для каждого из двух окружений. Строгие схемы также совпали. Набор включает
RU/EN, три модели, наличие/отсутствие фото и шаблона, двух пациентов.
Это сопоставление с уже измеренным вариантом, без новой генерации на GPU.

Main backend: 587 тестов прошли, 5 пропущены; Ruff и mypy прошли.
Общая проверка архитектуры по-прежнему выявила 13 нарушений `swift.view-fragment`
в файлах вне этой правки. Фактура: [implementation-checks.json](implementation-checks.json).
Исходные `checks.json` и `source-hashes.json` относятся к этапу измерений,
до применения перестановки.

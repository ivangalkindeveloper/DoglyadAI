# vLLM и llama.cpp: семейство MedGemma на DGX Spark

Замеры и проверка восстановления DGX завершены 5 ноября 2026 года по Москве.

## Результат

Для четырёх одновременных запросов текущий vLLM быстрее llama.cpp на всех трёх
моделях. llama.cpp даёт преимущество при одиночной генерации MedGemma 4B и
MedGemma 1.5 4B. У 27B разница одиночной скорости мала: около 1,3% по скорости
после первого текстового фрагмента и около 1% по времени всего ответа.

Данные 1.5 4B и 27B получены в этой серии. Данные 4B взяты из
[предыдущего исследования](../engine-survey/README.md): контрольного vLLM-замера
и llama.cpp с четырьмя слотами по 16384 токена. Версии движков, checkpoint,
параметры sampling и метод скоростного измерения сохранены. 4B заново не тестировалась.

## Скорость генерации

Все значения — медианы пяти измеряемых серий. Веса BF16, выход — 256 токенов.

| Модель | vLLM, один запрос, токенов/с | llama.cpp, один запрос, токенов/с | vLLM, четыре запроса, суммарно токенов/с | llama.cpp, четыре запроса, суммарно токенов/с |
|---|---:|---:|---:|---:|
| MedGemma 4B | 24.21 | 30.65 | 114.89 | 101.62 |
| MedGemma 1.5 4B | 23.73 | 29.56 | 115.03 | 100.20 |
| MedGemma 27B | 4.17 | 4.23 | 17.04 | 15.89 |

Один запрос: `(completion_tokens - 1) / (полное время - TTFT)`.
Четыре запроса: 1024 выходных токена / время всей серии. Последние два столбца
показывают суммарную скорость, а не скорость каждого клиента.

Относительно vLLM, скорость llama.cpp для одного клиента выше на 26,6% у 4B,
на 24,6% у 1.5 4B и на 1,3% у 27B. При четырёх клиентах суммарная скорость
llama.cpp ниже на 11,6%, 12,9% и 6,8% соответственно. Эти результаты относятся
к проверенным параметрам запуска; полный перебор настроек не выполнялся.

## Время ответа

Каждый ответ содержит ровно 256 токенов. В параллельном режиме указана медиана
времени отдельного ответа среди 20 запросов, а не сумма их времён.

| Модель | vLLM, один клиент, с | llama.cpp, один клиент, с | vLLM, четыре клиента, с на ответ | llama.cpp, четыре клиента, с на ответ |
|---|---:|---:|---:|---:|
| MedGemma 4B | 10.58 | 8.39 | 8.79 | 9.97 |
| MedGemma 1.5 4B | 10.81 | 8.70 | 8.81 | 10.14 |
| MedGemma 27B | 61.34 | 60.75 | 59.99 | 64.28 |

Для 27B прогретый TTFT в этом коротком запросе также меньше у vLLM:
0,26 с против 0,47 с при одном клиенте; 0,52 с против 0,97 с при четырёх.
Эти значения не описывают первый токен реального протокола через приложение.

Все полные ответы самостоятельно завершились и прошли JSON Schema. Генераций
до лимита 2048 токенов не было. Детектор одинаковых предложений длиной от

Для 1.5 4B main-валидатор выдал `reportMeasurementsMismatch`:

- vLLM: `conflict-greedy-0`;

У каждой новой модели IDs всех семи текстовых входов совпали между движками.
Сравнение изображений ограничено двумя цветными картинками; работа vision
encoder не проверялась на клинических данных.

## Воспроизводимость

Использованы vLLM 0.28.0 в прежнем образе
`sha256:89154ef00dd15368d2b293c167e5cc7dbb521fcfb2fbb77510e0d4df2b820e8f`
и прежняя сборка llama.cpp из commit
`5851a8e505f4d5fbb183f2847698eb6155d176b7`.
Исходные checkpoint, ревизии и хэши конвертированных GGUF находятся в
`provenance.json` и `gguf-artifacts.json`. Типы весов не понижались до Q4/Q8;
служебные тензоры, которым конвертер назначает F32, сохранены в F32.

CPU-конвертация обеих моделей завершилась до начала GPU-измерений. На время
каждого опыта с llama.cpp останавливался только соответствующий vLLM.
Два других движка оставались загруженными. Их счётчики до и после каждого опыта
совпали. У каждой серии vLLM счётчик завершённых запросов увеличился ровно на 40,
как предусмотрено тестом: посторонних завершённых запросов не обнаружено.

Сырые ответы и времена находятся в `*/results.jsonl`, проверки — в
`*/validation.json`. `summary.json` содержит TTFT, диапазоны времени и проверку
полноты всех пяти серий. `comparison.json` объединяет новые и предыдущие замеры.
`quality-snapshot.jsonl` — промежуточный снимок полных ответов 27B для проверки
входных IDs до окончания скоростной серии; он не добавляет запросы в статистику.

Локально из корня проекта:

```bash
.venv311/bin/python evaluation/inference/dgx-spark-2026-11-04/llama-family-comparison/analyze_survey.py
.venv311/bin/python evaluation/inference/dgx-spark-2026-11-04/llama-family-comparison/build_comparison.py
```

На DGX подготовка и последовательный запуск задаются `prepare_models.py` и
`run_sequence.py`. Они отказываются перезаписывать существующие результаты;
для нового опыта нужен отдельный каталог. Крупные GGUF сохранены только на DGX
в `/var/tmp/doglyad-llama-family-20261104`, а не в репозитории.

## Протокол

- Исходные checkpoint BF16, без квантования весов.
- Один и четыре одновременных HTTP-клиента. Прогрев и пять измеряемых серий.
- Одинаковый короткий запрос, greedy, ровно 256 выходных токенов.
- Девять полных синтетических запросов: шесть протоколов, диктовка, два цветовых изображения.
- JSON Schema, валидация main, завершение, повторы и время ответа проверяются отдельно.
- На время llama.cpp останавливается только соответствующий vLLM. Две остальные модели остаются загруженными и простаивают.
- После каждого опыта исходный контейнер восстанавливается. Проверяются ID, образ, команда, здоровье и отсутствие чужой нагрузки.

Для 27B лимит времени одного запроса увеличен до 900 секунд. Он не меняет лимит
выходных токенов: 2048 для полного ответа и 256 для скоростной серии.
Размер контекста llama.cpp — четыре слота по 16384 токена.
Все сообщения и схемы взяты из предыдущего исследования; изменены только ID модели.

## Артефакты

`provenance.json` фиксирует исходные версии и хэши. Планы `vllm-*.json` и
`llama-*.json` задают запуск. Файлы `cases-*.json` и `performance-*.json` содержат
синтетический набор. `run_trial.py` запускается на DGX. `analyze_survey.py`
запускается локально и проверяет сохранённые ответы.

## Ограничения сравнения

Проверяется каждый движок с одной активной моделью. Это не смешанная нагрузка
4/4/4. Два остальных checkpoint занимают память, но не генерируют ответы.
В параллельной серии четыре клиента отправляют одинаковый короткий запрос.
Скорость четырёх клиентов — сумма их выходных токенов за время всей серии.
Она не равна скорости каждого отдельного клиента.

TTFT измеряется до первого непустого фрагмента SSE на внутреннем loopback.
Телефон, сеть пользователя и main backend в эту задержку не входят.
Скорость одного клиента вычисляется после первого текстового фрагмента.
Пять повторов дают предварительную оценку, но не надёжные хвостовые задержки.
Порядок движков не рандомизирован.

vLLM использует рабочие лимиты KV: 4 GiB для 1.5 4B и 8 GiB для 27B.
llama.cpp получает четыре слота по 16384 токена и BF16 KV. Размер выделенной
памяти этих реализаций не выровнен. Сравниваются конкретные параметры запуска,
а не предел скорости каждого движка при всех возможных настройках.

Два теста изображений определяют цвет синтетических картинок. Они не проверяют
медицинскую точность. Прохождение JSON Schema и main-валидаторов также не является
клинической оценкой. Один seed не гарантирует одинаковый текст у разных движков.

## Состояние после теста и проверки

`restoration.json` подтверждает исходные ID контейнеров, образы, команды и
политики перезапуска. Все три vLLM имеют статус `healthy`; очереди пусты.
Рабочая схема — vLLM 4/4/4. Backend inference и vLLM 4B не перезапускались.
Модели 1.5 4B и 27B восстановлены после своих опытов с llama.cpp.

Временный GPU-контейнер удалён. Конвертация использовала контейнеры с `--rm`.
Остались четыре рабочих контейнера. Обе ручки inference без App Check вернули
HTTP 401. Код приложения, профили развёртывания и секретные конфиги эта работа
не меняла. Библиотеки на хосте не переустанавливались.

Ruff и проверка синтаксиса семи скриптов прошли. Все JSON/JSONL читаются; все
скоростные серии содержат пять полных повторов, по 256 токенов на запрос.
`make check-architecture` сообщил 13 существующих нарушений `swift.view-fragment`
в Swift-файлах вне этой работы. Полный вывод — в `architecture-check.log`.
Сборка приложения не выполнялась, поскольку изменения ограничены исследованием.

# Движки для MedGemma на DGX Spark

Исследование завершено 4 ноября 2026 года. Код приложения и рабочая конфигурация
DGX в рамках этой работы не менялись.

## Результат

Для текущей нагрузки с четырьмя одновременными запросами рекомендую сохранить
vLLM. В этом опыте он показал наибольшую суммарную скорость среди проверенных
HTTP-серверов. llama.cpp — кандидат для уменьшения времени одиночного ответа:
256 токенов за 8,39 с вместо 10,58 с у vLLM. При четырёх клиентах llama.cpp
уступает vLLM по суммарной скорости.

SGLang, TensorRT-LLM и изменённый LMDeploy не дали выигрыша в этих замерах.
LMDeploy потребовал двух изменений тестовой копии. TensorRT-LLM запустился,
но обнаруженные проблемы обработки входа и изображений мешают считать этот
профиль готовой заменой. Transformers полезен как контрольная реализация.
TensorRT Edge-LLM не имеет готового адаптера Gemma 3 в проверенной версии.

Это вывод для **MedGemma 4B BF16 и данного короткого набора**. Выбор движка для
всего семейства требует отдельной проверки 1.5 4B, 27B и смешанной нагрузки.

## Задача

Проверить llama.cpp, TensorRT-LLM, LMDeploy, Transformers/PyTorch и
TensorRT Edge-LLM. Сопоставить доступные варианты с рабочим vLLM.
SGLang включён как дополнительный контроль предыдущего сравнения.
Квантование весов не меняется. Рабочая схема остаётся vLLM 4/4/4.

## Условия опыта

- DGX Spark: ARM64, NVIDIA GB10, compute capability 12.1, драйвер 580.178.04.
- Сравнительная модель: `google/medgemma-4b-it`, ревизия
  `290cda5eeccbee130f987c4ad74a59ae6f196408`, BF16.
- Проверка поддержки семейства по документации не означает испытание всех трёх
  моделей. Численные замеры этой серии относятся к 4B.
- Два остальных движка остаются загруженными и простаивают. Перед опытом
  проверяются очереди. Их счётчики сохраняются до и после опыта.
- Новый движок работает в отдельном контейнере без опубликованных портов.
  Запросы отправляются через `docker exec` на внутренний loopback. По умолчанию
  сеть отключена. Для последних попыток TensorRT-LLM использована сеть Docker
  bridge: его MPI-процессам нужен сетевой интерфейс.
- После каждой попытки исходный контейнер 4B запускается с прежними ID, образом
  и командой. Ошибка теста также приводит к восстановлению.
- Main backend, App Check, сеть телефона и интерфейс iOS в замеры не входят.
  Защита приложения остаётся включённой.

## Набор и метрики

`cases.json` содержит девять синтетических запросов: шесть протоколов без
`contextualStrings`, разбор диктовки и два контроля изображений. Все движки
получают одинаковые сообщения и JSON Schema. Полные ответы ограничены 2048
токенами. Температура, seed и repetition penalty сохранены в запросах.
Для сравнения явно заданы `top_p=1` и отключённый `top_k`. У vLLM и
Transformers это `0`, у SGLang — `-1`. `probe_http.py` содержит этот адаптер.

Изображения — цветовые тестовые картинки. Проверка их цвета не подтверждает
качество медицинского анализа изображений.

Скорость измеряется отдельным запросом `performance.json`: ровно 256 выходных
токенов, greedy, без JSON Schema, без штрафа повторений, с подавлением раннего EOS.
Этот искусственный запрос не является медицинским протоколом. Для каждой
параллельности выполняется прогрев и пять измеряемых серий.

- TTFT HTTP — время до первого непустого текстового фрагмента SSE.
- Время ответа — время до завершения SSE.
- Скорость одного запроса: `(completion_tokens - 1) / (время ответа - TTFT)`.
- Суммарная скорость — все выходные токены серии / время серии.
- Transformers измеряет первый токен внутри `generate`, а не SSE. Его batch=4
  является статическим пакетом. Это не сервер с четырьмя независимыми клиентами.
- Приводятся медианы. Пять серий недостаточно для устойчивой оценки хвостовых
  задержек. Порядок движков не рандомизирован.

В параллельной серии четыре клиента отправляют один и тот же короткий запрос.
TTFT относится к прогретому движку и внутреннему loopback. Это не задержка
приложения и не испытание четырёх разных длинных медицинских запросов.

Время полных протоколов и скорость на фиксированном числе токенов учитываются
раздельно. Обрезанный скоростной ответ не считается успешно созданным протоколом.
Проверки JSON Schema, текущего валидатора main, повторов и изображений также
учитываются раздельно.

## Измеренная скорость MedGemma 4B BF16

| Движок / профиль | Один запрос, токенов/с | 256 токенов, с | Четыре запроса, суммарно токенов/с | 256 токенов на запрос при четырёх клиентах, с |
|---|---:|---:|---:|---:|
| vLLM 0.28.0, первый замер | 24,28 | 10,568 | 114,80 | 8,811 |
| vLLM 0.28.0, контрольный повтор | 24,21 | 10,579 | 114,89 | 8,794 |
| llama.cpp, четыре слота по 16 384 | 30,65 | 8,390 | 101,62 | 9,969 |
| SGLang 0.5.23 | 23,37 | 10,965 | 111,85 | 9,152 |
| LMDeploy 0.18.0, экспериментальное ядро | 23,86 | 10,760 | 112,05 | 9,024 |
| TensorRT-LLM 1.4.0rc2.post1, FlashInfer** | 23,60 | 10,857 | 112,24 | 8,995 |
| Transformers 5.15.1 + PyTorch 2.13, SDPA | 19,45 | 13,169 | 89,00* | 11,506* |

\* Transformers использует статический batch=4, а не четыре независимых HTTP-запроса.
Его значения не подтверждают производительность готового многопользовательского
сервера. `torch.compile` для этого профиля не включён.

\*\* У TensorRT-LLM обнаружен дополнительный BOS при обработке входа.
Сообщения одинаковые, но входные последовательности токенов не идентичны.
Это ограничение данного профиля, описанное ниже; результаты не изолируют
влияние одного только вычислительного движка.

При четырёх клиентах каждый получает 256 токенов, всего серия создаёт 1024 токена.
Например, 114,89 токена/с у vLLM — суммарная скорость четырёх ответов. Это не
скорость каждого клиента. Время в последнем столбце относится к одному ответу.
Полный медицинский протокол может иметь другую длину.

Контрольный повтор vLLM отличается от первого менее чем на 0,4% по скорости
одного запроса и менее чем на 0,1% по суммарной скорости. В этих условиях
преимущество SGLang не подтвердилось. llama.cpp даёт примерно на 27% больше
токенов/с одному клиенту, но примерно на 12% меньше суммарно четырём клиентам.

Сырые измерения, TTFT, диапазоны времени и проверки полноты пяти серий находятся
в `summary.json` и каталогах опытов. Результаты не усреднялись между движками
или разными режимами.

| Профиль | Завершились и прошли JSON Schema | Приняты main-валидаторами, текстовые случаи | Цветовые изображения |
|---|---:|---:|---:|
| vLLM, первый замер | 9/9 | 6/7 | 2/2 |
| vLLM, контрольный повтор | 9/9 | 7/7 | 2/2 |
| llama.cpp, контекст 16 384 на слот | 9/9 | 7/7 | 2/2 |
| SGLang, исправленные параметры API | 9/9 | 7/7 | 2/2 |
| Transformers + XGrammar | 9/9 | 7/7 | 2/2 |
| LMDeploy, только изменение ядра | 8/9 | 6/7 | 2/2 |
| LMDeploy, ядро + ограничение whitespace | 9/9 | 7/7 | 2/2 |
| TensorRT-LLM, FlashInfer | 5/9 | 4/7 | Не проверено: две ошибки передачи тензоров |

Первый vLLM-замер получил `reportMeasurementsMismatch` в `conflict-sample-42`.
В контрольном повторе ответ прошёл. Такой небольшой набор не позволяет ранжировать
движки по медицинскому качеству или считать один seed гарантией одинакового текста.

У llama.cpp, SGLang и Transformers token IDs семи текстовых промптов совпали с
vLLM. У LMDeploy в этой серии проверено число входных токенов; равенство всей
последовательности IDs не проверялось. При изображениях равенство текстовых IDs
не проверяет работу vision encoder и image processor.

## Диагностика TensorRT-LLM

Запуск 4B BF16 состоялся после выбора FlashInfer и исправления параметров
окружения. Сборка TensorRT-LLM использована без изменений исходников.
Это опубликованный ARM64 wheel 1.4.0rc2.post1 в отдельном окружении, а не
официальный контейнер NGC: его загрузка получила HTTP 403.

Обнаружены три разные проблемы:

- `conflict-sample-42` повторяет предложение внутри `conclusion` до 2048 токенов.
  `dictation-greedy-0` доходит до того же лимита на пробелах и переносах строк.
  Ответы не закрыли JSON. Ещё один завершённый протокол отклонён main-валидатором
  с `reportMeasurementsMismatch`.
- Обработчик Gemma 3 повторно добавляет BOS. В CPU-воспроизведении его вызова
  processor все семь текстовых входов начинаются с `[2, 2, ...]`. После удаления
  первого ID они совпадают с vLLM. Их длина совпадает с `prompt_tokens` сервера.
  Это аудит пути подготовки входа, а не извлечение IDs из работающего executor.
  См. `audit_trt_prompt.py`, `tensorrt-prompt-audit.json` и сохранённый
  `modeling_gemma3vl.py` из wheel.
- Оба запроса с изображениями получили ошибку передачи тензора между процессами.
  В журнале `torch_shm_manager` не находит `libcupti.so.13`. Это ошибка окружения;
  цвет изображения модель в этих запросах не оценивала.

Эти результаты **не доказывают, что TensorRT-LLM ухудшает MedGemma**. Для такой
проверки сначала нужны одинаковые входные IDs, согласованная политика whitespace
и исправное окружение передачи изображений. В данной серии TensorRT-LLM не даёт
выигрыша по скорости, который оправдывал бы переход рабочего сервиса сейчас.

Предыдущие неудачные попытки сохранены отдельно. Ошибки MPI, несовместимых кэшей
FlashInfer и неверного значения `kv_cache_config.dtype` не смешиваются с ошибками
генерации. Подробности подготовки — в [SETUP.md](SETUP.md).

|---|---|---|
| llama.cpp | Конвертация исходного checkpoint в GGUF BF16; отдельный BF16 projector для изображений. HTTP/SSE и JSON Schema через грамматику. | Требуется адаптация параметров sampling. Контекст сервера делится между слотами: для четырёх слотов по 16 384 нужно `--ctx-size 65536`. |
| SGLang | Исходный Hugging Face checkpoint BF16; OpenAI-совместимые HTTP/SSE и XGrammar. | В испытанном образе нужен исправленный chat template без повторного BOS. `top_k` отключается значением `-1`. |
| Transformers/PyTorch | Исходный checkpoint BF16, `AutoProcessor`, `generate`, XGrammar. | Это библиотека. HTTP/SSE, очередь, continuous batching, отмену и ограничения ресурсов придётся реализовать отдельно либо получить из серверного движка. |
| LMDeploy | Для Gemma 3 документация указывает backend PyTorch. | Проверен в отдельном окружении ARM64. Для нашего GB10 потребовались изменения attention-ядра и политики whitespace. Поддержку PyTorch нельзя переносить на TurboMind. |
| TensorRT-LLM | Проверен запуск 4B BF16, сервер SSE и JSON Schema. | Перед подключением нужны исправления подготовки входа и передачи изображений, затем повтор проверок. Поддержка архитектуры не гарантирует готовность всего профиля. |
| TensorRT Edge-LLM | Для DGX Spark есть сборка ARM64. | В проверенной версии 0.11.1 нет адаптера Gemma 3. Все три наших checkpoint объявляют `Gemma3ForConditionalGeneration`. Готовым вариантом замены его считать нельзя. |

Регистрация архитектур Edge-LLM проверена по исходникам, а не только по списку
в README: см. `edge-compatibility.json`. Наличие общего fallback `CausalLM` не
подтверждает реализацию vision encoder и особенностей attention Gemma 3.

## Границы сравнения

Тест не сравнивает все возможные настройки каждого движка. Это проверка
работоспособности и скорости выбранных BF16-профилей на одной машине.
Промпты короткие; доступный лимит контекста не означает, что четыре длинных
запроса были испытаны. У SGLang общий пул KV рассчитан на 16 384 токена.

Модели MedGemma 1.5 4B и 27B в этой серии не генерировали. Режим одновременной
нагрузки 4/4/4 здесь не проверялся. Перенос результатов 4B на них не обоснован.
Установка CPU-зависимостей некоторых кандидатов шла параллельно с опытами.
Это дополнительный источник вариации; второй движок одновременно GPU не занимал.

Успешный JSON и прохождение main-валидатора не доказывают медицинскую точность.
Смена движка также может менять текст при одинаковом seed из-за вычислительных
ядер, порядка операций, грамматики и реализации sampling. Проверка prompt token
IDs помогает исключить различие текстового шаблона, но не делает вычисления
двух движков идентичными.

## Диагностика LMDeploy

Штатный LMDeploy 0.18.0 загрузил checkpoint, но завершился при прогреве Triton
attention: ядру потребовалось 172 032 байта shared memory при лимите GB10
101 376 байт. Это `OutOfResources` для одного GPU-ядра, а не нехватка 128 ГБ RAM.
См. `lmdeploy-4b-bf16/container.log`.

Отдельная тестовая копия получила меньшее разбиение работы ядра для head dimension
256 на SM121. Формат весов и модель не менялись. Шесть проверок против FP32-расчёта
attention прошли с максимальным абсолютным расхождением менее 0,01 для BF16-входов.
Это ограниченная численная проверка, не доказательство корректности всех размеров
контекста. Patch и результаты находятся в `lmdeploy-kernel-*.{patch,json}`.

После этого восемь из девяти ответов завершились. Диктовка зациклилась на пробелах
и переносах строк до лимита 2048 токенов. LMDeploy вызывает XGrammar с разрешённым
произвольным whitespace. Во втором диагностическом варианте вызов получил
`any_whitespace=False`, как в наших остальных XGrammar-профилях. Схема, вход и
лимит токенов остались прежними. Все девять ответов завершились и прошли схему,
семь текстовых ответов — main-валидаторы.

Это объясняет исправление конкретного сбоя в данном наборе. Оно не доказывает,
что любой случай повторов имеет ту же причину. `lmdeploy-4b-sm121-experimental`
содержит исходный сбой и скоростную серию без грамматики;
`lmdeploy-4b-grammar-experimental` — повтор девяти полных запросов после изменения
whitespace. Скорость второго варианта заново не измерялась.

## Воспроизведение

`run_trial.py PLAN.json` выполняется только на DGX из каталога опыта.
Он проверяет простой исходных движков, сохраняет состояние, запускает временный
движок, выполняет `probe_http.py` или `probe_transformers.py` и восстанавливает
исходный контейнер. План содержит параметры запуска без секретов.

Сырые ответы и времена находятся в `*/results.jsonl`. Неудачные попытки сохраняются
в собственных каталогах с `failure.json` и журналом. Они не входят в медианы
успешных запусков. Исходники приложения и секретные конфиги опыт не меняет.

`analyze_survey.py` повторно проверяет ответы текущими валидаторами main и
пересчитывает `summary.json`. Его запускают из корня проекта через
`.venv311/bin/python evaluation/inference/dgx-spark-2026-11-04/engine-survey/analyze_survey.py`.
Хэши использованных исходников main сохранены в `validation-source-hashes.json`.

## Состояние DGX после опыта

`restoration.json` подтверждает восстановление всех четырёх рабочих контейнеров.
Их ID, образы, команды и политики перезапуска совпадают с исходными.
Все три vLLM-контейнера имеют статус `healthy`, очереди пусты, лимиты остаются
4/4/4. Inference backend и движки 1.5 4B / 27B не перезапускались.
Счётчики генерации двух простаивавших моделей не изменились.

Обе ручки inference без App Check возвращают HTTP 401. Временный GPU-контейнер
удалён. Ещё 15 остановленных контейнеров подготовки удалены; список находится
в `cleanup.json`. Сборки, GGUF, окружения и временные образы сохранены на DGX
для воспроизведения. Они не запускают дополнительные сервисы.

Скрипты исследования прошли Ruff и проверку синтаксиса. JSON и JSONL проверены
на чтение. `make check-architecture` сообщил 13 нарушений `swift.view-fragment`
в существующих Swift-файлах: `ExpandableContentView`, `PhotoCardView`,
`SectionHeaderView`, `DScreen`, `DButton` и `DToolbarButton`.
Эта работа не изменяла эти файлы. Сборка приложения не выполнялась: изменения
ограничены данным каталогом исследования.

# Контекст для проверки памяти DGX Spark

Проверено 5 ноября 2026 года. Эти источники объясняют ограничения измерений.
Они не устанавливают причину прежней записи `NV_ERR_NO_MEMORY` на нашем DGX.

- [NVIDIA: Known Issues](https://docs.nvidia.com/dgx/dgx-spark/known-issues.html).
  CPU и GPU используют общую DRAM. `cudaMemGetInfo` не учитывает всю память,
  которую система потенциально может освободить через swap. Поэтому отслеживаем
  также `MemAvailable`, активность swap, журнал ядра и успешность запросов.
  Значение `MemAvailable` само по себе не гарантирует успешную CUDA-аллокацию.
- [NVIDIA/dgx-spark-playbooks, issue 97](https://github.com/NVIDIA/dgx-spark-playbooks/issues/97).
  Пользователь сообщил о перезапуске при prefill на 128K токенов после ошибки
  выделения памяти. Это другой сценарий: у нас контекст ограничен 16384.
  Сообщение не доказывает общую причину и не является исправлением NVIDIA.
- [vLLM 0.28: Optimization and Tuning](https://docs.vllm.ai/en/v0.28.0/configuration/optimization/).
  Справочник параметров планировщика и памяти для закреплённой версии движка.
  Итоговый профиль выбираем по измерениям на наших трёх моделях.

В этой работе не сбрасываем системный page cache, не меняем swap, драйвер,
частоты, питание или параметры ядра. Одна конфигурация отличается от другой
только числом слотов и, для отдельного сравнения, KV-кешем 27B.

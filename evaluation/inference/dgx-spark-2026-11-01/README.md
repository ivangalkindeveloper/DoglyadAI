# Эксперименты MedGemma 4B на DGX Spark, 1 ноября 2026

Дополнительные серии для всех трёх моделей:
[совместная нагрузка 4/4/2](mixed-4-4-2/README.md) и
[сравнение 4/4/2 с 4/4/4](mixed-4-4-4/README.md).

Ниже описана первая серия MedGemma 4B. Её измерения и восстановление
завершены. Контрольная генерация, готовность трёх движков и защита App Check
проверены. Общие итоги и статус последующих серий приведены в
[RESULTS.md](RESULTS.md).

## Цель и границы

1. Сравнить исходный eager mode с компиляцией и CUDA Graphs.
2. Измерить обработку нескольких одновременных запросов одной моделью.

Модель: `google/medgemma-4b-it`, revision
`290cda5eeccbee130f987c4ad74a59ae6f196408`, BF16. Квантование не меняется.
Исходные лимиты: контекст 16384, 2048 токенов в scheduler batch,
KV-кеш 4 GiB, максимум шесть изображений, prefix caching включён.
MedGemma 1.5 4B и 27B остаются загруженными с исходными настройками.
Постоянные профили, Compose, конфигурация backend и маршруты не изменяются.

Варианты:

| Вариант | `--enforce-eager` | `--max-num-seqs` | Назначение |
|---|---|---:|---|
| eager-1 | Да | 1 | Исходный работающий контейнер |
| compiled-1 | Нет | 1 | Изолировать влияние компиляции и CUDA Graphs |
| eager-8 | Да | 8 | Пакетная обработка в eager mode |
| compiled-8 | Нет | 8 | Пакетная обработка с компиляцией и CUDA Graphs |

Удаление `--enforce-eager` проверяет совместный эффект стандартной компиляции
и CUDA Graphs. Этот эксперимент не разделяет вклад этих двух механизмов.
Фактически выбранные режимы нужно подтверждать журналом запуска.

## Методика

`benchmark.py` работает внутри контейнера vLLM и обращается к loopback HTTP.
Задержка Wi-Fi, SSH и main backend в эти измерения не входит.
Измерения используют monotonic clock. Все данные синтетические.

- Короткий и длинный текст повторяют задания предыдущего сравнения DGX/A10.
  Длина ответа фиксирована: 256 токенов, `ignore_eos=true`, temperature 0,
  seed 0. Сначала два прогрева, затем пять измерений на задание.
- Каждый запрос имеет уникальный `cache_salt`. Проверяется отсутствие
  попаданий в prefix cache. Модель остаётся загруженной между запросами.
- Варианты с `max-num-seqs=8` проверяются при 2, 4 и 8 одновременных клиентах.
  Для длинного текста выполняются один прогрев и три измеряемые волны.
  В каждой волне все запросы отправляются через `asyncio.gather`.
- В исходном режиме дополнительно проверяется одна волна из четырёх запросов:
  движок принимает HTTP-запросы, но выполняет генерацию последовательно.
- Структурированные ответы используют xgrammar и JSON Schema. Проверяется
  схема, перенос идентификатора случая и заданного измерения. Есть задания
  без изображения, с одним изображением и с шестью изображениями.
- Изображение — искусственная сетка JPEG 256×256, а не УЗИ. Это проверка
  мультимодального пути и структуры ответа. Она не оценивает клиническое
  качество или производительность на реальных УЗИ.
  Во всех запросах используется одна сетка. Кеш мультимодального процессора
  не отключается, поэтому задержки этих запросов нельзя переносить на поток
  разных изображений пациентов. Дополнительно проверяется волна из восьми
  запросов по шесть изображений: один прогрев и одна измеряемая волна.
- В compiled-8 добавлена отдельная проверка восьми запросов по шесть разных
  JPEG: каждый файл имеет уникальную нарисованную метку. Между запросами и
  волнами изображения не повторяются. Один прогрев, затем две измеряемые
  волны. Это проверяет обработку без повторного использования одного и того
  же изображения, но всё ещё не является испытанием на реальных УЗИ.
- Для JSON разрешён естественный конец ответа, максимум 384 токена.
  Длины могут отличаться, поэтому фиксированные текстовые задания дают
  более чистое сравнение скорости. Прогревы и измерения сохранены раздельно.
- Генерируемый текст не сохраняется: только SHA-256, количество токенов,
  метрики и результаты проверок. Секреты в артефакты не попадают.

Метрики:

- TTFT: от отправки запроса до первого непустого content chunk.
- Decode tok/s в итоговом отчёте:
  `(completion_tokens - 1) / (stream_end_time - first_content_time)`.
  Это клиентская оценка по потоку HTTP, не аппаратный профайлер.
  Исходное поле `decode_tokens_per_second` в raw JSON использовало последний
  непустой content chunk. В compiled-1 на коротком задании часть последних
  токенов не давала видимого текста, поэтому такое поле завышает скорость.
  Исторические raw JSON сохранены без изменений. `summarize.py` пересчитывает
  показатель по завершению полного потока в `stream_decode_tokens_per_second_p50`.
  Главная метрика сравнения — полное время фиксированных 256 токенов.
- Полное время: от отправки запроса до завершения потока.
- Общая скорость волны: сумма успешно сгенерированных токенов / время всей волны.
- p50 и p95: медиана и линейно интерполированный 95-й процентиль.
  Выборка небольшая. p95 здесь описывает этот запуск, а не гарантирует SLA.

`service_probe.py` отдельно вызывает существующий `VLLMService` из работающего
образа backend. В отдельном процессе создаётся конфигурация с ёмкостью 1, 2, 4
или 8 запросов. Настройки работающего HTTP-сервиса остаются исходными.
Проверка не проходит через HTTP/App Check, main backend или iOS и не заменяет
полный интеграционный тест. Обработчики и проверка App Check не изменяются.

## Выполнение и восстановление

`run_experiment.py` ждёт завершения исходного замера. Затем останавливает
только исходный контейнер 4B и последовательно создаёт временные варианты.
Используется тот же локальный Docker image ID и тот же volume с весами.
HF работает offline. Тестовый контейнер не публикует порты на хосте.

Блок `finally` удаляет временный контейнер и запускает исходный. В артефакте
`conditions.json` сравниваются ID контейнеров, образы, команды, контрольные
суммы Compose и серверной конфигурации. Запуск прерывается при доступной RAM
менее 4 GiB. После каждого варианта проверяются новые Xid/OOM в журнале ядра.
Отключение питания или сбой GPU могут помешать автоматическому восстановлению.

## Файлы

- `benchmark.py` — синтетические запросы и измерения.
- `service_probe.py` — проверка существующего класса сервиса и его очереди.
- `run_experiment.py` — временные контейнеры и восстановление.
- `test_benchmark.py` — проверки расчётов, полноты ответа и отсутствия кеша.
- `summarize.py` — производные метрики и CSV без изменения исходных записей.
- `verify_restoration.py` — подтверждение восстановления и контрольная генерация.
- `artifacts/` — исходные результаты, журналы запуска и телеметрия.
- `artifacts/runner_versions.json` — соответствие вариантов версиям runner.
  Исходный runner извлечён из сохранённого контейнера. Версия eager-8
  восстановлена из него добавлением единственной строки плана для шести
  изображений. Версия compiled-8 сохранена непосредственно с DGX.
  Форматированные скрипты рядом с README удобны для последующих запусков.
  В `run_experiment.py` также исправлен выход по SIGINT/SIGTERM: остановка
  сразу переходит к восстановлению, а не к следующему варианту.

Локальные проверки: девять тестов `test_benchmark.py` прошли. Ruff прошёл.

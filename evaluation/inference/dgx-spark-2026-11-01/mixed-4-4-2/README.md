# Проверка трёх моделей: 4 + 4 + 2

Дата: 1 ноября 2026. Статус: измерения завершены, исходный режим восстановлен.
При восстановлении 27B обнаружены сообщения драйвера `NV_ERR_NO_MEMORY`;
проверка чистоты журнала не прошла. Работоспособность всех моделей подтверждена.

Результаты и выводы: [RESULTS.md](RESULTS.md).

Цель — проверить одновременную работу MedGemma 4B, MedGemma 1.5 4B и
MedGemma 27B на одном DGX Spark. Предыдущая серия проверяла только 4B.

| Модель | Одновременных запросов | Ревизия | KV-кеш |
|---|---:|---|---:|
| `google/medgemma-4b-it` | 4 | `290cda5eeccbee130f987c4ad74a59ae6f196408` | 4 GiB |
| `google/medgemma-1.5-4b-it` | 4 | `91850547d9f0b2fdd21aa7c5f4f3d1a8a52c243b` | 4 GiB |
| `google/medgemma-27b-it` | 2 | `2d3e00ea38b50018bf5dd3aa1009457cd2d5a48f` | 8 GiB |

Исходный режим всех трёх моделей: BF16, eager, один запрос на движок,
контекст 16384, `max-num-batched-tokens=2048`, максимум шесть изображений.
В тестовых контейнерах убирается только `--enforce-eager`, меняется
`--max-num-seqs` на 4/4/2 и явно закрепляется уже скачанная ревизия.
Бюджеты кеша и остальные параметры остаются исходными.
Используется тот же Docker image ID, который записан в `conditions.json`.

## Методика

1. Контрольный одиночный текстовый запрос к каждой исходной модели:
   один прогрев и три измерения, 256 выходных токенов.
2. Последовательная загрузка трёх временных движков с компиляцией и
   CUDA Graphs. Они работают одновременно на одном GPU без опубликованных
   портов. Исходные GPU-контейнеры остановлены, но сохранены.
3. Для каждой модели отдельно: один клиент и целевое число клиентов.
   Для текста — один прогрев и три измеряемые волны. Для JSON с шестью
   уникальными JPEG — один прогрев и две измеряемые волны.
4. Совместная нагрузка 4 + 4 + 2. Текст: один прогрев и три измеряемые волны.
   JSON с изображениями: один прогрев и две измеряемые волны.
5. Совместная нагрузка почти на весь контекст. Через `/tokenize` подбирается
   текст из 15000–15872 входных токенов для каждой модели. Выход ограничен
   ровно 64 токенами. Один прогрев и одна измеряемая волна 4 + 4 + 2.
6. Три волны 4 + 4 + 2 через существующий класс `VLLMService` в отдельном
   процессе. Первая волна прогревочная. Три изолированных экземпляра класса
   имеют разные лимиты, поскольку рабочая конфигурация пока задаёт один
   общий лимит для очередей всех моделей. Сам HTTP-сервис не изменяется.
7. Удаление временных контейнеров и последовательный запуск исходных.

Синхронный старт волны обеспечивается `asyncio.Event`. Все изображения и
payload готовятся до открытия этого события. Время каждой отправки записано
в raw JSON. Для каждого запроса действует абсолютный дедлайн 120 секунд,
включая ожидание и весь поток ответа. Это соответствует внутреннему
operation timeout сервиса, а не только тайм-ауту между HTTP-чанками.

Текстовые задания используют temperature 0, seed 0, `ignore_eos=true`.
У каждого запроса уникальный `cache_salt`. Повторное использование prefix
cache не допускается. Изображения — синтетические сетки с уникальными
метками, не УЗИ. JSON проверяется по схеме, идентификатору случая и заданному
измерению. Текст генерации и изображения в результаты не записываются.

Для совместных волн суммарная скорость считается по полному времени всей
волны. Отдельно записываются задержки каждой модели. Эти показатели нельзя
смешивать: быстрые 4B могут завершиться раньше 27B. Decode измеряется до
завершения всего потока, включая невидимые служебные токены.

Телеметрия примерно каждые пять секунд включает доступную RAM, swap,
температуру/загрузку GPU, число активных/ожидающих запросов и вытеснения
из KV-кеша. Запуск прерывается при доступной RAM менее 4 GiB или новом
событии Xid/OOM. Восстановление выполняется в `finally` на самом DGX.
Потеря соединения с Mac не останавливает этот процесс.

## Файлы

- `benchmark_matrix.py` — измерения движков и проверка JSON.
- `service_matrix.py` — отдельная проверка класса сервиса.
- `run_matrix.py` — временные контейнеры, телеметрия и восстановление.
- `fixtures.py`, `host_helpers.py` — зафиксированные помощники предыдущей серии.
- `baseline-targets.json`, `candidate-targets.json` — адреса только приватной
  Docker-сети, идентификаторы моделей и ревизии. Секретов в них нет.
- `test_matrix.py` — проверки модели запроса, синхронного старта, полноты
  генерации, расчёта общей скорости и регистрации ошибок.
- `analyze_matrix.py` — построение производных JSON/CSV без изменения исходных
  результатов. Запуск: `python analyze_matrix.py --directory artifacts`.
- `verify_matrix.py` — проверка восстановленных контейнеров, конфигурации,
  контрольной генерации каждой модели и обязательного App Check.
- `artifacts/` — исходные результаты и подтверждения восстановления.

В `artifacts/` сохранены именно запущенные версии удалённых скриптов,
включая `baseline_runner.py`. До начала candidate-серии драйвер получил
форматирование, контрольные суммы и продолжение после неуспешной волны
при условии готовности и простоя движков. Функции подготовки запросов,
измерения, проверки и расчёта показателей совпадают на уровне AST.
Проверка зафиксирована в [provenance.json](artifacts/provenance.json).
Начальные суммы в `conditions.json` относятся к снимку до этих изменений;
суммы реально запущенного candidate-драйвера записаны в `candidate.json`.
Сырые скрипты в `artifacts/` нельзя форматировать при последующем анализе.

Ограничения: синтетические задания, короткие серии, одна машина. Это не
клиническая оценка, не испытание длительной случайной нагрузки и не полный
путь через main backend, App Check и iOS. Защита App Check не отключается.
Параметры рабочего развёртывания после теста остаются исходными.

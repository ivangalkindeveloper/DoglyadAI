# Бюджет обработки длинного входа

Статус: завершено. Из 12 сочетаний 11 прошли измерения; одно отклонено движком
при запуске. Все результаты, включая отказ, находятся в [таблице](TABLE.md).

Исходный бюджет 2048 остаётся разумным выбором для проверенного сценария.
У моделей 4B увеличение до 4096/8192 не дало заметного прироста скорости,
а максимальная пауза выросла примерно с 0,26 до 0,95–0,97 секунды.
У 27B переход с 2048 на 4096 увеличил максимальную паузу с 1,56 до 3,00 секунд
без ускорения полного ответа.

Бюджет 1024 сокращает максимальные паузы примерно вдвое. Цена для 27B —
снижение суммарной скорости примерно на 4%. Такой вариант можно рассматривать,
если плавность потока важнее пропускной способности на длинных входах.

27B с бюджетом 8192 не запустилась: для контекста 16384 vLLM потребовал минимум
8,76 GiB KV-кеша вместо выделенных 8 GiB. Это проверка допустимости конфигурации,
а не OOM хоста. Остальные параметры не менялись, чтобы принудительно запустить
этот вариант. Причина сохранена в [журнале](../runs/27b-prefill8192/container.log)
и [описании недоступного профиля](../unavailable-profiles.json).
Кеш здесь задан явно через `kvCacheMemoryBytes`; увеличение одного
`gpuMemoryUtilization` не заменяет изменение этого бюджета.

У этих моделей есть sliding-window attention. При расчёте необходимого кеша
vLLM учитывает окно и ещё не завершённые пакеты обработки входа. Поэтому
увеличение бюджета prefill может увеличить требование к памяти даже при
неизменном `max_model_len`. Формулы установленной версии сохранены в
[cache-accounting.json](../04-kv-cache/cache-accounting.json).

Сравниваются `max_num_batched_tokens=1024/2048/4096/8192`. Это бюджет работы
планировщика за шаг, а не `max_tokens` ответа. Остальные параметры модели
сохраняются: четыре слота, BF16, контекст 16384, исходный KV-кеш.

Четыре клиента одновременно отправляют независимые входы примерно по 8000
токенов. Для каждого запроса используются отдельный `cache_salt` и ровно 128
выходных токенов. Измеряются три волны после прогрева.

Таблица показывает TTFT, полное время и интервалы между текстовыми фрагментами
SSE. Последние не всегда равны интервалам между отдельными токенами. Больший
бюджет может ускорять обработку входа и одновременно увеличивать паузы уже
начавшегося потока. Поэтому максимальный бюджет не выбирается автоматически.

Это одновременный приход четырёх длинных запросов. Смешанный поток коротких
и длинных запросов с произвольными интервалами здесь не моделируется.

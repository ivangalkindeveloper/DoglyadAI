# Проверка и включение N-gram 8 на DGX Spark

Цель: проверить N-gram 8 при одновременной нагрузке 4/4/4 и применить его
к трём работающим MedGemma. Предыдущая серия проверяла speculative decoding
при одном запросе: [исходное исследование](../dgx-spark-2026-11-05/05-speculative-decoding/README.md).

Статус: N-gram 8 применён ко всем трём моделям на DGX. Все три движка готовы,
inference backend сохранил прежний контейнер. Итоговая проверка:
[`final-audit.json`](final-audit.json), [`verification.json`](verification.json).

## Результат проверки

Полный отчёт при нагрузке 4/4/4 ускорился в 1,62–1,74 раза:

| Модель | Без N-gram | N-gram 8 |
|---|---:|---:|
| MedGemma 4B | 31,92 с | 18,33 с |
| MedGemma 1.5 4B | 29,99 с | 17,41 с |
| MedGemma 27B | 90,90 с | 56,13 с |

Это медианы восьми запросов на модель в двух сериях, без прогрева.
Время первого токена практически не изменилось. Тексты и число выходных
токенов иногда различаются; таблица отражает время полного ответа.
Подробности и длительности смешанных серий — в [RESULTS.md](RESULTS.md).

В основной проверке оба режима завершили по 60 ответов с валидным JSON.
Все 12 проверок цветных изображений прошли; повторов длинных предложений
не было. У каждого режима два текстовых ответа отклонены main-валидатором
с `reportMeasurementsMismatch`. Набор этих ответов различается; считать
проверку подтверждением идентичного качества нельзя.

Для отличающегося случая 1.5 4B выполнена дополнительная проверка 16 одинаковых
seed. Без N-gram отклонены 9/16 ответов, с N-gram — 6/16. В трёх парах прошёл
только исходный режим, в шести — только N-gram. Увеличение частоты отказов
в этой малой выборке не подтвердилось. Ошибка встречается в обоих режимах;
это не доказательство улучшения или клинической эквивалентности.
Все 32 дополнительных ответа завершились с валидным JSON.

Без N-gram один запрос из основной серии занял 127,10 с и превысил штатный
предел inference API в 120 с. С N-gram таких превышений не было.
Минимум доступной RAM в нагрузочных сериях: 24,12 GiB без N-gram и 18,83 GiB
с N-gram. Максимальная температура GPU: 64°C и 69°C соответственно.
OOM-kill и вытеснений запросов из KV-кеша не было.

При этом в журнале NVIDIA есть одна запись `NV_ERR_NO_MEMORY` от
2026-11-05 22:15:01 MSK, во время первой смешанной серии с N-gram.
Это ошибка выделения памяти драйвером, даже при отсутствии OOM-kill.
Она не сопровождалась ошибкой запроса, падением контейнера или перезагрузкой.
Причина и принадлежность записи конкретному процессу не установлены.
Нельзя утверждать, что GPU-ошибок памяти не было, или что N-gram стал причиной.
После этого отдельно повторена смешанная нагрузка; фактура находится
в `memory-recheck/`. Encoder-кеши в повторной проверке уже прогреты, поэтому
она не воспроизводит начальную обработку новых изображений.
Все 24 повторных ответа завершились с валидным JSON; новых записей об ошибке
памяти до финальной проверки не появилось. Исходная запись остаётся открытым
вопросом для наблюдения, а не считается устранённой.

Счётчики движков подтвердили ровно четыре завершения на модель в каждой
серии. В N-gram-серии предложено 14 365 токенов, принято 6 508.
Все 60 входных последовательностей токенов совпали между режимами;
полностью совпали 35 текстов ответа. Входы не менялись между сравнениями.

## Метод

- Сначала исходный режим, затем N-gram 8. В каждом режиме все три модели
  загружены одновременно. В каждой серии одновременно поступают 12 запросов,
  по четыре на модель.
- Один прогрев, две измеряемые серии одинакового отчёта, две серии разных задач.
  Всего 60 запросов на режим: 12 прогревочных и 48 измеряемых.
- Девять разных синтетических случаев на модель: отчёты RU/EN, противоречивые
  измерения, исправление описания, диктовка, одно и два цветных изображения.
  Изображения проверяют работу multimodal-входа, а не качество диагностики УЗИ.
- Входы, JSON Schema, sampling и предел 2048 токена взяты из предыдущего
  исследования без изменений. Каждый запрос получает отдельный `cache_salt`.
  Строки ответа не обрезаются. Сборщик ждёт естественное завершение SSE.
- Запросы идут непосредственно к закрытым адресам движков внутри Docker-сети
  DGX. Это проверка движков. Она не заменяет проверку полного пути из приложения
  с App Check. Все штатные проверки доступа остаются включены.
- Полные ответы проверяет JSON Schema и текущий валидатор main backend.
  Отдельно учитываются повторы длинных предложений и превышение 120 секунд,
  которое сделало бы запрос непригодным для штатного inference API.
- Температура, память и swap записываются каждые пять секунд. Счётчики vLLM
  снимаются до и после каждой серии. Время завершения серии включает сбор
  финальных метрик; время каждого запроса включает только HTTP/SSE.

## Изменение конфигурации

```json
{
  "method": "ngram",
  "num_speculative_tokens": 8,
  "prompt_lookup_min": 2,
  "prompt_lookup_max": 5
}
```

Это единственное изменение аргументов vLLM. Сохраняются BF16, ревизии моделей,
образ vLLM, контекст 16384, 4/4/4 слота, KV-кеш 4/4/8 GiB, prefill 2048,
prefix caching, компиляция и CUDA Graphs. Квантование не выполняется.

В vLLM 0.28.0 N-gram автоматически отключает async scheduling и выбирает
Model Runner V1. Стартовый лог также предупреждает о бюджете 2048 токена
с учётом draft-токенов. Это внутренние последствия включения N-gram;
сравнение отражает режим целиком. Четыре слота на модель сохраняются.
Увеличение prefill-бюджета в эту проверку не входит.

`deploy.py` проверяет точный состав изменения, сохраняет прежние файлы,
останавливает только три движка и запускает их последовательно, начиная с 27B.
При ошибке старта восстанавливает прежнюю конфигурацию и движки.
Inference backend остаётся тем же контейнером. Во время загрузки моделей
генерация временно недоступна.

## Файлы

- `cases-*.json`, `source-input-hashes.json`: входы и их происхождение.
- `mixed.py`, `probe.py`, `observe.py`: сбор полных ответов и метрик.
- `baseline/`, `ngram8/`: результаты, исходные ответы, метрики и состояния.
- `evaluate.py`, `validation.json`, `summary.json`: проверка и сравнение.
- `deploy.py`, `deployment-*.json`, `startup-telemetry.jsonl`: применение.
- `execution-source/`: точные версии скриптов, выполненные на DGX. Копии
  в корне также отформатированы; из них удалены неиспользуемые импорты.
- `sampling_check.py`, `evaluate_sampling.py`, `sampling-check/`: дополнительная
  проверка 16 одинаковых seed для `conflict-sample-42` на 1.5 4B. Четыре
  одновременных запроса, остальные модели загружены без нагрузки. Сначала
  N-gram, затем исходный режим; после проверки N-gram восстанавливается.
- `memory_recheck.py`, `memory-recheck/`: две повторные смешанные серии.
- `deployment-files/`: применённые файлы генератора без секретов.
- `SHA256SUMS`: контрольные суммы фактуры.

## Проверка развёртывания

- 50 тестов `deploy/test` проходят. Ruff и проверка сгенерированного Compose
  проходят. Профиль без N-gram для отдельной amd64-машины сохраняет прежний CLI.
- Реальные команды трёх движков совпадают с каноническим профилем. BF16,
  ревизии весов и image ID сохранены. Все маршруты backend видят нужные модели.
- Обе API-ручки возвращают 401 без App Check. Проверка из приложения с настоящим
  токеном в эту работу не входит. Backend не перезапускался, boot ID DGX сохранён.
- После восстановления 1.5 4B выполнен один дополнительный полный отчёт;
  JSON Schema и main-валидатор приняли его. Всего получено 177 полных ответов:
  120 основной серии, 32 дополнительных по seed, 24 повторных и один smoke.
- Общий `make check-architecture` по-прежнему сообщает 13 существовавших
  замечаний `swift.view-fragment`; исходники iOS эта работа не меняет.
- Первая версия проверки готовности ошибочно учитывала три остановленных
  контейнера загрузки весов как лишние работающие контейнеры. Они сохранены.
  Финальная проверка отдельно учитывает работающие и остановленные контейнеры.

Откат файлов хранится на DGX в
`/var/tmp/doglyad-ngram-rollout-20261105/backup`. Для отключения N-gram следует
удалить `speculativeConfig` из трёх моделей исходного профиля, снова сгенерировать
стек и последовательно пересоздать движки. Backend и том весов сохраняются.
Изменения исходников находятся в рабочей копии; отдельный commit/push в этой
задаче не выполнялся.

Результаты этой проверки относятся к указанным синтетическим случаям.
Они не доказывают клиническую эквивалентность моделей на произвольных данных.
Различия текста при одинаковом seed возможны из-за численных особенностей
батчинга и декодирования; точное совпадение текста учитывается отдельно.
Документация vLLM различает сохранение распределения при speculative decoding
и воспроизводимость конкретного ответа. Она допускает различия из-за
численных вычислений и состава батча:
[vLLM 0.28.0 — lossless guarantees](https://docs.vllm.ai/en/v0.28.0/features/speculative_decoding/#lossless-guarantees-of-speculative-decoding).

# Общий harness Doglyad

Правьте навыки, хуки и настройки в `harness/`. Каталоги агентов содержат
генерируемые копии и исключены из Git. Общие инструкции остаются в `AGENTS.md`.

После клонирования, обновления ветки или изменения исходников выполните:

```sh
make sync-harness
make check-harness
```

Нужен Python 3.11 или новее. Дополнительные Python-пакеты не требуются.
Команды не запускают сборку приложения, backend или оценку моделей.
`python3 tools/sync_harness.py --dry-run` показывает ожидаемые изменения.

## Исходники и результаты

| Исходник | Генерируемые файлы |
|---|---|
| `skills/` | `.agents/skills/` для Codex и `.claude/skills/` для Claude |
| `hooks/` | Общие исполняемые скрипты; адаптеры вызывают их напрямую |
| `adapters/codex/config.toml` | Общие настройки в `.codex/config.toml` |
| `adapters/codex/hooks.json` | `.codex/hooks.json` с абсолютными путями к скриптам |
| `adapters/claude/settings.json`, `hooks.json` | `.claude/settings.json` |
| `mcp/servers.json` | MCP в `.codex/config.toml` и `.mcp.json` |
| `mcp/mobilebuildmcp.yaml` | `.mobilebuildmcp/config.yaml` |
| `AGENTS.md` в корне | `CLAUDE.md` с импортом `@AGENTS.md` |

`adapters/*/hooks.json` задают события и имена инструментов каждого агента.
Значения `@SECURITY_HOOK@` и `@POST_EDIT_HOOK@` заменяются командами с корректным
экранированием пути проекта. Логика проверки не копируется в адаптеры.

Пока поддерживаются локальные MCP-серверы через stdio. Версии пакетов закреплены
в `mcp/servers.json`. Установка пакета остаётся отдельным действием клиента MCP.
Данные доступа не помещаются в исходники harness.

## Обновление и личные настройки

Синхронизатор записывает состав и хеши своих файлов в
`.codex/harness-manifest.json`. Он сначала проверяет все назначения, затем
обновляет изменившиеся файлы и удаляет только устаревшие файлы из своего списка.
Повторный запуск без изменений ничего не перезаписывает.

Ручная правка генерируемого файла останавливает синхронизацию до записи.
Перенесите нужное изменение в исходник. Личные параметры Claude храните в
`.claude/settings.local.json`, личные параметры Codex — в пользовательской
конфигурации. Синхронизация их не меняет. Не удаляйте манифест для обхода
проверки конфликтов. Символические ссылки в назначениях не перезаписываются.

`make check-harness` проверяет соответствие генерируемых файлов исходникам.
Для свежего checkout сначала нужен `make sync-harness`. Файл блокировки находится
в `build/harness/`; он предотвращает одновременную запись двух запусков.
Для проверки в CI можно синхронизировать harness в чистом checkout и запустить
следующие тесты:

```sh
python3 -m unittest discover -s tools/tests -p 'test_harness*.py'
```

## Хуки

- `PreToolUse` вызывает `security_check.py` перед командами shell. Он проверяет
  известные формы `git add` и `git commit` на защищённые пути. Это вспомогательная
  проверка команд, а не полная граница безопасности shell.
- `PostToolUse` вызывает `post_edit.py` после `Edit`/`Write`/`MultiEdit` и патчей
  Codex. Для Swift он сначала выполняет существующий `make format-ios`, который
  форматирует весь разрешённый набор Swift-файлов. Затем хук проверяет архитектуру
  изменённых файлов под `ios/` и `backend/{main,inference}/app/`.
  Для правки Python запускается только анализатор архитектуры.
  Хук возвращает код 2 и диагностику агенту при ошибке; сделанная правка остаётся
  в файле. Сборки приложения, backend и длительные оценки не запускаются.

## Проверка архитектуры

```sh
make check-architecture
python3 harness/checks/architecture.py path/to/edited.swift path/to/edited.py
```

Команда без путей проверяет весь исходный код приложения и обоих backend.
Файлы в `ios/Config`, `ios/Firebase` и `ios/DoglyadNeuralModel/Resources`
исключены. Секреты, зависимости и результаты сборки не анализируются.
Удалённые файлы пропускаются. Изменения через shell не вызывают этот хук:
после них запустите команду явно. Проверка возвращает ненулевой код при нарушениях
и печатает путь, строку и идентификатор правила. Старые нарушения тоже видны;
автоматического списка исключений нет.

| Правило | Проверка |
|---|---|
| `swift.protocol-name` | Имя объявленного протокола оканчивается на `Protocol` |
| `swift.view-method` | View не содержит методов, кроме методов адаптеров и API модификаторов |
| `swift.view-fragment` | View не содержит вычисляемых UI-фрагментов вне `body` |
| `python.layer-import` | `model` не импортирует `service`/`route`; `service` не импортирует `route` |

Swift разбирается через SwiftParser/SwiftSyntax установленного Xcode. При первом
запуске компилируется только сам анализатор; кеш находится в
`build/harness/architecture/`. Скачивать SPM-пакеты не нужно. Для определения
наследования и расширений анализатор читает также остальные Swift-файлы проекта,
но сообщает нарушения только в выбранных файлах. Python разбирается через AST
без импорта приложения. Каждый backend проверяется как отдельный пакет `app`.

Проверки намеренно ограничены синтаксисом. Swift-проверка распознаёт явные
наследования, `some View`, `@ViewBuilder` и распространённые конкретные View-типы.
Она не разрешает typealias, типы сторонних библиотек, локальные переменные
с выведенным типом и связи между ViewModel. Свойства типа `Color` допускаются
как параметры оформления. Допустимы точки входа UIKit-адаптеров, расширения
`View`, возвращающие View, и методы расширений компонентов, которые только
вызывают `modifier(...)`. Python-проверка учитывает прямые, относительные и
вложенные импорты, но не транзитивные зависимости и динамический `importlib`.
Эта команда не заменяет проверку типов, сборку и архитектурное ревью.

Codex требует доверия к новым определениям hooks. Claude может потребовать
подтверждения проектного MCP. Синхронизация не подтверждает доверие за пользователя.
Проверьте загрузку настроек в клиенте после перезапуска сессии.

# Doglyad backend rules

### Python backend

- **Framework:** FastAPI with Pydantic models.
- **Formatting:** Run `make format-backend` and verify with `make lint-backend`. Put every nonempty function/method/constructor parameter and call argument on its own line, including single arguments and `self`/`cls`, with a trailing comma and the closing parenthesis on a separate line. The project combines LibCST with Ruff; use that pipeline instead of Ruff alone to enforce the rule. Keep empty lists as `()`. Preserve string values and f-string expressions; lambda parameter syntax, class inheritance lists and subscripts retain their normal Python syntax. The rule covers all Python sources in `backend/`, including tests, scripts and migrations, excluding secrets, virtual environments and generated directories. CI checks the same pipeline. See `tools/README.md`.
- **Typing:** Put `from __future__ import annotations` in every file and annotate all functions and values.
- **Naming:** Use snake_case for functions and variables, CamelCase for classes and Pydantic models, and camelCase for Pydantic fields shared with iOS.
- **Database entity names:** Name concrete SQLAlchemy mapped entities with the `DB` suffix, matching client persistence models: `BillingSubscriptionDB`, `BillingPaymentDB`, and `BillingOwnerDB`. Their files use the matching snake_case names, such as `billing_subscription_db.py`. Keep API/domain models free of this suffix. Engines, session managers, repositories and the abstract declarative base retain names describing their infrastructure roles. Renaming Python entities must not rename SQL tables or columns.
- **File names:** Name each implementation file after its single public class or top-level function, converting type names to snake_case: `NeuralModelService` lives in `neural_model_service.py`, `VLLMService` in `vllm_service.py`, and `NeuralModelServiceFactory` in `neural_model_service_factory.py`. Avoid generic names such as `base.py`, `factory.py`, or `utils.py` when the implementation has a more specific name.
- **Semantic packages:** Group main-backend implementations by responsibility inside `app/core/` and `app/service/`; keep only package declarations at those roots. `core` owns application composition, configuration, localization, App Check, HTTP/logging infrastructure, and feature-specific route dependencies. `service` owns billing, configuration responses, neural model access, reports, dictation, email, shared validation and HTTP request limiting. Import implementations from their owning packages without compatibility re-exports at the old paths. Keep declaration/file names aligned when moving files, and update dependent tests, tools and documentation together.
- **Composition responsibilities:** `ApplicationFactory` builds HTTP applications; `ServiceFactory` creates services once during startup; `ServiceDependencies` retrieves ready instances from `MainContainer` without recreating them per request. Group infrastructure methods in cohesive classes such as `AppCheck`, `BillingDependencies`, `LocalizationDependencies`, `HttpRequestPolicy` and `LoggingConfigurator`. Keep pure domain parsing functions where they have a clear responsibility; do not introduce universal utility/factory classes. The billing worker owns its resources directly and must not construct an HTTP application or initialize unrelated generation/authentication services.
- **One declaration per file:** A file contains only one class, dataclass, or enum, including private types. A function-based module provides only one public top-level function. Put additional public functions and types in their own named files; private implementation helpers and supporting constants may stay with their owning declaration. A module containing only a shared value, such as `limiter`, is named after that value.
- **Framework files:** Preserve required entry-point and discovery names: `main.py` composes the FastAPI application, `__init__.py` contains package exports without implementations, and pytest uses `conftest.py` and `test_*.py` for fixtures and test functions. These exceptions do not permit grouping application implementations or test helper classes; test doubles also live in separate files named after their classes.
- **Models:** Put each Pydantic model or request dataclass in its own file under `app/model/`. Keep configuration entities separate from localized response models.
- **Response model names:** In both backend services, models returned as HTTP endpoint responses must have the `Response` suffix, for example `GenerateReportResponse` or `GenerationResponse`. Internal models may use any meaningful CamelCase name and have no mandatory suffix.
- **Response field names:** Every backend model used in an HTTP response, including nested models and responses exchanged between the two services, must declare and serialize its fields in camelCase. Do not expose snake_case fields or use serialization aliases to conceal a differently named field. Technical identifier values and internal models outside the HTTP response contract are not field names.
- **Language and headers:** Use `LanguageCode` and `HttpHeader` in main-backend code; convert enum values to strings at JSON and HTTP boundaries.
- **Concurrency:** Use `async`/`await` for handlers and HTTP calls. Reuse the shared `httpx.AsyncClient` created by lifespan and injected into transport services.
- **Configuration:** Read environment values through `pydantic_settings` in main's `app/core/configuration/variables.py` or inference's `app/core/variables.py`. Compose supplies secret environment files; do not hardcode or directly read secret values in application services.
- **Dependencies:** Pin versions in `requirements.txt`.
- **API errors:** Raise concrete `ApiError` types from `app/error/` for expected runtime failures. Keep public code, description and HTTP status in the error class; translate known external failures with `raise ... from cause`. HTTP response formatting and error logging belong to `ApiErrorHandler`, including middleware responses. Pydantic validators retain their validation exceptions, and startup configuration failures abort startup. Never return raw exception messages, validation input or context; unexpected errors are logged with sanitized traceback locations.
- **Inference logs:** Never log request bodies because they contain patient data and images. Log only status, model ID, image count, and string lengths.
- **Inference route construction:** Build the inference path only in `NeuralModelServiceFactory.create()` (`app/service/neural_model/neural_model_service_factory.py`). The same connection applies to all environments. Lifespan injects the ready `NeuralModelService` into application services in `MainContainer`; routes receive services through `Depends`.

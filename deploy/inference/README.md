# Профили GPU-хостов и генерация Compose

Один профиль описывает модели одного GPU-хоста. Генератор создаёт один
`backend_inference`, отдельный приватный vLLM для каждой модели и локальную
карту `VLLM_ENDPOINTS`. Код backend одинаков для всех хостов.
Main хранит свою карту `modelId → URL inference-хоста`.

## Генерация на Mac или рабочей машине

Для DGX Spark:

```bash
make render-inference
```

Результат находится в `build/inference/dgx-spark/`. Для VM с одной MedGemma 4B:

```bash
make render-inference \
  INFERENCE_PROFILE=deploy/inference/profiles/medgemma-4b-amd64.json \
  INFERENCE_OUTPUT=build/inference/gpu-2
```

Новый хост получает свой профиль. Скопируйте подходящий пример и задайте
модели, архитектуру и доступные GPU. Параметры памяти в примере нужно проверить
на выбранной машине. Профиль amd64 использует образ, закреплённый по manifest
digest; этот генератор не выполняет проверку генерации на физическом GPU.

`render.py` использует стандартную библиотеку Python 3.10+. Он не подключается
к серверам, не читает секреты и не запускает Docker. Повторная генерация
обновляет производные файлы; `.env`, `secrets/`, `logs/` и веса сохраняются.

```text
docker-compose.yml            Compose в JSON-синтаксисе, совместимом с YAML
profile.json                  переносимая копия профиля
config/server.json            лимиты inference-сервиса
start.sh, start.py            последовательный запуск
host_profile.py               загрузка и проверка профиля
compose_document.py           проверка соответствия Compose профилю
.env.example                  пример машинных настроек
```

Редактируйте исходный профиль и генерируйте файлы повторно. Проверка без записи:

```bash
python3 deploy/inference/render.py \
  --profile deploy/inference/profiles/dgx-spark.json \
  --output build/inference/dgx-spark --check
```

Порядок записей в `models` задаёт порядок старта. `modelId` и `service` должны
быть уникальны внутри хоста. Для каждого движка задаются `dtype`, `maxModelLen`,
`maxNumSeqs`, `maxNumBatchedTokens`, `gpuMemoryUtilization`, `gpuDeviceIds`,
`tensorParallelSize`, `isEager` и `isPrefixCachingEnabled`. Дополнительно можно
задать `maxImages`, `kvCacheMemoryBytes`, закреплённую `revision` и собственный
`image`. `tensorParallelSize` должен совпадать с числом выбранных GPU.
Несколько движков могут использовать один GPU, как на DGX.

`vllmImage` и индивидуальные образы требуют digest. `weightsVolume` сохраняет
имя тома между генерациями; `isExternal: true` требует заранее созданного тома.
`serverConfig` — путь относительно исходного профиля. Генератор переносит этот
файл в каталог развёртывания. Профили содержат только несекретные параметры.

## Подготовка и запуск на GPU-хосте

Подготовьте Docker, NVIDIA Container Toolkit и Tailscale по руководству хоста.
Перенесите содержимое сгенерированного каталога в его каталог развёртывания,
например `/opt/doglyad/inference`. Для существующего стека сначала сохраните
прежние Compose, машинный `.env` и конфигурацию. Не удаляйте том весов.
При миграции задайте в профиле существующие имена Compose project, сервисов
и тома весов. Если `.env` содержит `COMPOSE_PROJECT_NAME`, он должен совпадать
с `projectName` профиля.

На новом хосте создайте `.env` по `.env.example` и заполните:

- `INFERENCE_BACKEND_IMAGE`: проверенный образ по digest; для локального
  переноса также допустим проверенный `sha256:...` image ID;
- `INFERENCE_BACKEND_BIND`: текущий результат `tailscale ip -4`;
- `INFERENCE_BACKEND_PORT`: порт приватного API, по умолчанию 8100.

Доставьте `secrets/.env` с HF_TOKEN и `secrets/firebase_credentials.json`
отдельно. Подготовьте права secrets/logs для UID/GID 10001 через
`deploy/prepare_backend_storage.py`, как в руководстве DGX. На существующем
хосте сохраните действующие секреты и `.env`. Параметры моделей теперь берутся
из профиля, а старые `VLLM_*` и `SERVED_MODEL_ID` в машинном `.env` не управляют
сгенерированным стеком. Не переносите в новый стек настройки чужого хоста.

Проверка синтаксиса не запускает контейнеры:

```bash
docker compose --env-file .env config --quiet
```

Проверенные файлы применяются отдельным действием:

```bash
bash start.sh
```

Скрипт проверяет архитектуру и приватный адрес API, сверяет Compose с профилем,
последовательно запускает движки с ожиданием `healthy`, затем пересоздаёт API.
Ошибка движка останавливает последовательность. `bash start.sh --restart`
сначала останавливает API и все движки из профиля. Такой запуск прерывает запросы.
Это процедура старта/изменения стека, а не обновление только backend.

Удаление модели из профиля не удаляет старый контейнер и веса автоматически.
Старые движки нужно остановить отдельно перед запуском изменённого стека.
Скрипт откажется запускать стек, если в его Compose project ещё работают
сервисы, отсутствующие в новом профиле.
Порядок загрузки после перезагрузки ОС требует настройки на уровне хоста;
`restart: unless-stopped` сам по себе не обеспечивает последовательный старт.

## Обновление backend через общий inventory

В `deploy/secrets/infrastructure.json` добавьте одну запись на стек:

```json
{
  "role": "inference",
  "ssh": "doglyad-spark",
  "directory": "/opt/doglyad/inference",
  "profile": "../inference/profiles/dgx-spark.json"
}
```

Путь `profile` задаётся относительно inventory. Архитектура, модели и имена
движков берутся из профиля; повторять `model` или `models` в записи нельзя.
Полный inventory по-прежнему содержит development и production main.
Старые записи с одним `model` и сервисом `vllm` поддерживаются. Один model ID
может принадлежать только одному target; балансировка реплик сюда не входит.

После применения сгенерированного стека используйте `make check-infrastructure`
и `make update-infrastructure`. Проверка сверяет профиль, маршруты работающего
backend и реальные model ID движков, их параметры запуска, образы, здоровье
и приватность портов.
Обновляется только `backend_inference`. ID, образы и счётчики перезапуска всех
vLLM должны сохраниться. Генерация отчёта этими проверками не выполняется.

Снимок обновления содержит нормализованный `target.json`, состояния всех
движков, `.env`, Compose, профиль и server config. Откат восстанавливает образ
backend и `.env`. Изменение файлов профиля во время обновления останавливает
автоматическое обновление/откат, чтобы не затереть другие изменения.
Изменение состава моделей применяется через генерацию и запуск, отдельно от
обновления backend. Main endpoint map обновляется отдельно при смене хоста модели.

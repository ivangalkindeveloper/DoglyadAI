# Регресс Doglyad

Все новые ресурсы мобильного регресса находятся в `test/`. Существующие unit-тесты
backend/iOS и длительные оценки моделей остаются в своих каталогах.

Сценарии разложены по модулям. [COVERAGE.md](COVERAGE.md) связывает описанные
шаги с Maestro и XCTest. Результаты исполнения находятся в
`build/regression/runs/<run-id>/report.json` и `index.html`.

Текущая платформа — **iOS**. Android-приложения ещё нет. Android не обозначается
как прошедшая платформа. При его появлении потребуется отдельный запуск эмулятора,
сборка APK, проверка селекторов и включение Android в общий барьер публикации.

## Состав и порядок

```text
test/
  modules/
    History/
      cases.yaml      # Действия, предусловия, результаты и статус автоматизации
      README.md       # Индекс сценариев модуля
      e2e/            # Исполняемые Maestro-кейсы
      atlas/          # Генерируемые снимки Preview
    TemplateAdd/
    SettingsAI/
    ScanSpeech/
    ...               # По папке для каждого модуля; сплеш хранится отдельно
  maestro/support/    # Общие шаги входа, навигации и подготовки данных
  functional.json     # Явный порядок исполнения, зависимости и профили подписки
  catalog.json        # Исходники, состояния, callback-методы и Preview
  COVERAGE.md         # Полнота описания и оставшиеся пробелы автоматизации
  CASES.md            # Ссылки на исполняемые YAML
  fixtures/           # Синтетические данные только для изолированного стенда
  secrets/config.local.json # Локальные пути, симулятор и цель Figma
  secrets/.env        # Локальный App Check токен; вся папка исключена из Git
  secrets/figma-bridge-key # Автоматический локальный ключ подключения плагина
  scripts/, checks/   # Запуск, отчёты, проверки публикации
  figma/              # Development-плагин Figma
```

Результаты находятся отдельно: `build/regression/runs/`. Исходники iOS —
в `ios/Doglyad/Regression/`, `ios/DoglyadTests/Regression/` и `ios/DoglyadUITests/Regression/`.

`functional.json` задаёт порядок функциональных кейсов, их зависимости,
подготовку данных и обязательные проверки. `catalog.json` генерируется из кода:
он содержит Preview, состояния, действия модулей и контрольные суммы исходников.
Runner читает оба файла; каталог также помогает обнаружить изменения приложения,
после которых нужно обновить кейсы.

`COVERAGE.md` — генерируемая карта описанных сценариев и связей с Maestro/XCTest.
`COVERAGE-GAPS.md` перечисляет оставшиеся пробелы автоматизации. Это не измерение
покрытия строк кода и не результат исполнения. Машинные результаты каждого запуска
находятся в `build/regression/runs/<run-id>/report.json`. Публикация проверяет по ним
полноту набора, JUnit, снимки и доказательства работы backend. `index.html` даёт
локальную галерею, показывает неуспешные кейсы и содержит ссылки на их логи.

`config.example.json` нужен только для первичной настройки нового компьютера.
Runner его не читает и не заменяет им локальные настройки. Содержимое `.env`
для первоначальной настройки приведено ниже; env-файлы, включая примеры,
исключены из Git во всём проекте.

`cases.yaml` — описание функциональных сценариев, а не файл Maestro. Каждый
шаг содержит действие и наблюдаемый результат. В `automation.flows` указаны ID
реальных Maestro-кейсов из `functional.json`.

- `maestro`: связанные flows реализуют описанные шаги. Это ещё не результат запуска.
- `mixed`: шаги покрыты flows и обязательными проверками XCTest из `automation.nativeTests`.
- `partial`: часть шагов автоматизирована; оставшиеся перечислены в `requires`.
- `manual`: сценарий описан, но для исполнения нужен человек или отсутствующий адаптер стенда.

Внутри настроек порядок соответствует интерфейсу: история → шаблоны → рабочие
настройки → AI → подписка → хранилище → документы → о приложении. Создание,
изменение, применение и удаление шаблонов находятся рядом. Общие селекторы AI
имеют собственные папки модулей, но исполняются в блоке настроек AI.

Подготовка данных может предшествовать блоку: пустая история проверяется до
первой генерации. Для пагинации тестовая сборка сохраняет 41 протокол через
настоящий SwiftData-репозиторий. Проверяются три страницы, все номера, число
загруженных записей, группы «Сегодня», «Вчера», 02.01.2020 и перезапуск.
Генерация через локальный backend проверяется отдельными функциональными кейсами.
Зависимости явно указаны в `dependsOn`; валидатор проверяет порядок.

`modules/*/atlas/` и `ios/Doglyad/Regression/RegressionScreens.swift` генерируются из существующих
`*Preview.swift`. Они проверяют отображение состояния, а не переход в него.
Каждый Preview в каталоге модуля называется `"{номер} {название}"`, например
`"01 OnBoardingInitialState"`. Нумерация начинается с 1 и идёт без повторов и
пропусков. Сначала идут состояния всего модуля по ходу работы пользователя,
затем компонентные Preview для Xcode Canvas. В atlas и Figma попадают только полноэкранные Preview модулей. Ошибки и альтернативы стоят рядом с соответствующим
шагом. Генератор проверяет номера и сортирует их как числа; перестановка номера
не меняет стабильный ID кейса. Порядок объявлений в Swift соответствует номерам.
`functional.json.moduleOrder` задаёт порядок просмотра: первый запуск, затем
переходы с основного экрана сверху вниз и слева направо. Каждый модуль показан
один раз, у первого места входа. Сначала идут сплеш и ошибки инициализации, затем обновление версии и легальных
документов, onboarding и обычная навигация. Исполнение функциональных кейсов сохраняет отдельный порядок подготовки
данных и зависимостей; внутри строки модуля снимки регресса идут по шагам сценариев.
Тестовая точка входа включается только флагом `DOGLYAD_REGRESSION` в DEBUG.
Файлы `ios/Doglyad/Regression/` обеспечивают эту сборку:

- `RegressionApplication` и генерируемый `RegressionScreens` открывают обычное
  приложение или выбранный Preview по аргументу Maestro. Обёртки нужны, чтобы
  снять Preview в симуляторе вне Xcode Canvas.
- `RegressionFixtures` подготавливает данные. Генерируемые адаптеры репозиториев
  вызывают заданную ошибку один раз, затем обращаются к настоящему репозиторию.
- `RegressionSpeechController`, `RegressionExternalActions` и
  `RegressionConfiguration` управляют речью, внешними действиями и проверкой
  обновления приложения. Платежи этими адаптерами не заменяются.

Native-тесты находятся в `ios/DoglyadTests/Regression/`. Проверки жестов,
которые управляют приложением через XCTest UI, находятся в `ios/DoglyadUITests/Regression/`.

Эти файлы исключены из обычной сборки условием `DEBUG && DOGLYAD_REGRESSION`.

Селекторы используют идентификаторы и признаки выбранных элементов доступности.
Клавиатура закрывается кнопкой приложения `keyboard.done`. Регрессионная сборка
не показывает автоматическое приглашение оценить приложение в App Store:
это системное окно иначе перекрывает форму после первой генерации.
Обычные сборки сохраняют приглашение. Проверка самого окна оценки в набор не входит.

В iOS 26.5 Maestro получает только первые 512 символов длинных многострочных
полей Scan. Кейс DEV-заполнения проверяет этот префикс фикстуры до и после
возврата из настроек. Он не подтверждает сохранность остальной части текста.
Кейс черновика отдельно проверяет полные значения шести коротких полей после
перезапуска. Кейс очистки требует появления подсказок пустых полей.

Сборка `DEBUG && DOGLYAD_REGRESSION` задаёт витрину `RUS` в фабрике подписок.
Так русский набор проверяет каталог и выбор планов Robokassa, полученных от
локального backend. Чистому симулятору не нужен аккаунт App Store.
Это тестовая фикстура выбора провайдера: она не подтверждает определение
реальной витрины или загрузку тарифов StoreKit. Для них нужны отдельные
Apple Sandbox/StoreKit-сценарии. Начальные кейсы Paywall ждут доступную кнопку
продолжения после загрузки тарифов; одного заголовка для успеха недостаточно.

## Подготовка Mac

1. Установите Xcode с iOS Simulator и Docker Desktop. Запустите Docker.
2. Установите [Maestro CLI](https://docs.maestro.dev/get-started/installing-maestro)
   по его официальной инструкции. Проверьте `maestro --version`; для стандартной
   установки можно вызвать `~/.maestro/bin/maestro --version`.
   Скрипт ищет Maestro сначала в `PATH`, затем в `~/.maestro/bin/maestro`.
   Поэтому стандартная установка доступна регрессу и без изменения `PATH`.
3. Установите зависимости скриптов: `python3 -m pip install -r test/requirements.txt`.
4. Создайте папку `test/secrets/`. Скопируйте `test/config.example.json` в
   `test/secrets/config.local.json`. Относительные пути внутри конфига считаются
   от корня репозитория.
5. Укажите `firebaseCredentials`: путь к существующему service account
   **development-проекта Firebase**. Сам файл и `config.local.json` не коммитятся.
6. Проверьте наличие `ios/Firebase/Debug-Local/GoogleService-Info.plist`
   и локальной конфигурации Xcode. Используются настройки существующего проекта.
7. В Firebase Console → App Check → приложение development → Manage debug tokens
   зарегистрируйте debug token. Укажите его в игнорном
   `ios/Config/Config.Local.xcconfig`:

   ```xcconfig
   APP_CHECK_DEBUG_TOKEN = ваш_зарегистрированный_токен
   ```

   Этого достаточно для Local-приложения и регресса. Xcode подставляет токен
   в `Info.plist` приложения `Debug-Local`. Клиент передаёт его в
   `AppCheckDebugToken` перед инициализацией Firebase. Для Development и Production
   настройка принудительно пуста; клиент её не использует.
   Предварительная проверка читает настройки через Xcode,
   не выводит токен и не сохраняет его в отчёт.

   Для отдельного токена регресса можно переопределить значение в
   `test/secrets/.env`:

   ```dotenv
   REGRESSION_APP_CHECK_DEBUG_TOKEN=ваш_зарегистрированный_токен
   ```

   Скрипт автоматически читает этот файл при `make regression-doctor`,
   `make regression` и `make regression-figma`. Выполнять `export` или `source`
   не требуется. Переменная, уже заданная в окружении процесса, имеет приоритет.
   Это переопределение имеет приоритет над iOS-конфигом. Если переменная
   отсутствует или пуста, регресс использует токен из iOS-конфига.
   Вся папка `test/secrets/` исключена из Git и расчёта хеша тестового набора.
   Значения из `.env` не выполняются как shell-команды и не подставляют другие
   переменные. Не помещайте токен в YAML, `Makefile`, исходники или отчёт.
8. Выполните `make regression-doctor`.

App Check остаётся включённым. При переопределении токен передаётся в окружение
только нового симулятора; иначе клиент читает его из своей Local-сборки.
При первом запуске приложение получает настоящие каталоги через
защищённые API. Проверка готовности сервера ожидает отказ без App Check;
доступ с действительным токеном проверяет вводный UI-сценарий.
Скрипт ждёт готовности до 120 секунд. Закрытое соединение, сброс соединения
и сетевой таймаут во время старта приводят к повторной попытке. Если сервер
не стал готов, ошибка содержит результат последней попытки; логи контейнеров
сохраняются в `services.log` текущего прогона.

## Тестовый магазин Робокассы

Новая оплата использует HTTPS checkout и подписанный ResultURL. Старые Maestro
сценарии SDK удалены из исполняемого набора. Покупка, банковское подтверждение,
отказ и восстановление после настоящей покупки отмечены как manual/partial в
модульных cases.yaml. Нужны подключённый тестовый магазин, публичный callback и
проверка селекторов браузера на устройстве. Это не пройденные E2E-тесты.

Для стенда предусмотрены `robokassaCredentialsFile`, тестовые
`ROBOKASSA_MERCHANT_LOGIN`, `ROBOKASSA_PASSWORD1`, `ROBOKASSA_PASSWORD2`.
`ENVIRONMENT=development` и `IS_ROBOKASSA_LIVE_ENABLED=false` обязательны.
Подпись успешного callback проверяет настоящий backend; OpStateExt для тестовых
платежей недоступен. SQL-профиль не подтверждает покупку.

## Данные Preview и управляемые ошибки

`test/fixtures/development/{ru,en}.json` формируются теми же методами backend,
которые собирают ответы конфигурации, локализации, типов исследования, моделей,
готовых шаблонов и тарифов. `catalog.py` обновляет эти файлы; `--check` обнаруживает
расхождения. Preview читает их без сети и использует весь каталог Development.
Полный функциональный прогон выполняется на русском: симулятор использует
`AppleLanguages = ru` и `AppleLocale = ru_RU`. Две фикстуры не означают два прогона.
Все зарегистрированные Preview показывают интерфейс на русском языке. Их названия
используют формат `01 MenuContentState HistoryCountAvailable`: реальный класс
состояния и английский сценарий с его внутренними значениями. Английские
варианты интерфейса удалены. Фикстура `en.json` остаётся для unit-тестов локализации;
она не создаёт английских экранов в визуальной коллекции.
Фото берётся из `SimulatorCameraImageFactory`, как при съёмке в симуляторе.
PhotoView без фото закрывается; отдельного пустого Preview нет.
WebDocument использует полные текущие страницы из `docs/legal/`: политику
конфиденциальности и условия использования. Генератор встраивает их CSS, шрифты
и скрипт для офлайн-просмотра; снимок готового документа ждёт завершения загрузки WKWebView.

Ошибки, которые приложение показывает через DMessager, имеют постоянный баннер
в Preview. Maestro требует его появления до снимка.

`ios/Doglyad/Regression/RegressionRepositoryAdapters.swift` генерируется из протоколов репозиториев.
Только сборка `DEBUG && DOGLYAD_REGRESSION` умеет один раз отклонить заданную операцию
через аргумент `regressionFault`. Повтор вызывает настоящий репозиторий.
Это позволяет проверить сохранность ввода и повтор после ошибки. Платёжные
репозитории такими адаптерами не заменяются. Все аргументы Maestro для iOS
записываются строками: иначе они не попадают в `UserDefaults`.
`regressionFaultModule` ограничивает ошибку задачами `onInit` указанного ViewModel.
Например, `MenuViewModel` позволяет проверить счётчик истории без зависимости
от порядка фоновых запросов при запуске приложения. Повтор читает реальный репозиторий.
Проверка `TemplateEdit` сначала выбирает шаблон в Scan и ограничивает сбой его
экраном редактирования. Чтение выбранного шаблона при запуске остаётся успешным.

Перед Maestro запускаются точные проверки из `test/scripts/native_checks.py`.
XCTest проверяет двойное нажатие, pinch, pan и возврат к исходному масштабу
для горизонтального, вертикального и квадратного фото. Каждое утверждение относится
к одному ID снимка. Maestro на этом симуляторе нестабильно воспроизводит двойное
нажатие; проблема раздельных событий описана в
[обсуждении Maestro](https://github.com/mobile-dev-inc/Maestro/pull/3586).
Maestro проверяет выбор снимка по явному номеру, переходы, порядок и лимит галереи.
XCTest также проверяет быстрый повтор захвата, поздний ответ
камеры и смена данных PhotoView. Пустой запуск, пропуск или сбой XCTest блокирует
публикацию. Полный результат хранится в `native-tests.xcresult`, проверенное
подтверждение — в `native-checks.json`. Длительные оценки речи не запускаются.

`RegressionSpeechController` подаёт известный транскрипт вместо микрофона.
Разбор через локальный backend и применение полей остаются обычными.
`regressionSpeech` задаёт подготовку с ошибкой, обзор предложений или пустую запись.
`regressionDelay` однократно задерживает выбранную операцию репозитория на 5 секунд.

Для проверки хранилища `regressionSeedSpeechModel` создаёт маленькую структуру файлов
WhisperKit. Удаление выполняет обычный `DSpeechWhisperKitModel`. Режим
`regressionSpeech: cached-model` показывает готовность только при наличии этих файлов;
после удаления он показывает необходимость загрузки. Качество распознавания и загрузка
настоящих весов в этот сценарий не входят.

XCTest также проверяет границы ввода, клавиатурный фокус, смену возможностей устройства
и подписки, сохранение настроек, жизненный цикл генерации и сбой чтения выбранного фото.
Семь снимков камеры Simulator добавляются в системную галерею перед Maestro.
В iOS 26.5 Simulator кнопка перехода в настройки открывает их корень. Maestro проверяет
этот переход, меняет реальные разрешения TCC и перезапускает процесс: без перезапуска
AVFoundation продолжает возвращать закешированный отказ. Это ограничение Simulator;
прямой переход в карточку приложения на физическом iPhone здесь не проверяется.
Сценарии очистки сравнивают строки локальной БД и настройки до и после действия;
подтверждения `local-evidence.json` обязательны для публикации.

Контейнер `mail` принимает письма локально через STARTTLS и SMTP AUTH.
Сценарий отправки сверяет адресата, текст с буфером Simulator, JPEG-вложение и
единственный успешный повтор после отказа SMTP. Подтверждение сохраняется в
`delivery-evidence.json` и проверяется перед публикацией.

`report-evidence.json` связывает буфер обмена с точной сохранённой версией ответа модели.
Проверка повторной генерации требует неизменных данных исследования и фото, сохранности
предыдущих ответов и ожидаемого числа успешных и неуспешных попыток. Снимок экрана сам
по себе эти проверки не заменяет. Системное письмо сравнивается с полным письмом, ранее
принятым локальным SMTP. При ограничении Base запрос отправки не должен доходить до API.

Только регрессионный Compose запускает backend через `test/backend/observed_main.py`.
Этот ASGI-обработчик передаёт запросы и ответы без изменений в настоящее приложение.
App Check и остальные проверки backend остаются обязательными.
Наблюдатель сохраняет выбранные поля запросов генерации и разбора, а также снимки
состояния задания. Он не сохраняет заголовки, платёжные запросы и байты фотографий.
Результаты лежат в `backend-evidence/` внутри прогона. Проверки `backendAssertions`
сверяют их с ожидаемыми параметрами и завершённой записью PostgreSQL.
Для рекомендаций и замечаний также проверяется фактический состав ответа.
Перед публикацией подтверждение `backend-evidence.json` должно оставаться неизменным.

`test/backend/controlled_worker.py` запускает настоящий worker с однократным
управлением только локальной моделью. Поле `backendAssertions.worker` задаёт номер
исследования и режим: ошибка до текста, ошибка после частичного ответа или задержка
завершения. Первый подходящий job забирает команду; повтор получает обычный ответ
mock-модели. Проверка связывает команду с ID задания, проверяет состояния обеих
попыток, доставленный частичный ответ и неизменность данных исследования.
`localAssertions.countDelta` подтверждает, что повтор не создал второй отчёт.
Эти механизмы не изменяют App Check, оплату или правила выдачи доступа.

Скрипт создаёт временный сертификат в игнорной папке `test/secrets/` и добавляет его
к доверенным сертификатам только тестового контейнера. Проверка TLS остаётся включённой.
Письма не пересылаются наружу. После прогона контейнер, письма и сертификат удаляются.

Готовность пациента проверяется как отдельный флаг `isPatientPreparedForExamination`:
переключатель Scan, черновик, сохранённый отчёт и JSON запроса сохраняют в том числе
`false`. Диктовка меняет флаг только по явной фразе о подготовке пациента; отсутствие
упоминания, вопрос, условная или противоречивая фраза не устанавливают готовность.
Надёжность распознавания управляет автоматическим применением и подтверждением.
Нативные проверки обоих путей разбора используют сохранённые ответы без запуска
моделей; это не оценка качества ASR или генерации медицинских замечаний.

## Запуск

Если нужны только актуальные Preview, используйте отдельный режим:

```sh
make previews                  # Все русские Preview без backend и БД
make previews-figma            # Затем обновить только раздел «Макеты» в Figma
make previews-publish RUN=build/previews/runs/<run-id> # Повторить передачу готовых снимков
```

Он собирает тестовую iOS-сборку и снимает все зарегистрированные Preview на
отдельных симуляторах. По умолчанию работают два симулятора. Функциональные
сценарии, серверные контейнеры и покупки не запускаются. Результаты находятся
в `build/previews/runs/`, подтверждение исполнения — в `preview-report.json`.
Публикация требует успеха всех Preview, наличия всех снимков, неизменности
JUnit/PNG и удаления созданных симуляторов. Это не результат полного регресса.
Прокручиваемые состояния имеют соседний вариант `ScrollEnd` с теми же данными.
Он показывает конец содержимого в Canvas и на снимке. Перед снимком Maestro ждёт
`preview.scrollEnd.ready`: фактическое смещение, размер содержимого и нижние отступы
должны стабилизироваться. Это касается и HTML-документов; поля ввода и горизонтальные
ленты фотографий не прокручиваются вместо основного вертикального списка.

Каталог включает только полноэкранные Preview модулей: экраны, шторки, сплеш и ошибки инициализации.
Компонентные варианты из модульных каталогов и общие компоненты из
`ios/Doglyad/Application/Application/View/Preview/` остаются в Xcode Canvas.
Они не создают atlas-кейсов, не выполняются в регрессе и не загружаются в Figma.
Публикация отклоняет наборы с компонентными кейсами; после изменения этой политики
нужно снять актуальный каталог, а не переиспользовать старый смешанный набор.

В Figma заменяется только раздел «Макеты». Снимки регресса, его подписи и ручные
заметки сохраняются. После обновления кода плагина его окно нужно переоткрыть.

```sh
make regression-check
make regression                 # Прогон и локальная HTML-галерея
make regression-figma           # Прогон, затем обновление Figma
```

Каждый запуск получает новый Compose project, собственный volume PostgreSQL и
новый iOS Simulator. Миграции применяются до старта API. После вводного сценария
SQL-фикстуры `fixtures/subscriptions/` задают профиль единственного тестового
владельца перед кейсом: `none`, `base`, `pro`, `expired`, `revoked` или `exhausted`. Смена профиля
не очищает историю клиента. Это подготовка UI-проверки, а не подтверждение покупки.
Внешние платёжные E2E теперь требуют стенда Робокассы и отдельно проверенных
браузерных шагов. Они обозначены в модульных сценариях как manual/partial;
никакой успех покупки из SQL-фикстур не выводится. Чистые владельцы для Base/Pro,
подпись ResultURL, сумма, planId, повтор, отмена, оплаченный период и перенос
по ключу должны быть проверены перед возвратом этих кейсов в исполняемый набор.
Apple Sandbox остаётся отдельной проверкой.

Почтовый клиент и App Store в симуляторе заменяет отдельный тестовый адаптер.
Он проверяет открытие и отмену внешнего приложения без отправки письма.
`external-evidence.json` подтверждает адрес назначения и параметры URL.
Этот адаптер не участвует в оплате Robokassa. Для проверки NewVersion меняется
только `actualVersion` после настоящей загрузки Development-конфигурации с App Check.
Проверяется блокировка для новой major-версии и отсутствие блокировки для minor-версии.
Генерацию обслуживает существующий `MODEL_SERVICE_TYPE=mock`; App Check остаётся включённым.


Backend доступен только на `127.0.0.1:18765`. Существующие локальные контейнеры,
БД на порту 5433, приложение и симуляторы разработчика не очищаются. Если порт
занят, команда завершится с ошибкой. После запуска удаляются только созданные
этим запуском симулятор и Compose volume. Отчёт остаётся в `build/regression/runs/`.
Кеш сборки переиспользуется; данные приложения, Keychain и БД создаются заново.
API и worker используют `restart: unless-stopped`, как в основном Compose.
После временного сбоя БД завершившийся worker запускается снова.

На сборку backend выделен **1 час**. При необходимости задайте
`"backendBuildTimeoutSeconds": 7200` в `test/secrets/config.local.json` для двух часов.
Этот параметр относится только к сборке образов; запуск контейнеров и UI-тесты
имеют свои таймауты. Конфиг `config.local.json` без этого поля использует 3600 секунд.

Сборка и запуск контейнеров выполняются отдельно. Каждые 15 секунд долгий этап
показывает прошедшее время, размер лога и время с его последнего обновления.
Полный вывод Docker находится в `build/regression/runs/<run-id>/environment.log`;
вывод Xcode — в `build.log` того же запуска.

BuildKit хранит кеш пакетов pip отдельно от контейнеров и данных PostgreSQL.
Полностью скачанные пакеты можно использовать при повторной попытке после
прерванной установки. При неизменённых зависимостях Docker переиспользует готовый
слой установки целиком. Если слой нужно пересобрать, pip использует накопленный
кеш. Очистка прогонов этот кеш не удаляет; очистка кеша Docker или смена builder
может потребовать новых загрузок. Подробности: [Docker cache mounts](https://docs.docker.com/build/cache/optimize/#use-cache-mounts).

Сценарии выполняются по порядку из `functional.json`, затем из `catalog.json`.
Вводный flow находится в `modules/OnBoarding/e2e/bootstrap.yaml`.
Он сначала снимает настоящий `ApplicationSplashView`. Только в тестовой сборке
начало инициализации удерживается до снимка; тестовое нажатие на сплеш разрешает
её продолжить. После этого тестовый обработчик отключается. Перед снимком onboarding сценарий ждёт исчезновения сплеша и
завершения анимации. Отдельный Preview сплеша использует тот же `ApplicationSplashView`.
Создание шаблона предшествует его открытию и удалению; очистка истории идёт после
генерации. Вводный сценарий служит обязательной подготовкой всего набора.
На первой ошибке запуск останавливается. Невыполненные кейсы делают весь прогон
неуспешным, даже если выполненные кейсы прошли.

Сборка и установка приложения выполняются один раз на весь прогон. Каждый кейс
вызывается отдельной командой Maestro и перезапускает приложение через `launchApp`.
Некоторые функциональные кейсы дополнительно перезапускают его для проверки
сохранения данных. Данные приложения и БД между кейсами сохраняются; чистое
окружение создаётся только в начале всего прогона. Поэтому функциональные кейсы
с зависимостями выполняются в заданном порядке.
После появления главного экрана общий сценарий ждёт окончания анимации перед
нажатием. Сценарии разрешений делают то же после каждого дополнительного запуска:
видимая кнопка ещё может перемещаться, а её промежуточные координаты дают промах.
Для каждого вызова Maestro скрипт выбирает свободный порт драйвера в диапазоне
22087–32767 через `--driver-host-port`. Это исключает пересечение со стандартным
диапазоном временных TCP-соединений macOS 49152–65535 во время запуска XCTest.
Занятые порты пропускаются; чужие процессы не останавливаются. Выбор случайного
порта в [Maestro](https://github.com/mobile-dev-inc/Maestro/blob/main/maestro-cli/src/main/java/maestro/cli/command/TestCommand.kt)
освобождает его до запуска драйвера, поэтому порт может занять другое соединение.

## Подключение Figma один раз

1. Создайте отдельный **Figma Design** файл для регресса и получите право редактирования.
2. Скопируйте ключ из URL `https://www.figma.com/design/<FILE_KEY>/...`
   в `figmaFileKey` файла `test/secrets/config.local.json`. `figmaPageName` задаёт префикс
   названия коллекции; существующие страницы не переименовываются.
3. В Figma Desktop создайте development-плагин через меню Plugins → Development.
   Скопируйте присвоенный ему `id` в конфигурацию локального плагина:

   ```sh
   python3 test/scripts/configure_figma.py <PLUGIN_ID>
   ```

4. Импортируйте **`test/cache/figma-plugin/manifest.json`** через **Import plugin from manifest**.
   Figma требует точное имя `manifest.json`. Скрипт помещает рядом готовые
   `code.js` и `ui.html`; сборка TypeScript не нужна. При первом запуске он
   также может перенести ID из прежнего `test/figma/manifest.local.json`.
   Сам импорт регистрирует плагин, но не открывает его окно. Затем выберите
   **Plugins → Development → Doglyad AI Regression**. Если показаны сообщение
   об автоматическом обновлении и кнопка «Проверить сейчас», подключён нужный плагин. Ошибка «This plugin template
   uses TypeScript» означает, что запускается шаблон, а не подготовленный каталог.
   Сервер передачи обновляет локальные копии кода при каждом запуске.
   Проверка SHA-256 встроена в HTML через локальную копию `js-sha256` с MIT-лицензией.
   Она работает и в окне Figma без `crypto.subtle`; загрузка библиотеки из сети не нужна.
   Включён
   `enablePrivatePluginApi` для чтения ключа файла локальным development-плагином.
   Это предусмотрено [манифестом Figma Plugin API](https://developers.figma.com/docs/plugins/manifest/).
5. Оставьте плагин открытым в выбранном файле. Запустите `make regression-figma`.
   После успешных тестов плагин сам загрузит изображения. Он проверяет наличие
   готового прогона каждые 5 секунд. Кнопка «Проверить сейчас» запускает проверку
   сразу; нажимать её для обычного обновления не требуется.

После обновления кода плагина закройте и снова откройте его окно один раз.
Дальнейшие прогоны загрузятся без ввода токенов и нажатия кнопок, пока окно открыто.
Если редактор или плагин закрыт, его нужно открыть. Без разрешения на управление
приложениями агент не может выполнить этот шаг за пользователя.

Во время самого регресса плагин может быть закрыт. Для импорта редактор и плагин
должны быть открыты до сообщения «Обновлено … снимков»; затем их можно закрыть.
Обычного REST-запроса для
создания фреймов нет. Плагин подключается к `http://localhost:8765`, а сервер
слушает только `127.0.0.1:8765`. В манифесте используется `localhost`:
валидатор Figma отклоняет IP-адрес в `devAllowedDomains`. Облачного
посредника и персонального API-токена Figma нет. Если Figma запросит доступ к
локальной сети, разрешите его этому development-плагину.

Скрипт сам создаёт постоянный случайный ключ в `test/secrets/figma-bridge-key`
и встраивает его только в игнорный `test/cache/figma-plugin/ui.html`. Оба файла
имеют права `0600`. Сервер по-прежнему отклоняет запросы без этого ключа.
Ключ не выводится в лог и не попадает в исходники, отчёт или хеш набора тестов.
Чтобы сменить его, удалите `test/secrets/figma-bridge-key`, выполните
`python3 test/scripts/configure_figma.py` и перезапустите окно плагина.

Страница регресса полностью заменяется при успешной публикации полного регресса, включая ручные
заметки и другие объекты на ней. Сначала плагин получает и проверяет все снимки,
затем очищает страницу и показывает новый набор с позиции `(0, 0)`.
При ошибке тестов или незавершённой передаче страница не очищается.
Другие страницы файла сохраняются. Первый импорт использует текущую страницу;
дальнейшие используют страницу с отметкой плагина. Новая страница не создаётся,
поэтому импорт работает при лимите страниц Starter.
Вверху находятся **Макеты**, затем отступ 1920 px и **Регресс**.
В каждом разделе у модуля своя горизонтальная строка с заголовком.
Между снимками 20 px, между группами 40 px. Фреймы без заливки; заголовки
разделов и названия модулей белые. Цвета самих снимков сохраняются.
Изображения обрезаются по непрерывному контуру экрана iPhone 17. Источник геометрии —
маска `4E5532ED-1470-47D1-BDF4-7AA90C26957A` из профиля iPhone 17 в Xcode CoreSimulator,
1206 × 2622 px. Контур масштабируется вместе со снимком; Dynamic Island не добавляется.
При обновлении Preview эта форма применяется также к уже загруженным снимкам в
управляемом разделе «Регресс», сохраняя их изображения, порядок и фреймы сценариев.
Исходные PNG и результаты проверок остаются неизменными. Для обновления формы
можно повторно опубликовать готовый успешный набор без новой съёмки.
Новые прогоны называются по времени старта в UTC: `YYYYMMDDTHHMMSSZ`, без случайного
суффикса. Одновременный запуск блокируется; существующая папка никогда не перезаписывается.
Старые папки и отчёты сохраняют свои ID, но Figma скрывает прежний случайный суффикс.
Название коллекции содержит префикс, время старта и число сценариев с неполной
автоматизацией. Платформа и количество исполняемых кейсов в название не добавляются.
Полный список оставшихся проверок: [COVERAGE-GAPS.md](COVERAGE-GAPS.md).
Порядок модулей задан в `functional.json`, сплеш идёт первым.
Preview внутри модуля идут по числовому префиксу названия, снимки регресса —
по порядку шагов сценариев. Порядок прихода изображений не влияет на раскладку.
Источник задаётся разделом «Макеты» или «Регресс».
У названий фреймов и слоёв изображений нет префикса «Preview». Над отдельными экранами нет текстовых подписей: английское имя состояния и сценария записано в имени фрейма и изображения, поэтому все изображения в строке выровнены по верхнему краю. Имя модуля берётся из самого снимка, даже если сценарий
прошёл несколько экранов.
При повторной публикации исторического прогона его английские Preview скрываются
в коллекции. Все исходные снимки передаются и проверяются; отчёт исполнения
остаётся неизменным. Подтверждение Figma отдельно указывает число видимых снимков.
Полный архив предыдущих прогонов остаётся на диске.

Успешная передача подтверждается `figma-receipt.json` с ID прогона, файла,
фрейма и числом изображений. Если ожидание Figma завершилось по таймауту:

```sh
make regression-publish RUN=build/regression/runs/<run-id>
```

Команда принимает только полностью успешный прогон с неизменёнными снимками.
Повторять тесты для повторной передачи того же успешного результата не требуется.

## Условие публикации

Публикация разрешена только когда одновременно выполнены все условия:

- Выполнен весь зарегистрированный набор без фильтрации.
- Каждый процесс Maestro вернул 0; его JUnit содержит ожидаемый кейс без
  `failure`, `error` или `skipped`. Пустой JUnit не считается успехом.
- Для каждого кейса найден ровно один PNG каждого ожидаемого снимка.
- Исходники и тестовые ресурсы не изменились во время запуска.
- Очистка созданного окружения завершилась успешно.

Сценарии `partial` и `manual` остаются видимыми пробелами покрытия. Они не
считаются пройденными, но не блокируют передачу успешно исполненного набора.

Только тогда записывается `publication.json`. Сервер повторно проверяет JUnit и
SHA-256 снимков. Плагин сначала получает все изображения и сверяет хеши, затем
заменяет старый набор. Ошибка теста или передачи не обновляет коллекцию Figma.

## Покрытие и ограничения

Текущие числа и ссылки находятся в [COVERAGE.md](COVERAGE.md) и [CASES.md](CASES.md).
Описаны действия всех найденных модулей: ввод и валидация, сохранение, отмена,
ошибки и повтор, подписки, медиа, голос, документы и доставка результата.
Проверка связи с callback-методами помогает заметить новый необработанный сценарий.
Она не измеряет покрытие ветвей кода и не доказывает отсутствие других пробелов.

Автоматизированная часть расширена: все восемь сочетаний рабочих переключателей,
границы температуры/токенов, Markdown, выбор опубликованных моделей, сохранение
WhisperKit и серверного парсера, применение готового шаблона, история и её подгрузка, разные
профили подписки и выбор всех восьми планов текущего каталога. Недоступные функции
не пропускаются с успехом. Требования Apple engine, Foundation Models, Sandbox,
SMTP, камеры и инъекции ошибок указаны в конкретных модульных сценариях.

Текущие модульные сценарии автоматизированы в описанных границах локального стенда.
`make regression` запускает зарегистрированные flows и сохраняет локальные результаты.
Если появляются `partial` или `manual`,
отчёт сохраняет `status: incomplete` для покрытия. Preview не закрывают
отсутствующий E2E-кейс.
Результат исполнения записывается отдельно в `executionStatus`. Команда
`make regression` возвращает код 0, только если прошли все зарегистрированные
кейсы, собраны все снимки и успешно завершена очистка окружения. Неполное
покрытие явно указано в отчёте и выводе команды. Публикация проверяет
`executionStatus: passed`, весь набор JUnit и все обязательные снимки.
Манифест передачи содержит `status: passed` и отдельный `coverageStatus`;
число неавтоматизированных сценариев остаётся в названии коллекции Figma.
Ранее успешный прогон можно передать через `make regression-publish`: сервер
повторно проверит его JUnit и хеши PNG, затем создаст манифест передачи.
Исходный `report.json` при этом не изменяется. Покупки, камера и другие
пробелы покрытия от такой передачи не становятся проверенными.
Для подключения сценария нужно реализовать все шаги и проверки, связать flows,
а затем изменить статус автоматизации. Нельзя менять статус ради публикации.

Выбор тарифов проверяется отдельно от покупки. Провайдерные E2E-кейсы браузерной оплаты требуют тестового магазина и ручной
проверки; SQL-профили не подтверждают оплату.
Apple Sandbox исключён. Качество AI/ASR и работа физических камеры и микрофона
не входят в этот локальный прогон. Для речи и внешних приложений используются
явно указанные тестовые адаптеры. Матрица описана рядом с каждым модулем.

Сгенерированный YAML, описание сценария и успешная сборка не доказывают прохождение
UI-теста. Результаты каждого запуска сохраняются в `build/regression/runs/`.

## Обновление кейсов

Используйте `$test-regress-update`. Изменённые исходники сначала нужно
сопоставить с функциональными YAML. Затем обновите каталог:

```sh
python3 test/scripts/catalog.py
python3 test/scripts/scenario_coverage.py
make regression-check
python3 -m unittest discover -s test/checks -p 'test_*.py'
node --test test/checks/figma*.test.js
```

Генератор обновляет atlas и Swift-каталог. Он не заменяет семантический разбор
действий пользователя и не переписывает функциональные утверждения автоматически.
Изменения маршрутов, состояний, API, локализации и UI обнаруживаются через хеши.
Частичный набор нельзя публиковать под видом полного регресса.

Проверка компиляции тестовой сборки без запуска стенда:

```sh
xcodebuild build -project ios/Doglyad.xcodeproj \
  -disableAutomaticPackageResolution -skipPackageUpdates \
  -scheme Doglyad-Debug-Local -destination 'generic/platform=iOS Simulator' \
  -derivedDataPath test/cache/DerivedData \
  'OTHER_SWIFT_FLAGS=$(inherited) -DDOGLYAD_REGRESSION' \
  'BASE_URL=http://127.0.0.1:18765' ONLY_ACTIVE_ARCH=YES ARCHS=arm64
```

На Intel Mac выберите соответствующую архитектуру. Не заменяйте
`SWIFT_ACTIVE_COMPILATION_CONDITIONS`: это может удалить `SWIFT_PACKAGE` у
зависимостей. Не запускайте обычную сборку с флагом `DOGLYAD_REGRESSION`.

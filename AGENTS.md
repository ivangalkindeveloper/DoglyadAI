# Doglyad — AI assistant for ultrasound examination analysis

Doglyad is an AI assistant that analyzes ultrasound images together with patient history and generates a medical report.

## Session communication

- **Required skill:** Read [asd-ste100](harness/skills/asd-ste100/SKILL.md) once at the start of each session. Apply it throughout the session to progress updates, plans, questions, explanations, reviews, and final answers. Do not wait for a separate request to simplify text.
- **Language:** Use Russian by default. Follow the user's explicit language choice. Apply these communication rules to both Russian and English.
- **Standard and adaptation:** Use the ASD-STE100 writing principles covered by the skill for English. For Russian, use the mandatory [Russian adaptation](harness/skills/asd-ste100/references/russian.md). ASD-STE100 defines English, so do not describe the Russian adaptation as an official standard or claim certified compliance.
- **Clarity:** State the result or intended action first. Use short sentences, direct verbs, and one stable term for each concept. Give one instruction per sentence. Make the actor, condition, and expected result clear when they affect meaning. Remove filler, bureaucratic wording, and unnecessary jargon.
- **Precision:** Preserve facts, conditions, exceptions, negation, numbers, units, and uncertainty. Distinguish completed actions from plans and verified results from assumptions. Keep code, commands, paths, API identifiers, and exact quotations unchanged when simplifying surrounding prose.
- **Scope:** Apply the rules to communication without changing the requested task or its output format. Keep necessary explanations and verification results. The skill's rewrite-only format applies only when the user requests a text rewrite.

## Product rules

- **Purpose:** Optimize and automate the work of physicians and other medical professionals. When designing or refactoring any feature, prioritize ease of use and let the application take over routine work so the clinician can focus on the examination.
- **Design approach:** Start every feature design or refactoring from the clinician's goal and the routine work needed to achieve it. Identify which steps the application can perform, then design a flow that reaches the result with the fewest necessary interactions. Evaluate it by the clinician's time, effort, and convenience throughout the task, including data entry and delivery of the resulting report. Avoid unnecessary screens, repeated entry, and redundant confirmations.

### Examples of the design approach

These examples explain why the features exist and illustrate how to apply the product rules when designing or refactoring features.

**Voice form filling:** A clinician can fill scan fields manually, and the toolbar makes moving focus between fields convenient. Even with that toolbar, entering all examination data by hand is slow and requires many interactions. Voice filling lets the clinician dictate the necessary information naturally during the examination while the application extracts it into the appropriate fields. The feature's goal is to take over routine form entry and reduce interruptions to the examination. Extract as much as possible while preserving the meaning, medical terminology, measurements, and units, without inventing missing information. When interpretation is uncertain, ask for confirmation or correction only for the affected fields or speech fragments, retaining reliably interpreted data without requiring the clinician to repeat or reconfirm the entire form.

**Sending a report to work email:** The clinician needs to receive the completed report at work and transfer it into the medical information system. Copying the report and sending it through other services adds routine steps. Sending it directly to the configured work email in one action removes those steps and makes the report available in the clinician's work mailbox. The feature's goal is to simplify the path from the completed examination report to its use in the clinician's existing workflow.

## Architecture

The backend is split into two independently deployable services: `backend/main` and `backend/inference`.

- **Main backend** (`backend/main/`) — Python, FastAPI, Docker. Runs on a **non-GPU VM** and never performs inference itself: it builds the prompt, selects the model, and routes the request. It also sends reports by email through SMTP.
- **Inference service** (`backend/inference/`) — Python, FastAPI, Docker. Runs once per GPU host beside one or more local vLLM engines. It validates App Check, selects the configured engine by `modelId`, and performs model-agnostic structured generation. Existing single-model VMs remain supported; DGX Spark uses one backend and three vLLM containers.
- **iOS application** — SwiftUI, MVVM, SwiftData, Alamofire, Apple Foundation Models for on-device inference, Firebase, StoreKit 2, and backend-owned subscriptions.

A report-generation request follows this path:

```text
iOS ──► backend/main (non-GPU) ──► backend/inference + vLLM (model GPU VM)
```

App Check is validated **twice**: at the system entry point (`backend/main`) and again on the model machine (`backend/inference`). The `X-Firebase-AppCheck` header is forwarded unchanged, so both services validate the same token.

The main-backend check protects the public system entry point. The repeated check prevents direct access to a GPU VM that bypasses the main backend. Both VM groups are controlled by the developer.

Validation cannot be disabled: there is no flag or mode. Every application endpoint lives under the versioned `/v1` router and is protected by App Check in every environment. This includes `/v1/application_config` and the two `/v1/ultrasound/examination_*` configuration endpoints. The iOS client configures Firebase and its App Check interceptor before downloading these documents.

### Billing

The subscription ledger lives in `backend/main` with PostgreSQL and an independent
reconciliation worker. All client `/v1/subscriptions/*` routes retain App Check;
owner-specific operations additionally require an anonymous bearer secret. Base
and Pro are paid tiers. UUIDs and browser redirects never prove access.

`billing.json` contains one `products` array with `id`, `entitlement`, `period`,
`price` (`amountMinor`, `currencyIso2Code`), `titleLocaleKey` and
`priceTemplateLocaleKey`. The backend resolves these keys through `l10n.json`
and returns `title` and `priceTemplate` for the requested language. The protected
`/v1/subscriptions/plans` response uses the same product list.
The catalog also declares `tiers` with `id`, `titleLocaleKey` and
`featureLocaleKeys`. The response resolves them into `id`, `title` and `features`.
Segment labels and benefits come from these entities for both providers. IDs are shared by
Apple and YooKassa. Apple prices and periods come from StoreKit; the catalog's
RUB price applies to YooKassa. YooKassa supports weekly, monthly, six-month and annual
periods; orders and renewals retain their agreed price and month/day intervals.
Client plans use `SubscriptionPeriod` and the `period` field for those four periods.
Subscription sources are only `apple` and `yookassa`; keep Apple's verified
Production/Sandbox environment in the ledger's separate `apple_environment` field.
Every listed billing product is available for new purchases; do not add availability
flags to this catalog. Removing a product stops offering it. Existing YooKassa
renewals retain their snapshots; previously recorded Apple products retain their
tier for verified restoration and reconciliation even after catalog removal.
Purchase completion must match the selected product and confirmed provider evidence.
YooKassa responses include `planId`; match it and the exact payment ID before accepting
success. Pending StoreKit purchases require a new verified transaction for the selected
product, distinct from the transaction snapshot taken before purchase. An existing
active subscription alone must never close a pending purchase.

Russian iOS storefronts use `YooKassaPaymentController` and the official native
YooKassa SDK; other storefronts use StoreKit 2. SDK tokens are processed by the
App Check/bearer-protected prepare/tokenize/check payment routes. Only a canonical
provider result grants access. Payment tokens are never persisted in plaintext.
The backend uses pinned `yookassa` through `YooKassaSDKAdapter` and a per-call
`YooKassaSDKClient`. SDK processing runs in a worker thread; its transport bridges
to the lifespan-owned asynchronous HTTP client. Preserve absolute deadlines,
cancellation, isolated credentials and persisted idempotency keys. Never configure
SDK global credentials, enable raw payment-body logging or rely on the SDK retry
backoff setting as a network timeout.

Persist dispatch evidence and renewal method snapshots before provider I/O. An
unknown outcome keeps its operation identity even after renewal cancellation.
New purchases may replace only unsent expired renewals under the owner lock.
Reconcile completed payments as well as pending orders. Store refund IDs, states
and amounts separately from access, including partial refunds; callbacks and
worker retries must not duplicate money or paid periods.

Derive the YooKassa mode from `ENVIRONMENT`: development accepts only test
shops/payments, production accepts only live shops/payments. Verify the mode
before charging through `/me` and again in canonical payment processing. Keep
the temporary `IS_YOOKASSA_LIVE_ENABLED=false` launch gate until the real-payment
prerequisites below are implemented; environment selection alone cannot enable
real charges. Do not restore a separate test-mode environment flag.

`app.payment_main:app` is a separate browser/provider ingress: CSRF-protected `/pay`
forms and verified callbacks, with per-route body/rate policies from the shared
`server.json.endpoints` map. It is not a
client API bypass. YooKassa notifications must be checked against a canonical API
response; Apple transactions/notifications require verified signatures and current
server state. Keep real charges disabled until receipts and Apple external-purchase
reporting are implemented and all merchant/signing prerequisites are met. See
[`backend/main/BILLING.md`](backend/main/BILLING.md) and
[`deploy/billing/README.md`](deploy/billing/README.md).

### Environments

`ENVIRONMENT` (`development` or `production`) selects a directory under `backend/main/config/` and the matching YooKassa test/live mode. The application reads the same documents from this backend instead of the repository. Otherwise, pushing a new model to `master` could expose it to the app before the backend deployment knows about it, causing a physician to receive `400`. With the default `MODEL_SERVICE_TYPE=inference`, both environments use the same inference route and token validation. A development-staging check is meaningful because it exercises the same code and path; the configuration documents and YooKassa payment mode differ.

`MODEL_SERVICE_TYPE` selects the main backend's generation implementation independently of `ENVIRONMENT`: `inference` calls GPU VMs, while `mock` returns local RU/EN fixtures. VS Code's `Backend: Local Mock` profile selects `mock` with development configuration. App Check, configuration, localization, request validation, and SMTP remain real. Mock generation does not require an inference endpoint map; see [`backend/main/README.md`](backend/main/README.md).

### Timeouts

Timeouts are strictly nested from outside to inside, with each wrapper wider than the operation it contains:

```text
iOS client                    300  application.json -> network.timeoutIntervalForRequest
main server.json operation    130  main backend waits for the GPU VM
inference server.json         120  queue waiting and local engine request
```

An inner timeout must be shorter than its outer timeout; otherwise the caller can terminate the connection while the wrapped generation is still running.

With `MODEL_SERVICE_TYPE=inference`, every published model must have an entry in `backend/main/secrets/inference_endpoints.json` containing the URL of its GPU VM. A missing mapping is a configuration error.

## Code style

- **Boolean flags:** Name every boolean flag with the `is` prefix, for example `isChecked`, `isAvailable`, and `isRemarksVisible`. Use `is_` in Python snake_case names, for example `is_available`; fields shared with iOS use camelCase, for example `isAvailable`.
- **Class member order:** In every class, declare stored fields first, then initializers (constructors), then computed properties and getter/setter accessors, then methods. Apply the same order within each Swift extension block. Separate each nonempty group with a blank line and leave a blank line between every pair of initializers or methods, including empty implementations. Keep property observers with stored fields. Preserve the relative order of stored fields so initialization behavior stays unchanged; order view-model methods according to the View-model method order rule below.
- **API string contract:** Required response strings must contain non-whitespace text. Normalize blank optional strings to `null` on the backend, including strings assembled there. Clients rely on optional presence and do not repeat empty-string checks for validated response fields.
- **Persistence results:** Propagate storage failures to the caller. A read returns `nil` or an empty collection only for absent or empty data, never to hide a storage or decoding failure. Report success, clear an examination form or draft, and notify dependent modules only after the required persistence operation succeeds. Preserve unsaved data when an operation fails; autosave must retain pending changes and report failures rather than silently discard them. Replacing a stored value must preserve the previous value if the replacement fails.
- **Defensive storage-to-domain mapping:** Make new preference fields optional in persistence models when stored records can omit them. Map optional enum preferences through failable parsing: trim surrounding whitespace, accept recognized values, and use explicit domain defaults for missing, blank or unknown values. These conversions must not throw, assert, force-unwrap or terminate the application. For `SettingsAIDB`, default `transcriberType` to `whisperKit` and `transcriptParserType` to `server`. Actual storage I/O and structural decoding failures continue to propagate under the Persistence results rule.

### Design and refactoring

- **Release status and compatibility:** The application has not been released. Until the first release, refactoring does not require support for previous client versions. Update backend and client contracts, localization keys, and their checks together; do not introduce compatibility aliases, deprecated keys, or adapters solely to support previous client versions.
- **Historical evaluation evidence:** Preserve recorded evaluation outputs in their original schema so results remain traceable to the run that produced them. Evaluation tools may explicitly normalize historical schemas when reading these artifacts. Keep such adapters in evaluation code; they do not authorize compatibility aliases in the application or backend API. Fixtures exercising the current transport contract must follow its current schema.
- **Existing conventions:** Write code consistently with the project's current architecture, naming, structure, and implementation style. Agree on any conceptual or architectural change with the user before implementing it, even when the code change is small.
- **Simplicity and readability:** Prefer the simplest clear implementation that solves the actual requirement. Keep code easy to read and change. Do not introduce extra layers, marker protocols, wrapper types, or state classes without a concrete responsibility that makes the code easier to understand. Before adding an abstraction, check whether an existing type or a direct implementation is sufficient.
- **Responsibilities:** Avoid spaghetti code. Keep responsibilities explicit and cohesive, dependencies clear, and coupling low. Use encapsulation, composition, polymorphism, and SOLID principles; choose patterns that solve the actual problem without introducing unnecessary abstractions.
- **Dynamic implementation selection:** When a dependency implementation depends on changeable external context, its factory obtains and interprets that context and selects the implementation. Consumers depend on the factory and request an implementation before each operation; they do not duplicate selection conditions, retain the selected implementation between operations, or observe context changes solely to switch dependencies. Initialization creates the factory and its dependencies without resolving a provider or storing a context snapshot in the container. A local implementation reference may remain fixed until the operation completes. The factory may reuse existing immutable instances; requesting an implementation does not require constructing a new object. For subscriptions, resolve the current storefront inside `SubscriptionRepositoryFactory` for plans and new purchases, and use the purchase source for existing-purchase operations. Do not observe storefront changes or preload storefront/provider selection during initialization.
- **Refactoring approval:** Before a refactoring that changes substantial code or many files, present a concrete proposed design: types and their responsibilities, dependency relationships, selected patterns and why they fit, and the migration scope. Obtain the user's approval of that design before starting the refactoring.

Use the following pattern catalog when evaluating a design. Apply relevant patterns rather than requiring every pattern in each feature. The catalog includes classic GoF patterns and common additional patterns; it is not an exhaustive list of every published pattern.

- **Creational (GoF):** Abstract Factory, Builder, Factory Method, Prototype.
- **Structural (GoF):** Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy.
- **Behavioral (GoF):** Chain of Responsibility, Command, Interpreter, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method, Visitor.
- **Additional object-oriented patterns:** Dependency Injection, Null Object, Object Pool, Specification.
- **Architecture and application patterns:** MVVM (the required client architecture), MVC, MVP, Repository, Unit of Work, Service Layer, Coordinator, Router, Composition Root. Listing an alternative architecture does not authorize replacing the project's existing architecture; such changes require prior agreement.

### Localization

- **Backend ownership:** The main backend is the source of truth for application localization. Keep the client thin: application UI text, language-dependent phrases and words, parsing patterns, numeric vocabularies, and schema descriptions live in backend localization catalogs.
- **Client exceptions:** Local application localization is limited to initialization errors and mandatory major-version update UI, which must work before backend catalogs are available. Mandatory iOS system bundle strings, such as permission descriptions and the display name, remain in `InfoPlist.xcstrings` because iOS reads them from the installed bundle. Do not add local copies or fallbacks for other application text.
- **Feature keys:** Name application UI localization keys as `{featureName}{keyName}` in lower camel case: a feature prefix such as `scan`, `history`, `onBoarding`, or `legalUpdate`, followed by a specific key name starting with an uppercase letter. For example: `scanUserDescription`, `scanServiceAvailabilityDescription`, `historyTitle`, `onBoardingContinueButton`, and `scanPatientNamePlaceholder`. Use the same key names in backend catalogs, `L10NKey`, and the permitted local bootstrap catalog.
- **Key ordering:** Always keep all localization keys in ascending alphabetical order by their full key names in every localization catalog and key declaration, including backend catalogs, `L10NKey`, and permitted client bundle catalogs. Preserve this ordering whenever adding, renaming, or editing keys.
- **Semantic suffixes:** Choose the suffix by the text's UI role. Use the exact spellings `Title`, `Label`, `Description`, `Button`, and `Placeholder`.

| Suffix | Purpose | Example |
|---|---|---|
| `Title` | Screen or bottom-sheet title | `historyTitle` |
| `Label` | Short section or field name | `scanPatientLabel` |
| `Description` | Medium or long explanatory text | `scanServiceAvailabilityDescription` |
| `Button` | Button wording specific to a feature | `scanGenerateReportButton` |
| `Placeholder` | Field placeholder specific to a feature | `scanPatientNamePlaceholder` |

- **Shared buttons:** Use the shared `button` prefix for generic actions that are not tied to a feature, for example `buttonAccept` and `buttonBack`. Reuse these keys across features. When the button phrase belongs to a particular feature, use that feature's prefix and the `Button` suffix instead.
- **Catalog usage:** UI accesses `L10N` with `L10NKey`; named substitutions use `L10NParameter` through `values: [L10NParameter: String]`. Views receive the catalog through `.localization(container.l10n)` and `@EnvironmentObject`, and non-UI code receives it through arguments. Select one catalog using `Language.currentLocale` and inject it through arguments. Do not embed or mix localized RU/EN matching rules in Swift models, parsers, or policies. Technical identifiers, protocol syntax, and test input data are not translations.

- **Entity localization comes from configuration:** Declare localization metadata beside each entity's data in its backend configuration, using fields such as `titleLocaleKey`, `descriptionLocaleKey` and `priceTemplateLocaleKey`. Resolve these references on the backend and return localized text or templates with the entity in the API response. The client must never select an entity's localization key by its type, ID, enum case, tier, period or other attributes. This prohibits `switch`, `if`, ternary expressions and lookup dictionaries that map entity attributes to localization keys anywhere in client code, including views, view models, models, extensions, repositories and helpers. Moving such a mapping to another client type does not satisfy this rule. The client displays the entity's supplied text and can substitute runtime values, such as a StoreKit price, into a server-supplied template. Follow the subscription products in `billing.json` and the ultrasound examination type and neural model configurations as examples.

Put every nonempty call argument and declaration parameter on its own line, including single arguments, with a trailing comma. Add a phase only when it changes the scenario, available actions, or presentation. - **State publication and transitions:** `DStateViewModel<State>` owns `@Published private(set) var state: State`; transitions use `emit`. The generic parameter accepts `any FeatureStateProtocol` without requiring the existential to conform to a generic protocol constraint. States are immutable classes: use `let` for stored data and publish every change by passing a new instance to `emit`, including changes within the same phase such as legal acceptance or proposal selection. States do not conform to `ObservableObject` and do not declare `@Published` or `@NestedObservableObject`; the base view model does not subscribe to state internals.
- **State equality and repeated publication:** Every concrete lifecycle state implements `Equatable`, isolated to `@MainActor` with its state. Equal states have the same concrete type and equal stored data; stateless instances of the same type are equal. Compare all operation and presentation data, including changed progress, selected fields, and results. `DStateViewModel.emit` owns equality checks and suppresses repeated equal states before publication and animation. Feature view models call `emit` directly without checking whether the next state duplicates the current state. Keep guards that prevent duplicate side effects or reject stale asynchronous results: checking an operation's state instance serves a different purpose and must protect the entire callback, not only publication. Compare opaque errors conservatively; different associated values must never collapse merely because their bridged NSError domain and code match.

Direct state assignment in the initializer does not start an animation. Observe root presentation state and switch its content inside a SwiftUI view, rather than inside `App.body` / `SceneBuilder`, so transitions update within the view hierarchy. Animate shared `@Published` data through `DStateViewModel.animate` in the corresponding view-model action; it uses the same default animation and accepts an explicit override. Do not repeat `withAnimation` wrappers and the default duration in feature view models. Views declare `transition` and `contentTransition` effects but do not attach implicit `animation(_:value:)` modifiers to view-model state or published data. Gesture and local geometry animations remain in views or design-system components. Use stable, typed presentation identifiers instead of random UUIDs for root screen identity: Initial and Initializing share one splash rendering branch and its identifier; a retry that retains the error view retains the error identifier. An enum used for presentation identity does not replace the class-based state composition.
- **Module initialization:** Each module loads its own screen-specific data through its view model. Do not preload a module's data in application initialization or another root view model merely to hide its first loading state. Application-wide configuration and existing shared domain data retain their own owners.
- **View-model initialization lifecycle:** Keep constructors limited to assigning stored properties, constructing owned dependencies and setting the initial state. Move startup behavior such as observation registration, loading and asynchronous tasks into `onInit`, invoked through the owning view's lifecycle; do not call it from the constructor. Root view models guard repeated `onInit` calls so view reappearance cannot duplicate subscriptions or tasks. Modules retain the existing `View.onAppear` → `DModuleViewModel.onAppear` → `onInit` chain: the base method guards one-time initialization and establishes common subscription observation before invoking the feature hook. Application dependency bootstrap retains its explicit `ApplicationRootViewModel.initialize()` entry point. The amount of startup code does not exempt it from this rule.
- **State data ownership:** States own the data produced by their scenario and the user's selection within those data: a loaded catalog, selected category or item, an error, a current-operation snapshot, or a proposal awaiting confirmation. For example, paywall `plans`, `selectedType` and `selectedPlanID` belong to the states that have loaded subscription data, rather than separate `@Published` view-model fields. Publish catalog or selection changes as one immutable state through `emit`; do not keep a parallel representation of that screen state in the view model. A loading state must not supply dummy empty catalogs or default selections just to satisfy a shared interface. Preserve valid loaded data through purchase, pending and operation-failure phases. Data fixed independently of the scenario belongs to the view model, including contact email, application version, module arguments, fixed screen titles, selection limits and date bounds. State objects remain immutable.
- **State protocol contracts:** Require only members that have a meaningful value in every conforming state. Keep phase-specific fields on the concrete class instead of forcing other states to return `nil`, empty values, or dummy implementations. For example, only SubscriptionRootActiveState owns a nonoptional subscription status; SubscriptionRootInactiveState has no status field. Shared consumers resolve phase-specific data with a typed `switch` in the owning view model.
- **View-model infrastructure and orthogonal processes:** Keep dependencies, focus handling, stable input controllers, tasks and independently owned processes on the view model. Use `let` for fixed dependencies and `@NestedObservableObject` for concrete observable controllers. Data being needed in several phases does not justify separate `@Published` fields when it belongs to the same screen scenario; that data must remain in its immutable states. Do not wrap common data in FormState, DataState, SessionState or similar containers just to pass the same object through every phase. Ordinary boolean data and derived validation, navigation or availability values are allowed; separate phase flags such as `isLoading` or `isSaving` are not.
- **State observation and UI ownership:** `@Published state` publishes both phase changes and updated data in a new instance of the same phase. `@NestedObservableObject` forwards controller changes to the owning view model. Keep necessary explicit subscriptions for observable protocol existentials unsupported by that package, and cancel subscriptions when their owner is released or its observed controller is replaced. Preserve controller identity and entered values across loading and error phases. Root-to-module notifications must deliver the new data; notifications that refresh getter-based snapshots must run after the root data has changed. Views use `@StateObject` for feature-view-model ownership, private `@EnvironmentObject` for descendants, and `@ObservedObject` for externally owned framework controllers. Local `@State` is limited to view mechanics such as gestures, measured geometry, and focus synchronization.
- **View disappearance lifecycle:** `DModuleViewModel` defines `onDisappear` as the module lifecycle cleanup hook. Every override must call `super.onDisappear()` before feature-specific cleanup. The base hook cancels and clears its serialized UI `operationTask` and subscription observation; `onAppear` restores that observation without repeating `onInit`. Keep operations that must outlive the screen in their root view model or service, rather than in the module task slot. Other independently owned tasks retain their explicit lifecycle policy. In application code, invoke a feature view model's `onDisappear` only through the owning view's `.onDisappear` modifier, for example `.onDisappear(perform: viewModel.onDisappear)`. Never call it manually from interaction handlers, asynchronous success/error callbacks, coordinators, or other view-model methods to simulate disappearance. Close the screen or sheet through its coordinator and let the view deliver the lifecycle event. When late results or repeated actions must be blocked immediately, invalidate the presentation's activity flag or token before requesting navigation; keep disappearance cleanup in `onDisappear`.
- **State rendering:** When a module has only one concrete state, render its view directly without `switch`, type checks, or an unexpected-state branch. When several states exist, select presentation and state-dependent behavior with `switch` and typed cases such as `case let state as ScanLoadingState`, including states adapted from camera, speech, or web controllers. Do not choose a phase with `if`/`else`, `if case`, `is` checks, or independent `is...` flags, and do not let a view inspect a controller's lifecycle flags to bypass its module state. Swift does not make protocol/class switches exhaustive; when no presentation matches the current state, render `EmptyView()` in the fallback branch. Do not use a diagnostic view, assertion, or precondition failure for an unrecognized presentation state. Small local values derived through `switch` may adapt states to existing control APIs that require booleans, optional callbacks, icons, or dimensions; these are render-time adapter values, not published phase flags. Ordinary input validation, optional domain values, and collection contents are data, not alternate phase publishers.
- **State mutation and persistence:** Change state through explicit view-model methods by emitting a new immutable instance, and perform persistence or other side effects in those methods. Never mutate fields on the current state object. Do not use `didSet`, `willSet`, or custom getter/setter accessors to mutate state or trigger side effects. A failure must retain entered data, prior content, and any already generated result required for a retry. Retrying a failed local report save must not invoke generation again. Clear forms, dismiss successful save flows, and notify dependent modules only after required persistence succeeds. Guard duplicate operations through the current state, and ignore stale asynchronous results after dismissal, cancellation, or replacement of the operation's state. Read-only computed data on states remains permitted; view-valued helpers follow the View composition rule below.
- **Root view models:** State shared between several screens or throughout the application belongs to root view models. Their type names must end with the literal `RootViewModel` suffix (`{FeatureName}RootViewModel`), for example `ApplicationRootViewModel` or `ExaminationRootViewModel`.
- **Module data ownership and isolation:** Each module fetches and owns its own screen data through repositories or factories obtained from `DependencyContainer`. Do not expose data-loading methods on another module or root view model as a substitute for calling a repository, including through forwarding closures. Root view models fetch and own their shared state and expose only that state and operations needed to maintain it. Share state getters, updates and observations through the existing closure boundaries; do not turn root view models into repository facades. For example, `PaywallViewModel` loads the paywall catalog into its module states, while shared subscription status, payment tracking and identity coordination belong to `SubscriptionRootViewModel`.
- **Module communication:** Direct interaction between client module view models is prohibited: do not pass, store, or call another module's view model. Exchange data and update state only through closures carried in the next module's `FeatureArguments` and forwarded to its view-model initializer, such as `getIsActive`, `getAvailableRequestCount`, `getSettingsAIAvailability`, and `onNeuralModelSelected`.
- **Root-to-module communication:** Interaction between a root view model and a module view model must occur only through closures passed into the module view model's initializer. Use getter and callback closures for state access and updates, and observation closures returning cancellable subscriptions to preserve reactive UI updates; never inject the root view model instance into a module view model or let the module access it directly. `DependencyContainer` must not be used to bypass these closure boundaries.
- **View-model propagation:** `FeatureScreenView` / `FeatureBottomSheetView` owns the model received from the entry view through `@StateObject` and injects that same instance into its subtree with `.environmentObject`. Every descendant feature view obtains `FeatureViewModel` only through private `@EnvironmentObject`; never pass it through descendant constructors or store it as `@ObservedObject` or a plain property. Read actions and shared screen data/controllers from that environment object instead of forwarding them as individual constructor arguments. Concrete phase-state snapshots follow the State-specific view inputs rule below. Repeated row identities/domain items and reusable design-system component inputs remain explicit inputs. The entry-view-to-presentation-view handoff is the required constructor-based ownership boundary.
- **State-specific view inputs:** When a parent selects a concrete state and renders a child view dedicated to that phase, pass the immutable state instance through the child's initializer as a typed `let` property, for example `let state: ScanSpeechReviewProposalState`. The child and its state-dependent descendants render that snapshot directly instead of switching, casting, or checking `viewModel.state` again to recover the already selected phase. Pass updated snapshots on every parent render, including updates within the same phase; do not copy them into `@State` or make them observable. Keep the module's single view model in `@EnvironmentObject` for actions and shared data/controllers. Do not create another view model, force-cast its state, or add fallback UI inside a view whose concrete state is guaranteed by its input. Containers that render several phases may own their state switch; avoid redundant checks of a phase already resolved in the same branch, including binding getters.
- **View declarations:** Keep views limited to input/state properties, initializers, and declarative `body`. Do not declare additional view-valued computed properties or getters. Do not declare `func` methods in any view, including rendering helpers, event handlers, or business logic. The only method exception is mandatory protocol entry points in framework adapters, such as `UIViewRepresentable.makeUIView`, `updateUIView`, and `makeCoordinator`; these delegate behavior to the feature view model or an adapter/controller and contain no unrelated presentation helpers. Other methods belong in the feature's view model; action and lifecycle closures call those methods. Express layout directly in `body` by composing separate SwiftUI view types.
- **View source spacing:** Separate adjacent views, subviews and conditional rendering blocks with one blank line in result-builder scopes, including nested stacks. Keep a modifier chain attached to its view. Do not add blank lines between call arguments or ordinary event-handler statements merely because they occur in a View. Every nonempty closure, conditional body, function body and accessor body starts on the next line after its opening brace (or closure signature) and places its closing brace on a separate line. Empty bodies may remain inline. Use `make format-ios`; `make lint-ios` checks these rules.
- **One state switch per view:** A View body may contain at most one `switch`, including nested switches and local value mappings. Extract additional conditional presentation areas into named module-prefixed subviews. Each subview may have its own switch and receives its typed snapshot and inputs. When several flags describe the same state, derive them together in one switch. Do not hide repeated lifecycle dispatch behind casts or Boolean getters. Ordinary Boolean conditions and Optional unwrapping remain valid for presence checks.
- **View composition:** Do not implement view fragments as methods, stored or local helper variables, computed properties, or explicit getters that construct or return views. This includes `func ... -> some View`, `var ...: some View`, `@ViewBuilder` helpers, concrete view types, and `AnyView`. Extract each fragment into a separate named SwiftUI view type and instantiate it directly in the owning view's `body`. Do not move a view-producing helper into a view model or service. Required protocol presentation entry points, such as `View.body`, `ViewModifier.body(content:)`, and style `makeBody`, required framework adapter implementations, and existing view-modifier APIs remain valid integration boundaries. Components may store view content received as an explicit input; they must not use helper variables to construct additional view fragments.
- **View-model method order:** Arrange public interaction methods in the order their controls appear from top to bottom on the screen or bottom sheet. Group methods by the corresponding visible section so that reading the public API indicates where each interaction occurs. Put initialization and lifecycle methods before the interaction groups, then private helpers after the public methods, following the same section order where applicable.
- **Environment privacy:** `@EnvironmentObject` properties are private, except `theme` when it implements the `DViewProtocol` requirement. Declare that theme directly as `@EnvironmentObject var theme: DTheme` (public in public components), without a separate stored property or forwarding getter.
- **Presentation ownership:** The module view model owns lifecycle decisions and shared presentation data. Presentation containers select the current phase from its state; phase-specific descendants render the concrete snapshot passed by their parent. Read shared values from the view model. Use existing domain enums such as `SubscriptionFeatureAvailability` for access-dependent controls. Do not duplicate lifecycle state with parallel loading or visibility flags, and do not read unrelated environment objects for lifecycle decisions.
- **Protocol names:** Every project-owned Swift protocol must end with the literal `Protocol` suffix, including feature state protocols. Do not rename protocols supplied by Apple or third-party packages.
- **Naming:** Prefix ultrasound domain models with `US` and database models with the `DB` suffix. Use the `D` prefix for foundational framework types such as `DDatabase`, `DTheme`, and `DHttpClient`, and for the application's shared module base `DModuleViewModel`. Feature and root view models follow their own naming rules. All types declared in `DoglyadSpeech`, including nested helper types, use the `DSpeech` prefix. Keep engine-specific speech files in `SpeechAnalyzer/`, `SFSpeechRecognizer/`, and `WhisperKit/`; keep shared types outside these folders. Keep transcript confidence and decoding span types in `DoglyadSpeech/Span/`.
- **Application models:** Place models owned by the `Doglyad` application target under `ios/Doglyad/Domain/`, grouped by feature; repositories contain persistence/transport behavior, not model declarations or a `DTO/` folder. Do not use the `DTO` suffix for application models. Name HTTP payloads by their role with `Request` or `Response`, for example `BillingPreparePaymentRequest` and `BillingPaymentResponse`; ordinary domain values retain semantic names such as `SubscriptionStatus` and `BillingPaymentState`. Models owned by reusable framework targets remain in the corresponding framework's semantic folders.
- **Domain model prefixes:** Start domain model names with a recognizable owning-domain prefix, such as `USExamination` (ultrasound examinations), `Billing`, or `Subscription`. Put the model's purpose or variation after that prefix: use `USExaminationRecentTypes`, rather than `RecentUSExaminationTypes`. Keep the prefix consistent with the semantic folder and related models so names group naturally and make their responsibility clear.
- **Localization:** Follow the shared Localization rules above for backend ownership, permitted client strings, key names, suffixes, and catalog injection.
- **Neural module:** Shared types use `DNeural`; ultrasound-specific types, including nested helpers, use `DNeuralUltrasound` and live in `UltrasoundExamination/`. Keep `DNeuralUltrasoundModelFactory` at that folder's root, above its Foundation Models integration. Shared code must not depend on ultrasound field IDs, schemas, or catalogs. Keep `DNeuralGenerationParameters`, `DNeuralModelError`, and `DNeuralModelProtocol` at the module root. Keep the ultrasound model and foundation provider protocols in `UltrasoundExamination/Contract/`. Keep shared values and numeric vocabularies in semantic folders at the module level; keep ultrasound contracts, parsing, validation, localization, server implementations and DTOs under `UltrasoundExamination/`. Extensions of shared values that parse ultrasound fields belong inside that domain folder. Experimental candidates and historical legacy schemas used only by comparisons belong in `DoglyadTests/VoiceSupport/`. Both Foundation Models and server parsing implement `DNeuralUltrasoundModelProtocol`; the factory selects the implementation, and `DNeuralUltrasoundProposalProcessor` owns shared validation/reconciliation. Server HTTP stays in the application repository through `DNeuralUltrasoundServerTransportProtocol`.
- **Utilities and extensions:** The client `Utility` directory is for extensions, mock data and factories, view modifiers, and integration classes tightly coupled to external packages, such as the App Check provider factory and HTTP interceptor. Place these in `ios/Doglyad/Utility/`, using `Extension/` for extensions of framework and package types, `Mock/` for mock data and factories, `Modifier/` for view modifiers, and package-specific folders such as `AppCheck/` for integrations. Do not scatter these utilities across feature modules. Application managers retain their established folders under `ios/Doglyad/Application/`; `PermissionManager` and `ConnectionManager` belong in `ios/Doglyad/Application/Application/Manager/`.
- **Extension organization:** Group extensions by the extended type within their owning target. Keep extensions of the same class, struct, or other type together in one file and combine compatible members in a single extension block. Do not create separate files for individual extension methods or features; for example, `View.localization`, `View.paidBadge`, and `View.previewable` belong together in `ios/Doglyad/Utility/Extension/View.swift`.
- **Modules:** Keep reusable domain services and components in the local framework targets `DoglyadUI`, `DoglyadDatabase`, `DoglyadNetwork`, `DoglyadNeuralModel`, `DoglyadCamera`, and `DoglyadSpeech`. Client utilities and framework extensions follow the locations specified above.
- **External SPM dependencies:** Firebase, Alamofire, YooKassa Payments, swift-markdown-ui, SwiftMessages, SwiftUI-Shimmer, BottomSheet, WhisperKit, `DependencyInitializer`, `NestedObservableObject`, `Handler`, and `Router`. FluidAudio is used by the experimental Parakeet comparison in tests.
- **Enum branching and comparison:** Use an exhaustive `switch` without `default` when different enum cases require different behavior, for example visibility rules based on `SubscriptionFeatureAvailability`. Adding a case must require handling in those branches. Use `==` or `!=` for ordinary value comparisons, including whether the selected and requested subscription types or periods match. Never enumerate tuple-case combinations merely to implement equality or inequality. This exception does not permit replacing case-specific behavior with a check against one known case. For non-frozen enums owned by an external SDK, handle every known case explicitly and use `@unknown default` only for future SDK cases; this exception does not apply to project-owned enums.

## Constraints

- Preserve camelCase fields in backend Pydantic models because they are the iOS API contract.
- Build visible client UI and its style from `DoglyadUI` components, including loading shimmer. Use native SwiftUI containers only under the Design system rule above, without introducing native visible UI or styling.
- Use visual resources only through `DoglyadUI` or `ios/Doglyad/Assets.xcassets`; direct use of system or third-party framework resources is prohibited.
- Client module view models communicate only through closures in module arguments; root-to-module interaction uses only closures in the module view-model initializer.
- Use only `DoglyadNetwork` resources for client networking.
- Use only `DoglyadDatabase` resources for client persistence.
- Do not modify `ios/DoglyadNeuralModel/Resources/`, `ios/Config/`, `ios/Firebase/`, `backend/main/secrets/`, or `backend/inference/secrets/`. For local iOS preparation, `make init-ios-local` may update only `BASE_URL` in `ios/Config/Config.Local.xcconfig`.
- The main backend does not run inference and lives on a non-GPU VM. All model execution belongs in `backend/inference/`.
- Prompts, application localization, and templates live in the main backend, with only the explicitly listed bootstrap and iOS system localization exceptions on the client. The inference service receives final text and only performs generation.

## Commands

The `Makefile` contains all project commands. Common targets:

- `make venv` / `make pip-install` — create a Python 3.11 environment and install `backend/main/requirements.txt`.
- `make format` — run the iOS and Python formatting pipelines.
- `make format-backend` / `make lint-backend` — apply or check argument line breaks and Ruff formatting for every Python source under `backend/`.
- `make format-ios` / `make lint-ios` — apply or check SwiftFormat and the mandatory argument line breaks without modifying protected resource/configuration folders.
- `make start-local-billing` / `make stop-local-billing` — start local PostgreSQL 17 and apply migrations, or stop it while preserving its Docker volume. VS Code's `Backend: Local Mock` runs this preparation before the API and supplies the matching loopback-only database URL.
- `make reset-local-billing` — recreate the dedicated local PostgreSQL volume and apply migrations. Requires the local API to be stopped and a local Docker Unix socket. This deletes all local billing data; it is the prelaunch action only for `Backend: Local Mock (Cold)` and `Backend: Local Inference (Cold)`.
- `make sync-harness` / `make check-harness` — generate or verify local agent settings and skills from `harness/` without starting application or model checks.
- `make init-ios-local` — update the local iOS `BASE_URL` with the `en0` address; see [init-ios-local](harness/skills/init-ios-local/SKILL.md).
- `make build-ios-debug-local` / `make build-ios-debug-development` / `make build-ios-release-development` / `make build-ios-release-production` — build the matching Xcode scheme; override `IOS_DEST` to select another simulator.
- `make start-backend-main-development` / `make start-backend-main-production` — run the main backend with the matching environment profile.
- `make check-infrastructure` / `make update-infrastructure` — check or update all inventoried existing backend VMs through the central deployment script. Set `INFRASTRUCTURE_SCOPE=main` to select both main environments without contacting inference VMs; inference availability/routes are unverified in this mode. See `deploy/README.md`; `start-backend-*` builds from source and is not the deployed-fleet update path.
- `make render-inference` — generate a GPU-host deployment from `INFERENCE_PROFILE` into `INFERENCE_OUTPUT` (defaults: the DGX profile and `build/inference/dgx-spark`). Does not connect to hosts or start containers. Edit profiles, not generated Compose files.
- `make start-backend-main-logs` / `make stop-backend-main` — follow logs or stop the main backend.
- `make start-backend-inference` / `make start-backend-inference-logs` / `make stop-backend-inference` — manage the inference stack **on a GPU VM**, not on a developer machine. The stack starts vLLM with `SERVED_MODEL_ID` and the adjacent inference service.
